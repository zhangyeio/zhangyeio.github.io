FDE 的工作贯穿业务问题识别、工程实现、真实使用与产品改进。企业需要明确谁定义问题、谁验证结果，以及系统上线后由谁持续维护。

本文以中文一线访谈为背景，结合官方技术资料，将这些问题整理成可执行、可查阅的实践手册。你可以按目录系统阅读，也可以直接复制项目模板，用于调研、试点、验收与交接。

版本：1.1 · 最近审校：2026 年 10 月 19 日  
适用对象：希望理解或转型 FDE 的工程师、产品经理、解决方案人员，以及准备开展 AI 项目的团队负责人。  
适用范围：以企业 AI 应用与产品型 FDE 为主；基础设施型 FDE 可复用需求、验证和交付方法，技术能力侧重点需调整。

> 使用说明：本文以六份中文资料为背景，并补充截至审校日可访问的官方技术文档。来源经验与技术依据集中在第 2、6、7、14 节；其余框架、清单、流程、模板和算例是本文的综合建议，不构成行业统一标准。时间安排、样本规模和目标数值均需根据项目风险与现场条件重新确定。全文没有将招聘薪资、融资金额或行业增长预测作为执行依据。

**本次审校结论：**业务问题定义、现场验证和产品反馈仍然成立；需要加强的是任务执行系统的设计与持续运营。1.1 版将技术选择改为并行比较方案，补充 MCP／Skills 的职责边界、长任务状态恢复、分级自主执行、轨迹与重复试验评估，以及采购部署和双方的经济性。新增做法均需按项目选用，不要求每个试点建设完整平台。

## 1. 先建立正确的工作模型

### 1.1 本文采用的工作定义

FDE 是 Forward Deployed Engineer 的缩写，中文常译为前线部署工程师或前沿部署工程师。本文把它理解为：**贴近客户真实业务，以工程方式将尚不清晰的问题转化为能运行、能验证、有人使用的解决方案，并推动现场经验形成可复用能力的角色。**

这是一种工作模型，不是所有公司的统一岗位说明。判断一份工作是否符合这个模型，要看它有多大的问题定义权、实施能力和结果责任，而非只看职位名称。[量子位从业者访谈](https://ad.36kr.com/p/4011048293666944)

### 1.2 FDE 要完成的两条链路

**客户链路：**观察真实流程 → 选定问题 → 定义成功 → 实现系统 → 小范围使用 → 评估结果 → 交接运营。

**产品链路：**收集现场失败 → 区分个性与共性 → 改进产品或工具 → 回归验证 → 在后续项目验证复用收益。

本文建议同时管理这两条链路。第一条决定客户是否受益；第二条决定团队能否持续提高交付效率。只完成一条，并不说明项目无价值，但需要如实描述其商业与组织性质。

### 1.3 用四个问题识别工作的实质

1. 谁负责把客户的模糊诉求变成可验证的问题？
2. 谁能实际修改系统，并协调必要的数据与权限？
3. 谁确认业务是否改善，谁负责日常运营？
4. 哪些成果会进入产品，下一个同类项目为什么会更容易？

例如，“做一个知识库机器人”只是交付物描述。可执行的问题定义应该进一步说明：服务哪类员工、处理哪类任务、允许访问什么信息、成功如何判断、何时转交人工。

### 1.4 需要纠正的理解偏差

| 常见理解 | 更有用的工作判断 |
|---|---|
| FDE 就是到客户办公室驻场 | 是否需要驻场取决于信息获取难度；远程也可能形成高质量协作 |
| 会搭 Agent 就能胜任 | 还需理解流程、连接系统、评估效果、处理异常并完成交接 |
| FDE 应该一个人包办全部工作 | 需要有人推动端到端闭环，同时保留清楚的专业分工和客户责任 |
| 只要上线就完成任务 | 上线、稳定运行、持续使用、产生收益是不同的验证层次 |
| 所有客户都应建设完整 Ontology | 从当前任务所需的对象、规则、关系和权限开始，避免先造大型平台 |
| 客户提出的需求都要满足 | 需要判断价值、可行性、范围和代价，保留拒绝与延期的能力 |

### 2.2 综合后可以形成的工作判断

**第一，客户说出的需求需要被检验。**现场观察、历史记录与一线操作，往往比会议中的流程描述更接近实际工作。本文据此建议把流程观察和基线记录放到开发之前。

**第二，原型是发现错误理解的工具。**让真实使用者操作原型，比只给管理者演示更容易暴露漏掉的审批、异常和边界条件。因此，原型阶段应留下否定意见及修正记录。

**第三，责任应落实为操作权限与处理机制。**谁批准业务规则、谁批准系统写入、出错谁接管，都应落实到具体人员和操作步骤，而非只写一句“对结果负责”。

**第四，复用需要被验证。**只有当后续项目在可比条件下更容易实施，或者维护负担下降，才有证据说明沉淀产生了价值。代码数量和文档数量不能替代这类证据。

以上四点是本文从材料中形成的综合判断；下一节起，将它们转为可执行的方法。

### 2.3 尚无统一答案的问题

- **是否必须驻场：**需要观察物理操作、建立信任或处理隐性知识时，驻场往往有帮助；明确的开发者接口与性能任务可能更适合远程协作。
- **FDE 归哪个部门：**关键在于能否获得工程支持、推动产品改动，并对客户结果承担合理责任。归属工程、交付或独立业务团队都需要检验相应激励。
- **应偏重资深技术还是行业理解：**取决于项目主要不确定性。推理优化与工厂工艺改造不应采用相同的招聘标准。
- **深度定制能否规模化：**要看共性是否足够强、客户是否可分群，以及可复用能力的维护成本。

### 2.4 从当前技术与企业应用角度，需要更新的判断

本次核对了工作流与 Agent 的区别、上下文管理、任务运行环境、评估、接入协议和企业采用指南。官方资料说明了可用的工程方法，但不证明某个产品在你的业务上一定有效；本文的实施要求是据此形成的建议。

| 1.0 版的不足 | 1.1 版调整 | 实际用途 |
|---|---|---|
| 技术顺序容易被读成必须逐级升级 | 按任务比较现成产品、固定工作流与 Agent；尽早建立强模型基线 | 避免为模型旧短板堆叠长期维护逻辑 |
| 主要以文本、检索和回复草稿为例 | 补充结构化业务数据、图像／语音与界面操作的接入判断 | 覆盖真实企业系统的多类输入和操作方式 |
| 有权限要求，但执行边界不够具体 | 按操作影响设置自主范围，补身份、状态、停止与恢复规则 | 支持可控执行，减少无意义的逐步审批 |
| 评估偏重最终答案 | 同时检查最终业务状态、执行记录和重复运行稳定性 | 发现“答对了但实际没做成”等问题 |
| 交接后运营安排较薄 | 补充系统登记、变更验证、持续监测与退出 | 防止上线后无人负责 |
| 收益计算侧重客户节省工时 | 同时评估总投入、价值兑现与供应方交付成本 | 判断试点是否值得扩围和长期服务 |

例如，Anthropic 在 2026 年的运行架构文章中指出，曾用于补偿旧模型能力的运行逻辑可能在模型升级后失去必要性。因此，模型更新后的评估也应检查哪些复杂设计可以删除。[技术依据 T4](https://www.anthropic.com/engineering/managed-agents)

## 3. 岗位边界与团队责任

### 3.1 与相邻岗位如何协作

下表是项目分工建议，实际职责以团队约定为准。成熟的实施、咨询与客户成功团队也可能承担其中多项责任。

| 角色 | 通常关注的问题 | 与 FDE 的协作接口 |
|---|---|---|
| 产品研发 | 哪些能力应该服务多类客户 | FDE 提供可复现问题、使用证据与共性判断，研发维护产品能力 |
| 解决方案／售前 | 方案是否可行，客户是否认可价值 | FDE 提前核验高不确定性环节，避免不可兑现的承诺 |
| 实施交付 | 怎样将约定方案稳定上线 | FDE 明确探索结论与边界，交付团队按约定完成部署与集成 |
| 行业专家／业务顾问 | 业务规则、约束和利益关系是什么 | 为 FDE 提供行业判断，参与样本标注与规则确认 |
| 客户成功／运营 | 如何提高采用率、维持长期效果 | 与 FDE 共同设计培训、反馈和移交后的支持机制 |
| 客户业务负责人 | 问题是否值得解决，结果是否可接受 | 决定优先级、业务规则和验收标准，协调一线人员 |
| 客户 IT／安全负责人 | 数据、权限、运行环境是否可接受 | 批准接入方式与权限，确认运行及停用条件 |

### 3.2 FDE 必须具备什么权限

承担闭环责任的同时，应明确以下工作权限：获取经过授权的样本；接触真实使用者；提出范围调整；要求关键假设得到验证；在放行条件未满足时建议延期上线；将共性问题提交产品团队并获得反馈。

这些权限不等于可以代替客户审批、绕过访问控制，或自行承诺商业结果。

### 3.3 小团队的最低责任覆盖

一个试点至少需要覆盖四类责任，可由多人或一人兼任，但每项都要有具体名字：

| 责任 | 主要承担者 | 关键确认事项 |
|---|---|---|
| 业务决策与验收 | 客户业务负责人 | 目标、范围、样本规则、验收结论 |
| 方案实现与问题协调 | FDE／技术负责人 | 方案、集成、测试、问题跟踪 |
| 环境、数据与权限 | 客户 IT／数据负责人 | 接入许可、数据口径、访问控制 |
| 日常使用与运行 | 客户运营负责人及支持团队 | 培训、接管、监控、故障联络 |

**建议的责任原则：**业务语义由客户确认，系统实现由实施方验证，使用结果由双方依据同一套记录共同复核。技术处置责任与最终合同责任不同，本文不替代合同约定。

### 3.4 能力要求与证明方式

| 能力 | 可观察的行为 | 可提交的证据 |
|---|---|---|
| 问题定义 | 能将抽象诉求缩小到一个流程、一类人和一个目标 | 问题定义卡、基线数据、范围取舍 |
| 工程实现 | 能连接接口、处理状态和异常、发布可运行版本 | 可演示系统、集成说明、失败处理记录 |
| 数据理解 | 能说明字段含义、来源、时效与缺失影响 | 数据字典、样本检查、权限映射 |
| 模型应用 | 知道哪些任务适合模型，哪些使用规则更可靠 | 方案对比、失败样例、成本与效果记录 |
| 效果评估 | 能定义完整成功、识别误差和不确定性 | 固定评估集、指标口径、分组结果 |
| 现场协作 | 能处理各方理解冲突并推动决定 | 访谈纪要、决策记录、范围变更记录 |
| 产品沉淀 | 能识别共性并证明复用收益 | 复用组件、后续项目对比、维护说明 |

AI 编程工具可以加快原型、接口适配和评估脚本的实现。FDE 仍需能审查生成结果、解释系统行为并定位失败；代码产出速度不能替代工程责任。基础设施型岗位还需补充相应的容量、推理性能和部署运维能力。

## 4. 项目筛选：哪些值得做

### 4.1 先检查必要条件

进入开发前，逐项填写“已具备／待补齐／不具备”，并标出补齐负责人和日期。

- 有明确的业务负责人，能决定优先级并协调相关人员。
- 能接触真实使用者，获取至少一部分有代表性的授权样本。
- 能说明当前流程怎样完成，以及最主要的成本或错误在哪里。
- 有可使用的数据来源和现实可行的接入路径。
- 有人能够判断输出是否正确，并愿意参与复核。
- 明确系统输出将由谁使用，失败后如何继续工作。
- 试点有资源上限、范围边界及继续／停止的决策日期。

缺少条件时，可以先做调研、数据准备或离线验证；不要在关键权限和验收人均未明确时承诺生产上线。

### 4.2 再比较候选场景

为每个场景写一页事实，而不是只凭印象打分：

| 维度 | 要收集的证据 | 需要警惕的情况 |
|---|---|---|
| 业务价值 | 任务量、耗时、错误代价、等待或返工 | 痛点描述很强烈，却无任务记录 |
| 流程边界 | 清楚的开始、结束、参与者和例外 | 一次要重构全公司流程 |
| 数据可用性 | 样本、数据字典、更新方式、访问权限 | 只有数据数量，没有内容和使用许可 |
| 判断可能性 | 业务专家能给出可复核的成功标准 | 专家之间对正确答案长期无共识 |
| 集成复杂度 | 系统清单、可用接口、测试环境 | 依赖多个未知接口且无法安排负责人 |
| 采用条件 | 实际用户、试用安排、原流程替换方式 | 只有高层支持，一线没有参与时间 |
| 复用潜力 | 同类客户、重复工作、已有产品能力 | 每个客户都需要独立维护完整分支 |

优先考虑：价值具体、边界较窄、反馈快、失败可接管的流程。若候选场景各有优势，先选择最能验证关键假设的一项，而非简单选择演示效果最好的任务。

### 4.3 常见进场结论

- **进入试点：**业务和技术条件足以验证一个小范围任务。
- **先补准备工作：**问题有价值，但缺数据、规则或权限；先安排独立的准备阶段。
- **采用普通自动化：**固定规则或现有产品已能满足需求。
- **暂缓：**缺少明确责任人，或投入与预期明显不匹配。

记录作出判断的依据，避免“暂缓”被理解成无限期等待。

### 4.4 先做自建、采购与部署方式比较

在自建前，用少量代表性任务试用企业已经采购的 AI 功能或成熟垂直产品。比较能否完成完整任务、接入现有系统、满足权限与运行要求，以及定制和退出的成本。已有产品能满足需求时，FDE 的价值可以体现在配置、集成、评估和采用上。

| 选择 | 需要验证的关键问题 |
|---|---|
| 已有产品／采购服务 | 数据导出、接口、权限、可观测性、收费及版本变更是否可接受 |
| 自建应用＋托管模型／运行环境 | 网络可达、服务区域、配额、数据处理约定、故障支持是否符合项目条件 |
| 自有环境部署模型与运行组件 | 硬件、性能、升级、运维和值班成本是否有人承担，实际效果是否满足要求 |
| 混合方式 | 数据经过哪些系统和区域，身份与故障如何跨系统追踪，维护责任是否清楚 |

部署范围要拆开说明：数据存储位置、检索服务、模型推理、工具执行、日志和会话存储可能分别位于不同环境。“应用私有化”并不自动意味着推理与日志也留在本地。敏感数据也不必然要求所有组件自建，应由企业依据自身要求确认允许的方案。

这些是工程与采购核查项，具体要求需查对应产品在采购时的实际条款；不根据某个部署标签推断合规结论。没有明确需求时，不预先建设多模型网关或备用供应商体系；有连续性要求时，再为替代路径单独验证效果与切换成本。

## 5. 项目全流程：八个阶段与放行条件

本流程以产物和证据推进，不要求所有项目使用相同工期。每个阶段都记录负责人、待解决问题和下一次决策日期。阶段用于组织检查点，可短周期往返：调研时就能做离线原型，试用发现问题后也应返回问题定义或工程阶段。小项目可以合并文档，但保留影响决策的证据；不把八个阶段变成八轮串行审批。

### 阶段 0：确认合作条件

**动作：**确认业务负责人、真实用户、数据及系统联系人；选择一个候选流程；约定调研范围和资源上限。

**产物：**项目章程、联系人表、样本获取计划。

**放行条件：**有授权的数据获取路径、有验收人，双方同意首先验证的问题。

### 阶段 1：还原真实工作

**动作：**观察真实任务从开始到结束；记录正常流程与例外；对照管理者描述、一线操作和系统记录；采集基线。

访谈时优先问：请带我看最近一次完整任务；哪一步最容易返工；哪种输入必须转给资深同事；如果这一步做错，谁先发现；哪些数据看得到却不能使用。

**产物：**当前流程图或步骤表、问题清单、初始样本、基线测量说明。

**放行条件：**业务负责人和一线使用者都确认流程没有遗漏关键步骤；主要分歧已记录。

### 阶段 2：定义问题与验收

**动作：**选择一项主目标；约定质量与操作边界；说明哪些任务暂不覆盖；确定比较方式与样本来源。

**产物：**问题定义卡、范围表、指标字典、初始评估集。

**放行条件：**能够回答“什么情况算成功、什么错误不能接受、失败后谁处理”。此时确定验收方法，避免开发结束后才寻找有利指标。

### 阶段 3：验证最危险的假设

**动作：**先验证最可能让项目失败的部分，例如能否正确检索、接口是否允许写入、业务专家能否判断输出。用最少实现完成真实链路的一小段。

**产物：**可操作原型、假设验证记录、用户否定意见、已知限制。

**放行条件：**关键假设获得支持；使用者亲自试用后，确认继续开发仍有价值。原型可行不等于生产可用。

### 阶段 4：完成工程与评估

**动作：**接入真实测试环境；实现权限、输入校验、异常处理、日志和版本管理；使用独立留出的样本评估；与现有流程比较。

**产物：**候选版本、评估报告、问题分级清单、运行说明。

**放行条件：**约定质量条件通过；关键问题已修复或有明确处理；环境和权限负责人完成相应确认。

### 阶段 5：受控试用

**动作：**限定用户与任务范围；按操作影响设置人工确认或抽样复核；记录实际采用和修改；安排固定复盘；按预先规则决定是否扩大范围。低影响、可逆且已验证的操作可在授权范围内自动执行，参照第 6.9 节。

**产物：**试用日志、效果对比、用户反馈、事故与接管记录。

**放行条件：**在真实任务上满足约定目标，新增工作量和失败代价可接受；结果不只依赖 FDE 在旁代操作。

### 阶段 6：交接运营

**动作：**由接手人员独立完成常规操作、规则更新、故障联络及停用演练；确认知识更新人、系统维护人和支持窗口。

**产物：**交接包、培训记录、运行负责人确认、未完成事项清单。

**放行条件：**接手团队能按手册操作，待解决问题有负责人与日期。交接后仍需约定效果复核时间。

### 阶段 7：复盘与产品沉淀

**动作：**比较目标与结果；归因差距；区分客户配置、行业共性和产品缺陷；选取值得投入的复用项。

**产物：**项目复盘、产品改进建议、可复用评估样例与组件说明。

**放行条件：**客户数据处理和成果使用边界明确；沉淀资产有维护者和验证计划。

### 一个四周试点的参考节奏

| 时间 | 核心工作 | 周末决策 |
|---|---|---|
| 第 1 周 | 观察流程、准备样本、明确基线和验收 | 是否有足够证据进入实现 |
| 第 2 周 | 做最短原型、验证关键接口和质量 | 哪些假设成立，是否缩小或调整范围 |
| 第 3 周 | 补工程能力、独立评估、修复关键问题 | 是否符合受控试用条件 |
| 第 4 周 | 小范围真实使用、复核结果、准备交接 | 扩大、继续验证、调整或停止 |

这只是资源安排示例。涉及复杂集成或高影响操作时，阶段可能明显更长；不要用固定日历替代放行条件。

## 6. 技术落地：先把最短链路跑通

### 6.1 技术选择：先比较候选方案，不设固定升级阶梯

先明确任务、可用数据和操作边界，再选最简单且达到要求的实现。无需把脚本、模型、RAG、Agent、微调逐个做一遍。

| 任务特征 | 优先比较的方案 | 决定依据 |
|---|---|---|
| 规则稳定、输入结构清楚 | 现有功能、SQL、脚本或普通工作流 | 规则覆盖、维护与集成成本 |
| 文本理解或生成，步骤较固定 | 模型直接调用或固定模型工作流 | 留出样本质量、结构校验、端到端耗时 |
| 依赖企业事实 | 数据库／业务 API、全文或语义检索、适当的长上下文输入 | 数据类型、实时性、权限、证据充分性 |
| 路径需根据反馈动态调整 | 单 Agent＋必要工具＋明确停止条件 | 是否比固定路径改善完整任务结果 |
| 可拆成相互独立且确有价值的任务 | 并行任务或多个 Agent | 增益能否覆盖协调、运行与调试成本 |
| 稳定且重复的特殊任务仍无法达标 | 微调等进一步优化 | 授权数据、误差归因、训练及维护代价 |

用企业允许使用的、能力合适的强模型尽早做一个最小基线，估计任务能做到什么程度；再比较较小模型、规则和其他方案的质量、速度与总成本。复杂提示词、多层路由和手写补丁都应有具体失败证据支持，并在模型更新后重新检查必要性。

工作流通常由预定路径组织模型和工具；Agent 则让模型根据反馈决定下一步。二者可组合，并非新旧替代关系。[技术依据 T1](https://www.anthropic.com/engineering/building-effective-agents)

对扫描件、图表、音频等输入，比较原生多模态处理与 OCR／转写后处理的效果；对缺少接口的旧系统，可评估界面自动化，但需计入页面变化、登录状态和恢复成本。优先使用已能满足任务的稳定接口，不能把“看见成功页面”当作后台业务已经完成。

### 6.2 最小生产链路需要考虑什么

```text
用户／业务系统
  → 身份确认与输入校验
  → 读取获授权的数据或知识
  → 规则／模型生成建议
  → 业务规则与输出结构校验
  → 必要时人工确认
  → 受控工具执行
  → 核对结果并返回

全程关联：请求记录、版本、耗时、成本、错误与用户反馈
```

只读问答可以没有执行步骤，但仍需正确的权限过滤、来源和失败处理。日志只保留实现排查所需的信息，敏感字段按项目约定脱敏并限制访问。

### 6.3 把业务上下文变成可维护资产

| 资产 | 至少包含什么 | 负责确认的人 |
|---|---|---|
| 业务对象表 | 对象、字段、含义、唯一标识、关系 | 业务与数据负责人 |
| 规则表 | 适用条件、例外、生效时间、冲突处理 | 业务规则负责人 |
| 知识清单 | 来源、版本、有效期、可见范围、更新方式 | 知识维护人 |
| 工具说明 | 输入、输出、副作用、调用权限、错误码 | 系统接口负责人 |
| 权限映射 | 用户／角色可读取和执行的范围 | IT／权限负责人 |
| 评估集 | 输入、可接受结果、评分方法、分组、版本 | 业务专家与评估负责人 |

Ontology 可理解为对业务对象、关系、规则和动作的结构化描述。它在 Palantir 语境中也涉及具体的平台实现；本文不把“建一张表”与完整平台能力等同。小项目可从上述必要资产开始，待重复需求出现后再扩大建模。

### 6.4 写入操作要单独设计

对于退款、改价、改库存、发送通知等有实际副作用的操作，至少明确：谁有权发起；参数由哪里产生；执行前校验什么；是否需要确认；超时后如何查询状态；怎样防止重复执行；失败后怎样补偿。

“撤回软件版本”不会自动撤销已经发生的业务动作。不能逆转的动作，应预先约定停止、通知和补救流程。

### 6.5 一条通用的检索排查链

资料是否存在 → 当前用户是否有权访问 → 数据是否已更新 → 是否检索到正确段落 → 段落是否足以回答 → 模型是否忠实使用 → 输出是否符合规则。

不要在尚未区分这些原因时反复修改提示词。

### 6.6 上下文与记忆：按任务提供信息，保存可核验状态

上下文管理涉及指令、资料、工具返回和历史记录的选择；上下文窗口更大，并不保证所有资料放进去就更可靠。可比较预先检索与按需读取的组合。[技术依据 T2](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

本文建议分开管理三类信息：

- **业务事实：**订单状态、库存等从权威业务系统查询，不用聊天记忆代替实时记录。
- **任务状态：**已完成动作、待处理事项、审批状态和业务编号，保存为明确字段及事件记录。
- **长期偏好与经验：**只有得到允许、确认适用范围后才持久保存，并规定更新、失效和删除方式。

跨会话记忆应关联用户、企业或项目，防止混入其他客户内容。总结和记忆中的信息保留来源与时间；压缩历史时优先保留未解决事项、约束和操作凭据。记忆写入本身也需要验证，不能让不可信文档中的指令成为长期规则。

### 6.7 MCP、工具与 Skills：分别解决什么

| 层次 | 主要作用 | 不能替代什么 |
|---|---|---|
| API／MCP 工具接入 | 让应用或 Agent 使用外部能力和数据 | 不自动赋予业务权限，不保证返回内容可信 |
| Skill／流程资源包 | 按需加载任务说明、参考资料和脚本 | 不保证执行正确，不代替审批、评估和运行环境 |
| 任务运行环境 | 管理调用、状态、执行资源和恢复 | 不代替业务规则与客户的最终决策权 |

Agent Skills 的公开规范允许把说明和可选脚本、资料、资产打包，按需加载；不同运行产品的支持程度仍需验证。[技术依据 T6](https://agentskills.io/specification)

已有几个稳定 API 时，直接调用可能更简单；需要多种客户端或接入生态时，再评估 MCP。每个工具写清输入、返回结构、数据时效、失败状态和副作用。Skill 与工具都应有维护者、版本、适用环境和回归样例；把操作写进 Markdown 不等于完成产品化。

### 6.8 长任务运行：超出一次对话后怎样继续

当任务跨分钟、跨系统或需要等待审批时，应记录任务 ID、当前状态、已确认动作和待办，允许暂停、取消与恢复。会话事件的持久保存和模型当前看到的上下文可以分开；这是运行设计选择，不要求拆成多套服务。[技术依据 T4](https://www.anthropic.com/engineering/managed-agents)

按任务需要配置：

1. **预算与停止：**最长时长、调用次数或费用上限，连续失败后如何停止。
2. **操作状态：**区分准备执行、执行中、成功、失败和结果未知。超时通常需要查询实际状态，不宜直接视为失败并重试。
3. **恢复依据：**从保存的事件和业务系统状态恢复，避免重复发送、重复下单等副作用。
4. **可观测性：**关联请求、工具参数、结果、版本、耗时和错误；无需依赖或索取模型的私有思维过程。
5. **隔离：**执行生成代码或脚本时，限制文件、网络和可获得凭证；避免把高权限密钥放进模型文本或可随意读取的执行环境。

单次分类任务通常不需要完整任务队列；采用现有应用设施即可。采购托管运行环境时，也需验证这些行为及数据导出方式。

### 6.9 按操作影响设置自主范围

以下是项目讨论用分类，不是行业强制分级；应按具体动作而非整个 Agent 一次性定级。

| 操作性质 | 可考虑的执行方式 | 最少需要确认的条件 |
|---|---|---|
| 只读查询、内部草稿 | 在授权范围内直接完成，按需抽查 | 身份、数据可见范围、结果来源 |
| 低影响且可逆的内部更新 | 规则校验后自动执行，监测并抽样复核 | 操作限额、幂等、撤销和异常接管 |
| 对外发送、财务或权限相关动作 | 按企业规则设置预先授权或具体确认 | 对象、内容、额度、批准人及结果记录 |
| 后果难逆转或缺少验证手段的动作 | 限制为建议，或先重设计流程 | 具备足够依据与处置能力后再讨论放行 |

人工审核也有成本和注意力限制。确认界面应展示对象、关键参数、依据及具体后果；系统仍在工具或业务服务层执行权限检查，不能只靠“请不要越权”的提示词。按影响设置边界比对每一次模型调用弹出确认更有意义。[技术依据 T7](https://www.anthropic.com/engineering/how-we-contain-claude)

不要仅凭模型自报的“置信度”放行操作；优先依据必需字段、来源有效性、业务规则、历史评估及操作范围作判断。

### 6.10 把不可信内容与执行权限分开

企业邮件、网页、附件和工具返回中可能包含诱导系统改变任务的文本。把这些内容当作待处理数据，不允许其自行修改权限、审批或目标。提示词与输出过滤可作为辅助；关键限制仍应由身份、工具、执行环境和业务校验落实。

项目至少验证：文档要求外传资料时不会照做；跨用户或跨客户的数据不能被读取；接口只能执行授权动作；凭证不会写入模型上下文与普通日志。具体测试按实际接入面选择，不要求所有项目完成相同规模的专项评审。

采用 MCP 时，核对所实现的协议版本与授权要求，按用户及服务范围限制权限；不能将未经目标校验的客户端令牌直接透传到下游服务。[技术依据 T5](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)

## 7. 评估、验收与价值测算

### 7.1 同时验证四个层面

| 层面 | 要回答的问题 | 建议记录 |
|---|---|---|
| 业务 | 实际减少了什么成本或增加了什么价值 | 端到端耗时、返工、完成量、实际收益 |
| 质量 | 是否按约定正确完成完整任务 | 成功数／总数、错误类型、分组表现 |
| 工程 | 能否持续稳定地运行 | 接口失败、超时、延迟、成本、接管结果 |
| 采用 | 真实使用者是否持续使用 | 合格任务覆盖、实际使用、采纳、修改负担 |

业务目标不宜过多。试点可先选择一个主目标，并配上必要的质量和操作约束。

### 7.2 指标必须写清分子与分母

- **任务成功率：**达到全部必需条件的任务数 ÷ 被评估任务总数。先列出“全部必需条件”，避免把只完成一半的任务算成功。
- **建议采纳率：**按约定规则被采纳的建议数 ÷ 实际展示的建议数。原样采纳与修改后采纳建议分别记录。
- **人工接管率：**进入人工处理路径的任务数 ÷ 被系统接收的任务数。接管可能是正常设计，不能简单视作越低越好。
- **单个成功任务成本：**期间系统运行与相关人工成本 ÷ 成功任务数。共享固定成本的分摊方式需说明。
- **有效使用覆盖率：**实际由系统参与处理的合格任务数 ÷ 同期合格任务总数。预先固定“合格任务”的定义；自动触发任务也要计入，不能只统计打开聊天窗口的人数。

记录被排除、未完成和失去跟踪的任务及原因，避免分母随结果改变。提示词、模型、知识和规则版本应随评估结果一并保存。

### 7.3 评估集如何建立

从真实授权样本出发，覆盖正常任务、高频异常、信息缺失、规则冲突、过期知识和越权访问等情形。按业务重要性分组，保留困难样例；用于日常调优的样本与最终留出评估样本分开。

对需要专家判断的答案，先请两位评审独立标注一部分样本，讨论分歧，再完善评分规则。专家尚无共识的任务，不宜直接归因于模型失败。

模型评分可以协助筛查，但高影响结果应保留独立人工复核。评估集中的敏感数据遵守与生产数据一致的授权边界。

### 7.4 不把小样本结果解释得过满

报告实际样本量、失败数与分组表现，不只给一个百分比。某次测试没有发现严重错误，只说明该批样本未观察到此类错误，不等于生产风险为零。

探索性试点可先用较小样本发现方向性问题，扩围前应补充有代表性的样本和真实使用观察。样本量取决于错误代价、允许误差与场景分布，没有适用于全部项目的固定数量。

### 7.5 比较方式应减少偏差

条件允许时，将同一时期、相近难度的合格任务分配到原流程和新流程；不便分组时，至少匹配任务类型、人员熟练度和繁忙程度。记录培训、人员变化、业务量变化等可能影响结果的因素。

端到端耗时要包括阅读、核验、修改、提交、接管及返工。演示中模型生成只需十秒，并不代表整项任务只需十秒。

### 7.6 价值测算的基础口径

```text
每月节省工时
= 同期合格任务量 × 实际使用比例 × 每个使用任务平均净节省分钟 ÷ 60

工时价值估计
= 节省工时 × 约定的综合小时成本

月度净价值估计
= 可确认收益 − 运行与维护增量成本 − 新增复核及返工成本
```

若净节省分钟已包含复核与返工，不要再次扣除相同成本。一次性建设费用可单独列示；若分摊到月份，应明确周期，不再重复计算。

工时价值通常代表释放产能，只有在实际减少支出、减少加班或形成额外有效产出时，才可进一步认定为相应的现金或经营收益。收入提升需要单独验证，不能直接等同于系统使用量。

### 7.7 验收的四种可能结论

1. **通过并按约定扩围：**业务、质量和运行条件均达到预设要求。
2. **限定范围通过：**只开放验证充分的任务和用户群。
3. **继续验证：**结果有潜力，但样本、稳定性或使用周期不足。
4. **停止或重新定义：**收益不足，或关键前提已被否定。

验收表应同时记录限制、待办事项及下一次复核日期。

### 7.8 Agent 评估：最终结果、执行边界和重复稳定性

Agent 的答案、实际动作和后台最终状态可能不同。评估应允许不同的有效解法，同时检查必要权限与操作约束。重复试验可揭示单次通过无法显示的不稳定性。[技术依据 T3](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

建议把评估拆成三个问题：

| 问题 | 证据 | 典型误判 |
|---|---|---|
| 任务真的完成了吗 | 订单、工单、数据库或文件等最终状态 | Agent 声称已更新，实际只生成了建议 |
| 完成方式符合约定吗 | 工具事件、授权、参数、审批及副作用记录 | 最终答案正确，却读取了无权访问的数据 |
| 同类任务是否稳定完成 | 多次独立运行及按任务组统计的结果 | 只保留多次尝试中的最好一次 |

不要求所有任务遵循唯一工具调用顺序，除非该顺序本身是审批、业务或安全约束。调试时分析轨迹，是为了定位错误而非奖励固定走法。

对代表性任务，在重置环境的条件下重复运行，报告首试成功、重试后成功、失败、超时与未知状态；附重试预算和成本。“多次尝试至少一次成功”和“多次均成功”含义不同，不能互相替代。不重置缓存、记忆或数据会影响比较，应说明哪些状态刻意保留。

评估还应包含应该执行与不应执行的成对情形，以及长任务暂停恢复、数据变化、依赖不可用等实际失败模式。上线后持续抽样，发现新失败后先形成可重现样例，再补入回归集；保留用于下一轮独立检验的新样本。

### 7.9 按系统用途衡量效果，并补齐总投入

**辅助型系统**重点看采纳、修改负担和端到端效率；**执行型系统**重点看合格任务中的有效自动完成比例、错误动作、接管、恢复与业务结果。聊天活跃度和人工审核次数不宜成为通用的成功目标。

补充两个可选指标：

- **有效自动完成率：**在约定权限、质量和时限内无需人工处理而完成的任务数 ÷ 预先定义的合格任务总数。按场景解释“无需人工”，不把事后人工修正隐藏掉。
- **复核负担：**每个完成任务的平均人工复核与接管时间，包含异常处理。若自动化后人工队列变长，也应记录等待和业务延误。

客户决策还应纳入数据准备、系统集成、许可、模型与运行资源、评估、培训、维护和替换迁移等实际成本。共用成本按约定分摊，不把同一投入重复计入。对“减少错误”的收益，同时记录错误基线、实际减少量和业务确认的损失口径。

扩围时重新测量并发量、尾部延迟、配额、人工接管承载能力与单位成本。小范围试点的表现不能直接按人数线性放大；只对已经出现或明确约定的规模要求做验证，避免提前建设复杂容量体系。

## 8. 完整示例：企业售后工单助手

**本节是虚构教学案例。所有数据、门槛、进度与结果仅用于演算，不是原文案例、实测结果或行业基准。**

### 8.1 从诉求到可验证问题

初始诉求：“我们想用 AI 自动处理售后。”

调研后将范围缩小为：客服在人工最终确认的前提下，为一类标准产品的常见售后问题完成分类、检索政策和拟写回复。退款批准、赔偿承诺和库存修改均不在试点内。

目标用户是一个售后小组；业务负责人为售后主管；知识负责人负责政策更新；IT 负责人提供测试工单接口与读取权限。

### 8.2 当前流程和样本

当前流程：阅读工单 → 查产品与订单 → 查政策 → 分类 → 拟写回复 → 核验并发送。

假设通过计时记录，确认这类任务平均人工活跃处理时间为每单 8 分钟，月合格任务量为 3,000 单。将等待客户补充信息的时间与人工活跃处理时间分开记录。

准备样本时覆盖：标准问题、产品信息缺失、政策过期、客户表述模糊、多问题混合、无法访问订单等情况。另留一部分未参与调优的任务用于评估。

### 8.3 最小实现

读取工单和获授权的订单字段 → 使用当前有效政策检索 → 输出分类、回复草稿、依据和缺失信息 → 客服核验与修改 → 通过原工单系统发送。

规则校验负责限制赔偿承诺、检查必要字段及来源有效性；信息不足时生成补充提问或转人工。试点阶段由客服发送最终回复，系统不直接联系客户。

### 8.4 示例验收规则

以下门槛仅用于展示如何写规则，正式项目须由业务负责人确认：

| 检查项 | 示例规则 | 如何验证 |
|---|---|---|
| 完整任务质量 | 留出集至少 90% 的任务满足全部必需条件 | 专家按固定规则逐项评分，报告实际分子分母 |
| 人工处理时间 | 实际使用任务平均不超过 5 分钟 | 记录包含核验与修改的活跃时间，并按难度分组 |
| 政策依据 | 涉及政策的结论可追溯到有效来源 | 人工抽查引用是否支持结论 |
| 操作范围 | 未授权角色不能访问订单；没有自动退款路径 | 权限与操作测试 |
| 失败接管 | 检索缺失、接口超时可回到人工流程 | 故障注入与使用者演练 |
| 实际采用 | 合格任务中持续使用比例达到约定目标 | 从任务系统核对覆盖率，记录不用的原因 |

任何“严重错误零容忍”规则，都要具体说明错误类别及发生后的停用或限制措施；不能把评估中零次发生解释为长期不会发生。

此处 90% 仅是有人核验的草稿助手教学门槛，并不证明可自动对外回复；还需与原流程质量比较，单独检查高影响错误。时长结果应同时展示样本分布及慢任务，避免平均值掩盖少量严重返工。

### 8.5 示例收益演算

假设试点确认：合格任务中 70% 使用助手；使用任务平均每单净节省 3 分钟，已包括人工核验与修改；综合人工小时成本按 80 元估计。

```text
每月使用任务 = 3,000 × 70% = 2,100 单
每月节省工时 = 2,100 × 3 ÷ 60 = 105 小时
工时价值估计 = 105 × 80 = 8,400 元／月

假设每月运行与维护增量成本 = 2,000 元
扣除增量成本后的产能价值估计 = 6,400 元／月
```

若一次性建设投入为 30,000 元，在任务量、采用率、净节省时间与成本均保持不变，且释放产能确实可兑现价值的假设下，简单价值回收周期约为 30,000 ÷ 6,400 = **4.7 个月**。这不是现金回款预测，也未计入资金时间价值。

敏感性检查：若采用率降至 40%，则月节省 60 小时，工时价值 4,800 元；扣除 2,000 元增量成本后为 2,800 元，简单价值回收周期约 **10.7 个月**。因此，培训、工作流入口和使用者信任可能比进一步缩短模型生成时间更值得优先投入。

### 8.6 复盘时该问什么

- 不使用系统的工单，是否本来就不适合自动化，还是用户缺乏信任？
- 时间节省是否集中在资深客服，是否让新人负担更重？
- 错误来自政策质量、检索、模型理解还是流程设计？
- 政策变更后，谁更新知识、谁重新评估？
- 下一家客户能复用的是接口工具、评估方法还是业务规则？哪些必须重新确认？

### 8.7 如需发展为执行型 Agent，应怎样扩围

保留当前助手作为比较基线，先选一类低影响、可逆的内部动作，例如给工单补充经验证的分类标签。实现身份校验、允许标签集合、版本或并发冲突检查，以及重复请求处理；先在测试环境验证，再限定任务范围试用。

扩围依据包括：后台标签确已写入且没有覆盖人工更新；重复请求不重复产生动作；超时可查询状态；错误可撤销；有效自动完成率和接管负担符合约定。人工标签的原始依据也要可复核，不能只把人机一致当作正确。

自动发送客户回复属于另一种操作影响，需要单独验证和授权；不能沿用内部打标签的放行结论。退款与赔偿仍在本案例范围之外。新阶段重新计算任务量、人工工作和运行成本，不直接继承第 8.5 节的收益。

## 9. 团队运行与产品反馈

### 9.1 让例会服务于决策

| 节奏 | 讨论对象 | 需要产生的结果 |
|---|---|---|
| 试点期间短会 | 当天阻塞、异常和用户反馈 | 明确下一步动作与负责人 |
| 每周业务复盘 | 任务量、质量、耗时、采用情况 | 决定范围、培训或流程调整 |
| 每周产品反馈 | 重复失败、组件不足、可复用需求 | 接受、拒绝或继续观察，并说明理由 |
| 阶段评审 | 放行条件、投入、未解决事项 | 继续、扩围、限定或停止 |

频率按项目规模调整。会议结束应形成具体决定，避免用汇报替代现场观察。

### 9.2 三类成果分开管理

1. **客户专属资产：**数据映射、权限配置、内部规则及特定流程。明确客户使用与维护方式。
2. **行业可复用资产：**在授权允许的范围内抽象出的模板、工具与评估方法。保留适用边界。
3. **核心产品改进：**需要进入统一产品的功能或缺陷修复，由产品团队确认维护责任。

复用时不得直接搬运客户数据、专有知识或未经授权的样例。匿名化并不自动意味着具备复用权，需要结合实际授权确认。

### 9.3 一份合格的产品反馈

包括：出现在哪类客户；真实任务是什么；当前行为与期望行为；可复现输入；版本与日志；发生频次和影响；已尝试办法；为什么应进入产品；实现后怎样验证收益。

“客户觉得不好用”无法直接排期；“三类任务都因同一接口限制多出一次人工操作，已有复现材料”才足以支持讨论。

### 9.4 衡量复用收益

追踪后续同类项目的首次可用时间、专属开发工作量、缺陷和维护成本、客户自主更新比例。比较时说明集成难度和范围差异。

复用率高并不必然更好：一个需要大量配置、维护和解释的通用组件，可能比两段简单实现更昂贵。只沉淀重复出现且边界较稳定的能力。

### 9.5 从项目交接到持续运营

企业采用指南强调根据用途和影响安排治理、所有权及运行方式；不要求所有助手与自主执行系统使用同样的管理强度。[企业应用依据 T8](https://learn.microsoft.com/en-us/agents/adopt-overview)

小团队可先用一张系统登记表，记录：业务负责人、技术维护者、运营联系人、使用范围、数据与工具权限、模型及配置版本、费用归属、更新方式和停用入口。已有应用管理或运维系统可以直接承载这些信息，无需为少量试点单独建立大型治理组织。

明确以下三类变化的验证责任：

- **模型或提示词变化：**在固定任务上对比新旧效果、操作行为和成本；通过后小范围发布。允许固定版本时记录版本，不能固定时建立变更观察和异常处置方式。
- **知识、规则或工具变化：**确认生效时间，复核受影响样例及权限，确保旧规则不继续被使用。
- **业务和用户变化：**新增客户群、任务或自动执行范围时，重新确认基线、授权和验收条件。

移交可以是客户自行运营、供应方持续服务或双方分工。目标是责任、访问和能力可移交，未必要求客户自行维护所有技术组件。停用时要处理在途任务、撤销不再需要的凭证、导出约定数据，并按约定处理会话、知识副本和记忆。

### 9.6 同时核算供应方是否能持续交付

客户获得价值与服务商能否持续经营是两个问题。对每个项目记录实际回款或收入、交付人工、差旅、资源费用、采购、持续支持及返工；产品研发等共用成本另行说明分摊，不把合同金额当作已收款。

```text
项目贡献估计 = 项目确认收入 − 可归属的交付和运行支持成本
```

确认收入与现金回款另表追踪。该公式用于项目管理，不替代财务核算。结果付费还要约定结果的定义、归因、排除条件和核对方法；按工时、订阅或混合收费也可能合理，不能用计费名称判断是否具备 FDE 能力。

在可比项目中追踪支持工时、交付周期和贡献变化。如果客户越多，维护分支与返工同步增加，应收窄客户分群、改善产品或调整服务范围；不要只依靠增加 FDE 人数维持增长。

## 10. 常见失败及排查顺序

| 现象 | 优先检查 | 建议动作 |
|---|---|---|
| 演示很好，实际使用很差 | 样本是否只覆盖理想输入 | 收集真实失败，按任务类型分组评估 |
| 回答流畅但经常不可信 | 来源、检索、时效和规则冲突 | 沿第 6.5 节逐层定位，加入依据与拒答路径 |
| 质量不错，却没人使用 | 入口是否增加步骤，核验是否太重 | 观察完整操作，减少切换，核对使用成本 |
| 一直做原型，无法上线 | 权限、环境和责任是否从未确定 | 明确具体阻塞；无法补齐则限定为离线成果 |
| 需求持续扩大 | 范围与验收是否允许无限追加 | 将新增事项写入变更表，说明成本和工期影响 |
| 项目依赖某位 FDE | 配置、排查与决策是否只存在其记忆中 | 让接手者按手册独立操作，暴露交接缺口 |
| 一个客户一个代码分支 | 差异是否应配置化，共性是否真实存在 | 先梳理差异来源，避免直接建复杂框架 |
| 单次调用便宜，总成本仍高 | 重试、长上下文、失败与人工核验 | 按成功任务核算端到端成本 |
| 模型更新后效果下降 | 版本和评估集是否可追溯 | 暂停变更，比较新旧版本，按结果决定恢复 |
| 显示成功但业务没更新 | 是否只检查文字回复或页面提示 | 核对后台业务状态、执行编号和实际权限 |
| 重试造成重复动作 | 超时是否被直接视作失败 | 查询状态，按业务请求标识避免重复执行 |
| 审核越来越多且没人认真看 | 确认是否过密，信息是否足以判断 | 按操作影响设置边界，突出需判断的具体后果 |
| 记住了错误规则或其他客户信息 | 记忆来源、隔离与更新方式 | 停用受影响记忆，修正来源并重新评估 |
| 频繁争论谁负责 | 决策、业务规则和接口变更是否留痕 | 按具体故障定位处置人，再依据约定处理责任 |

故障处理先恢复可工作的流程，再保留证据进行归因。对用户可见的异常，需要说明处理状态和替代操作，不让使用者反复尝试未知状态的写入请求。

## 11. 八周能力建设计划

这是一份面向已有基本开发能力者的参考计划。时间安排是练习节奏，不保证八周后能够独立承担所有 FDE 项目。完全没有编程基础者，应先补足基本工程能力。

| 周次 | 学习与实践 | 必须留下的产物 | 自检问题 |
|---|---|---|---|
| 1 | 选一个能接触真实用户的窄流程，观察完整任务 | 流程表、访谈记录、问题清单 | 我是否知道用户实际怎样工作？ |
| 2 | 采集基线、明确范围和判断标准 | 问题定义卡、指标字典、初始样本 | 什么证据会让我停止这个项目？ |
| 3 | 用现有工具完成一条端到端最短链路 | 可运行原型、方案取舍记录 | 用户能否亲自试，而非只看演示？ |
| 4 | 处理数据、权限、异常和接口约束 | 数据字典、权限表、故障处理记录 | 输入不完整或接口超时后会怎样？ |
| 5 | 建立留出评估、分析失败与成本 | 评估报告、错误分类、版本记录 | 我是在修真实问题还是调好展示样例？ |
| 6 | 小范围试用，记录采用和修改负担 | 使用日志、反馈、比较结果 | 全流程是否节省时间？ |
| 7 | 交接给另一人，演练维护和接管 | 运行手册、交接缺口和修复记录 | 我离开后，别人能否继续工作？ |
| 8 | 复盘、识别复用项、整理作品集 | 项目复盘、演示、可分享材料 | 证据支持哪些结论，又不能支持哪些？ |

如果练习对象是执行型 Agent：第 3 周加入单 Agent 与固定工作流对比；第 4 周练习状态记录、幂等和暂停恢复；第 5 周增加独立重复运行与最终状态验证；第 7 周演练模型变更、凭证撤销和任务停用。多模态或界面操作项目，另外准备相应输入样本与后台核验方法。

### 作品集建议结构

背景与用户 → 当前流程及基线 → 目标与范围 → 方案选择 → 真实失败及修正 → 评估与实际采用 → 业务结果及限制 → 交接与复用。

使用经授权的脱敏或合成材料。面试中应能解释一次放弃的技术选择、一个失败样例，以及效果数据的分母；这些通常比展示框架清单更能证明判断力。

## 13. 术语速查

| 术语 | 本文中的含义 | 使用提醒 |
|---|---|---|
| FDE | Forward Deployed Engineer，贴近客户问题开展工程工作的角色 | 各公司职责不同 |
| FDSE | Forward Deployed Software Engineer | 常见于 Palantir 等公司的岗位语境 |
| Echo／Delta | 材料中用于描述业务理解与工程建设的角色分工 | 不是所有公司的通用组织名称 |
| Ontology | 业务对象、属性、关系、规则与动作的结构化模型 | 平台语境下含义更具体 |
| RAG | 根据外部资料检索内容，再辅助模型生成 | 引用存在不代表结论正确 |
| Agent | 可在约定范围内选择或调用工具执行任务的系统 | 自主程度与操作权限需单独规定 |
| Context | 完成任务所需的知识、状态、规则与上下文 | 需要维护时效与访问边界 |
| POC | 对关键可行性假设的验证 | 不等同于生产交付 |
| MVP | 足以让目标用户验证核心价值的最小可用范围 | 最小范围仍需必要的异常与接管设计 |
| 留出集 | 未用于日常调优、保留作独立评估的样本 | 反复据其修改会削弱独立性 |
| 影子运行 | 生成结果供比较，不直接影响实际业务决策 | 仍需合法授权和数据保护 |
| 幂等 | 相同业务请求重复提交时，避免重复产生副作用 | 需结合具体接口实现 |
| 回滚／补偿 | 恢复软件版本，或处理已发生业务动作的影响 | 两者不能互相替代 |
| MCP | Model Context Protocol，用于连接模型应用与外部能力的协议 | 协议接入不等于业务授权 |
| Skill | 可按需加载的任务说明及可选资源包 | 不等于独立服务或正确性保证 |
| Harness | 管理 Agent 调用循环与执行环境交互的运行逻辑 | 范围依实现不同，不要求自研框架 |
| 执行轨迹 | 请求、工具调用、结果、状态与错误等可观察记录 | 不等于模型的私有思维过程 |
| 总拥有成本 | 建设、采购、运行、维护与退出等全周期成本 | 需说明范围与分摊，避免重复计入 |

### 本手册没有验证什么

- 没有核验每家受访公司的全部内部流程、项目效果和经营数据。
- 没有取得牛透社完整白皮书及 CIO 调研底稿，不能外推市场总体比例。
- 没有以原文中的融资、薪酬或就业增长数字证明 FDE 的投资或职业回报。
- 没有将访谈中的组织形式、人员配置和时间安排认定为统一最佳实践。
- 没有将本文教学案例视为真实项目效果，也未宣称小样本通过等于生产无风险。

### 后续用于真实项目时怎样更新

为手册建立本地版本记录。每完成一个项目，补充一次：验证了哪些假设；修改了哪些模板；发现哪些原有判断不适用；效果证据保存在何处。将项目事实与通用方法分开，保留失败和不适用条件，才能让资料随实践持续变得可靠。
