## 前言

面对层出不穷的 AI 新概念，我们首先要拒绝 FOMO（Fear of Missing Out，错失恐惧）：不必因为一个新术语出现，就急于追捧或重新包装已有实践。

Harness 并不是 AI 领域凭空创造的概念。在传统软件工程中，`test harness` 通常指用于运行测试、提供输入、收集输出和验证结果的一组支撑工具。进入智能体时代后，Harness Engineering 将类似思路扩展到模型运行环境：通过上下文、工具、规则、反馈和安全边界，帮助智能体更可靠地完成任务。

本文尝试从概念、架构和生产实践三个层面解释 Harness Engineering。文中的 REST、PPAF 和二维分析矩阵是为了便于讨论而做的归纳，并非已经形成行业共识的标准模型。

## 1. Harness Engineering 是什么

### 1.1 术语的来源

2026 年 2 月，HashiCorp 联合创始人 Mitchell Hashimoto 在个人实践总结中使用并阐释了“Harness Engineering”这一称呼。他同时明确表示，自己并不确定业界是否已经存在广泛接受的统一术语。他对这一概念的概括是：当智能体出现错误时，不只修正当前结果，还应把解决方案沉淀为指令、工具或验证机制，尽量避免同类错误再次发生。

随后，OpenAI 在 Codex 工程实践文章中使用“harness engineering”作为标题，介绍了如何通过代码仓库结构、工具、自动化检查和反馈回路支持编码智能体工作。这两篇文章共同推动了这一说法的传播，但它目前更适合作为一种工程视角，而不是边界严格、定义统一的标准术语。

### 1.2 从“缰绳”改为“驾驭系统”

`Harness` 更接近“马具”“挽具”或一整套驾驭装置，而不是单指 `reins`（缰绳）。如果沿用“马”的比喻，模型可以被理解为提供推理和生成能力的动力来源，Harness 则是围绕它构建的支撑与约束系统。

不过，比喻不能代替工程定义。一个可投入实际使用的智能体系统通常包括：

- 模型能力；
- 上下文与状态管理；
- 工具和外部数据接口；
- 任务编排与执行环境；
- 验证、评测和反馈机制；
- 权限、安全、合规及成本控制。

因此，可以将 Harness Engineering 定义为：**围绕模型设计运行环境、工具接口、反馈回路和治理边界，使模型的不确定性能够被约束、检测、恢复和持续改进的一组工程实践。**

它不是“更长的提示词”，也不等于“模型之外的全部基础设施”。提示词、上下文、工具、测试、沙盒和策略控制都可能成为 Harness 的组成部分，但是否纳入，应取决于它们是否直接支持智能体可靠地理解和完成任务。

## 2. 为什么需要 Harness Engineering

随着 AI 从单轮问答工具演进为能够调用工具、维护任务状态并执行多步工作的智能体，工程问题也随之变化。模型能力仍然重要，但模型能否稳定工作，越来越取决于它所处的环境是否清晰、可执行、可验证。

### 2.1 从“有趣的演示”走向“可靠的系统”

为了便于讨论，本文将智能体系统的核心工程目标归纳为 REST。这里的 REST 只是本文的分析框架，不是行业标准。

#### R：可靠性（Reliability）

系统在预期与非预期输入、环境变化或局部故障下，仍能提供符合约定的服务。

- **可恢复：** 任务中断后能够从检查点恢复，或安全地重新开始。
- **幂等：** 关键写操作可以重试，而不会产生重复副作用或破坏状态。
- **行为受控：** 即使模型输出存在差异，最终行为也应被限制在可接受范围内。
- **失败可见：** 系统应明确报告失败，不用貌似成功的输出掩盖异常。

#### E：效率（Efficiency）

系统在满足功能、质量和可靠性要求的前提下，有效使用计算、存储、网络和人工注意力。

- **预算可控：** 对 token、模型调用、工具调用、计算时间和外部服务成本设置预算。
- **交互延迟合理：** 在交互场景中尽快提供有意义的进度或结果。
- **吞吐能力匹配场景：** 在批处理和并行任务中合理调度资源。
- **避免无效循环：** 为重试、反思和重规划设置明确上限与终止条件。

#### S：安全性（Security）

系统应防止未经授权的访问、数据泄露、危险操作和供应链风险。对于能够自主调用工具的智能体，安全必须从系统设计阶段开始考虑。

- **最小权限：** 只授予当前任务必要的身份、数据和工具权限。
- **隔离执行：** 根据威胁模型选择进程、容器、轻量级虚拟机或虚拟机等隔离边界。
- **敏感操作审批：** 对不可逆、高风险或影响外部主体的操作引入人工确认。
- **不可信输入治理：** 将网页、文档、工具输出等外部内容视为不可信数据，避免其越权改变系统指令。

#### T：可追溯性（Traceability）

系统应保留足够的日志、指标、追踪和状态记录，使关键行为可以被理解、定位和审计。可追溯性依赖良好的可观测性，但两者并不完全等同。

- **全链路追踪：** 能够关联用户请求、模型调用、工具执行和最终结果。
- **决策归因：** 记录关键工具选择、策略判定及触发条件，而不是试图保存或展示不可验证的“内心推理”。
- **状态审计：** 关键状态变更有版本、时间、主体和结果记录。
- **数据最小化：** 追踪信息本身也要满足隐私与保留期限要求。

### 2.2 工程师角色的变化

当智能体承担越来越多具体执行工作时，工程师的价值不会消失，而会更多地体现在以下方面：

- 将模糊目标转化为清晰的需求、约束和验收标准；
- 为智能体提供可发现、可调用、可验证的工具；
- 建立稳定的架构边界、测试体系和反馈回路；
- 判断哪些任务适合交给智能体，哪些必须由人负责；
- 对质量、安全、成本和最终结果承担责任。

OpenAI 曾披露一项内部实验：一个最初由三名工程师组成的团队，在五个月内借助 Codex 构建了约一百万行代码的内部 beta 产品，并打开和合并了约 1,500 个 Pull Request；其代码、测试、CI 配置、文档和内部工具均由 Codex 生成。这个案例说明，在投入足够多的环境设计、自动化约束和反馈机制后，智能体可以承担高比例的工程执行工作。但它是特定团队、工具和代码仓库条件下的案例，不应直接外推为所有团队都能复现的普遍结论。

## 3. Harness Engineering 包含什么

### 3.1 管理不确定性，而不是“驾驭无序算力”

自回归大语言模型根据已有上下文，按条件概率逐 token 生成内容。输出序列本身是有序的，但生成结果具有非确定性，也可能出现事实错误、格式偏差、指令误解或不恰当的工具选择。

Harness Engineering 的任务不是消除这种不确定性，而是通过确定性的工程机制限制风险：让模型可以访问正确的信息，只能调用获准的工具，执行结果能够被验证，失败可以被捕获和恢复。

### 3.2 智能体运行闭环：PPAF

本文将智能体运行过程归纳为 PPAF 闭环：感知、规划、行动、反馈。这里将反馈和反思区分开来：反馈是系统返回的外部观测，反思则是模型或规划器基于反馈进行的后续处理。

| 阶段  | 英文         | 核心内容                                     |
| --- | ---------- | ---------------------------------------- |
| 感知  | Perception | 获取用户指令、任务状态、历史记录、工具结果和环境信息，并判断信息的来源与可信度。 |
| 规划  | Planning   | 理解目标与约束，拆解任务，选择路径和工具，预估风险与资源消耗。          |
| 行动  | Action     | 调用工具、执行工作流、更新状态或向用户返回结果。                 |
| 反馈  | Feedback   | 收集执行结果、错误、测试和评测信号，并据此结束任务、重试或重新规划。       |

### 3.3 四个工程维度

围绕 PPAF 闭环，Harness 可以从四个维度建设：

| 工程维度  | 核心机制                     | 主要目标                | 重点支撑阶段 |
| ----- | ------------------------ | ------------------- | ------ |
| 边界与接口 | 定义工具 Schema、协议、权限与输入输出契约 | 让智能体获得清晰、稳定、安全的能力边界 | 感知、行动  |
| 编排与执行 | 任务拆解、调度、状态机、超时和资源控制      | 可靠地执行多步骤任务          | 规划、行动  |
| 评测与反馈 | 测试、验证器、质量指标、错误分类与恢复策略    | 尽快发现偏差并形成可操作反馈      | 反馈、规划  |
| 知识与演进 | 文档、记忆、案例回流、规则更新和工具改进     | 把重复问题沉淀为可复用的系统能力    | 感知、反馈  |

### 3.4 二维分析矩阵

还可以用“规划主动性”和“上下文获取效率”两个维度观察智能体应用。该矩阵用于分析工程挑战，不代表严格的成熟度等级。

|              | 被动响应                        | 主动规划与反馈                      |
| ------------ | --------------------------- | ---------------------------- |
| **上下文获取效率高** | 专家辅助系统：IDE 助手、对话式 BI、交互设计工具 | 自主智能体：长周期编码、实验平台、复杂自动化系统     |
| **上下文获取效率低** | 基础问答和单点工具：客服问答、简单 API 包装    | 高阶流程自动化：自然语言 CLI、多步骤 API 工作流 |

Harness 的成熟度是系统能否从单轮响应走向复杂任务的重要因素之一，但不是唯一因素。模型能力、任务可验证性、数据质量、组织流程和风险容忍度同样会影响结果。

## 4. 如何设计 Harness

### 4.1 将 REPL 作为一种架构类比

对于交互式智能体，可以借用 REPL（Read–Eval–Print Loop）的结构理解其运行方式。这只是一种架构类比，并非所有 Harness 的本质定义；生产系统也可能采用工作流、状态机或事件驱动架构。

- **Read：** 上下文管理器读取用户请求、外部状态、工具定义和必要记忆，并形成结构化输入。
- **Eval：** 模型或规划器生成下一步意图；调用层校验请求并将其路由到相应工具或工作流。
- **Print：** 系统将执行结果、错误和验证信号整理为结构化观测。
- **Loop：** 系统根据观测结束任务、继续执行、重试或重新规划，直到达到终止条件。

设计重点不在于复刻传统 REPL，而在于清晰分离模型决策、确定性执行和反馈组装。

### 4.2 在外部状态与有限上下文之间建立映射

现实环境中的状态规模通常远大于一次模型调用的上下文窗口。Harness 需要持续选择、压缩和组织信息，把与当前决策最相关的部分提供给模型。

#### 4.2.1 上下文管理策略

| 策略          | 核心机制                  | 适用场景          | 主要风险           |
| ----------- | --------------------- | ------------- | -------------- |
| 滑动窗口        | 保留最近若干轮交互或步骤          | 连续性强的短期任务     | 较早但仍关键的信息可能被丢弃 |
| 检索增强生成（RAG） | 根据任务从文档、数据库或知识库检索相关内容 | 需要外部静态知识的任务   | 检索遗漏、过期信息及知识冲突 |
| 按需加载        | 只在需要时读取特定实体或文件        | 状态空间大但访问稀疏的任务 | 依赖准确的实体识别和依赖分析 |
| 分层记忆        | 分别管理当前上下文、任务状态和长期知识   | 长周期、多阶段任务     | 提取、融合和跨层一致性较复杂 |

上下文管理不是简单地“塞入更多内容”，而是一组信息规约规则。系统需要明确：

- 信息的权威来源及新鲜度；
- 哪些内容必须保留，哪些可以摘要或丢弃；
- 不同信息类别的 token 预算；
- 工具输出、外部文档与系统指令之间的信任边界；
- 内容在上下文中的组织方式及引用关系。

将所有重要信息堆入一个超长指令文件通常不是好办法。更稳健的方式是提供一张简洁、稳定的“地图”，再按需加载可验证的详细资料。

#### 4.2.2 Function Calling：从模型意图到确定性执行

Function Calling（函数调用或工具调用）是连接模型规划与外部行动的重要机制。不同供应商的具体实现并不相同：工具定义通常通过 API 的专门字段提交，服务端可能将其转换为模型可处理的上下文表示；调用结果也可能以结构化事件而不是普通文本返回。

一个通用生命周期可以描述为：

1. **工具注册：** 系统声明工具名称、用途、参数 Schema、权限要求和副作用。
2. **调用生成：** 模型根据任务和工具定义，生成工具选择及参数。
3. **校验与授权：** Harness 对工具名称、参数类型、权限、预算和策略进行确定性校验。
4. **执行与隔离：** 工具执行器在适当的超时、资源和安全边界内运行。
5. **结果反馈：** 系统将结果、错误和验证信息组织为结构化观测，供下一步规划使用。

其中任何一步都可能失败。稳健的降级路径包括：

- 对格式或参数错误返回机器可读的校验信息，并在有限次数内请求修正；
- 对缺失的业务信息向用户提问，而不是猜测；
- 对临时故障采用带退避和抖动的重试；
- 对永久错误快速失败，并提供可诊断信息；
- 对高风险或不可逆操作要求人工审批；
- 在无法安全执行时退回只读分析或建议模式。

将结构化工具调用降级为“自然语言指令再由传统解析器处理”，通常会引入更多歧义，不应作为默认方案。

#### 4.2.3 状态分离原则

在应用架构中，不应依赖模型自行维护需要跨轮次保持一致的关键状态。用户会话、任务进度、幂等键、审批结果和资源使用量应由 Harness 控制的外部状态存储管理，并具备版本、审计和恢复机制。

这并不意味着所有模型服务都绝对无状态，而是要求业务正确性不能依赖模型“记住”某件事。即使使用有状态会话 API，关键状态仍应在应用侧拥有明确的记录系统。

### 4.3 三类核心约束

| 约束      | 典型表现                    | 工程应对                       |
| ------- | ----------------------- | -------------------------- |
| 模型能力不完整 | 事实错误、指令误解、推理不稳定、格式偏差    | 事实校验、自动测试、结构化输出、行为边界和人工复核  |
| 上下文有限   | 关键信息缺失、长程遗忘、注意力分散       | 检索、摘要、渐进式披露、分层记忆和 token 预算 |
| 环境不可预测  | 工具故障、资源状态变化、并发冲突、用户中途干预 | 异常分类、超时、重试、幂等、回滚、重新规划和状态机  |

标准自注意力的计算和内存成本通常随序列长度快速增长，但实际模型可能采用缓存、稀疏注意力或其他优化。因此，工程限制不应被简单归因于单一的复杂度公式。

### 4.4 六项设计原则

1. **为失败而设计（Design for Failure）：** 将异常视为正常运行的一部分，预先设计超时、恢复、重试和降级路径。
2. **契约优先（Contract First）：** 用机器可读的 Schema、API 和事件定义系统边界，并对契约进行版本管理。
3. **默认安全（Secure by Default）：** 从最小权限、零信任和纵深防御出发设计系统。
4. **决策与执行分离（Decision–Execution Separation）：** 将“决定做什么”与“如何执行”解耦，使策略可审查、执行可控制。
5. **关键行为可度量（Measure What Matters）：** 对质量、延迟、成本和安全信号进行度量，避免为了“指标齐全”采集无用或敏感数据。
6. **数据驱动演进（Data-driven Evolution）：** 将经过筛选的运行数据、失败案例和人工反馈用于更新评测集、文档、规则与工具。

### 4.5 关键工程组件

| 组件        | 核心职责                  | 设计要点                   |
| --------- | --------------------- | ---------------------- |
| 工具网关      | 管理工具发现、Schema、版本和访问控制 | 动态注册、能力授权、兼容性和弃用策略     |
| 调用拦截器     | 在执行前后应用策略并记录遥测        | 超时、预算、重试、熔断、审批和幂等      |
| 反馈汇编器     | 将原始执行结果转化为模型可用的观测     | 统一错误分类、裁剪敏感信息、保留可诊断信息  |
| 上下文与状态管理器 | 管理上下文预算、任务状态和记忆       | 信息优先级、版本、新鲜度、检索和归档     |
| 异常处理器     | 对错误分类并选择恢复策略          | 区分临时、永久、业务和安全错误，避免无界重试 |
| 评测与追踪系统   | 衡量质量并定位问题             | 离线评测、在线指标、回归测试和审计关联    |

Harness Engineering 不是某一种 SDK、插件或 Agent 框架的别名。它是一组工程手段：当智能体在同一问题上反复失败时，把问题转化为更明确的文档、更好的工具、更强的校验或更合理的边界。随着模型和平台能力提升，一部分 Harness 机制可能被内化，新的应用场景也会产生新的工程需求。

## 5. 如何实现 Harness

### 5.1 控制平面与数据平面

在规模化系统中，一种常见实现方式是分离控制平面与数据平面，但小型应用不一定需要从一开始就采用完整的双平面架构。

- **控制平面**负责策略与协调，例如任务调度、模型和工具选择、资源配额、身份权限及审批规则。
- **数据平面**负责实际运行，例如智能体实例、状态读写、工具执行、沙盒和运行时遥测。

可以进一步抽象出四个功能层级：

| 层级          | 控制平面视角             | 数据平面视角                  |
| ----------- | ------------------ | ----------------------- |
| L1 呈现与集成层   | API 网关、事件总线和统一能力入口 | SDK、Webhook、聊天界面及业务应用集成 |
| L2 任务与状态管理层 | 调度器、工作流引擎、审批和长任务编排 | 状态存储、检查点、任务上下文和事件记录     |
| L3 智能体核心层   | 规划器、上下文策略、模型与工具路由  | 智能体运行时、短期记忆和长期知识访问      |
| L4 执行与治理层   | 策略引擎、身份权限、资源和成本控制  | 沙盒、工具执行器、网络和文件系统边界      |

这种分层的价值是明确责任边界，而不是为了追求架构复杂度。系统规模较小时，可以先用模块边界实现同样的职责分离，再根据负载和组织需要拆分服务。

### 5.2 核心循环、记忆与上下文转换

#### 5.2.1 核心循环

生产环境中的核心循环不是简单的 `while (true)`。它通常需要与工作流引擎或状态机结合，并明确支持：

- 暂停、恢复和取消；
- 幂等重试和最大尝试次数；
- 并发事件及状态冲突处理；
- 长周期任务和检查点；
- 用户审批与中途修改目标；
- 超时、预算耗尽和安全策略终止。

从运行视角看，这一循环可以表述为“观察—规划—行动—反馈”，与前文 PPAF 保持一致。

#### 5.2.2 记忆分层

“记忆”不是单一数据库，也不等同于向量检索。可以按用途划分为：

| 层级    | 典型载体                   | 治理要点                           |
| ----- | ---------------------- | ------------------------------ |
| 当前上下文 | 当前提示、工具结果、短期摘要         | 容量有限、访问最快；需要精细管理 token 预算      |
| 任务状态  | 状态数据库、KV 存储、工作流记录      | 保存中间状态、检查点和交互历史；需要 TTL、版本和并发控制 |
| 长期知识  | 文档库、关系数据库、对象存储、搜索或向量索引 | 关注来源、新鲜度、权限、删除机制和按需检索          |

每轮模型调用前，Harness 可以通过一条上下文转换流水线组织信息：

1. **信息源收集：** 聚合任务目标、当前状态、最近交互、工具定义和检索结果。
2. **可信度与相关性排序：** 综合来源权威性、时效性、任务相关性和权限判断优先级。
3. **裁剪、压缩与摘要：** 保留关键事实和引用关系，避免摘要引入新事实。
4. **预算分配：** 为系统指令、任务、状态、工具和输出预留 token 配额。
5. **结构化组装：** 明确区分用户请求、系统规则、外部数据和工具输出。
6. **调用后归档：** 保存必要状态和证据，清理临时信息并执行保留策略。

核心思想是把注意力管理转化为可测试、可观察的外部工程问题，而不是要求模型自行判断所有信息的优先级。

### 5.3 规划与执行策略

不同规划模式适合不同任务，不存在对所有场景都最优的默认方案。

| 模式               | 核心机制                      | 优点与限制                     | 典型场景              |
| ---------------- | ------------------------- | ------------------------- | ----------------- |
| ReAct            | 在多轮中交替生成行动并接收观测           | 灵活、实现简单；容易迷路或产生无效循环       | 探索性任务、短链路工具使用     |
| Plan and Execute | 先生成结构化计划，再逐步执行并在必要时重规划    | 计划清晰、易审计；对快速变化的环境可能不够敏感   | 结构化工作流、报告生成、数据流水线 |
| 分层规划             | 顶层规划器拆解目标，子规划器或智能体完成子任务   | 能处理复杂项目；协调成本、状态管理和边界设计更困难 | 大型研发、自动化研究、多团队任务  |
| 确定性工作流           | 由状态机或工作流预定义大部分路径，只在局部使用模型 | 行为稳定、易验证；开放性较低            | 高风险操作、合规流程、固定业务链路 |

选择策略时，应综合任务开放度、可验证性、执行风险、环境变化速度和成本，而不是仅根据任务长度决定是否使用多智能体。

### 5.4 运行治理：隔离、安全与成本

#### 5.4.1 执行隔离

隔离级别应根据威胁模型选择，不能只按技术名称排列一个绝对的“安全等级”。

| 方案     | 特点                  | 适用范围与注意事项                                                        |
| ------ | ------------------- | ---------------------------------------------------------------- |
| 受限进程   | 启动快、成本低             | 应结合低权限身份、系统调用限制和文件权限；`chroot` 单独使用不能构成可靠安全边界                     |
| 容器     | 生态成熟、部署便利，但与宿主机共享内核 | 需要 namespaces、cgroups、seccomp、能力裁剪、只读根文件系统及 AppArmor/SELinux 等防护 |
| 轻量级虚拟机 | 提供独立内核，隔离通常强于普通容器   | 适合多租户和不可信代码，但要承担镜像、启动和运维成本                                       |
| 完整虚拟机  | 隔离边界清晰、兼容性高         | 资源和管理成本较高；安全性仍取决于配置、补丁和外围控制                                      |

即使在沙盒中，也应限制网络出口、挂载目录、凭证可见性、进程数、CPU、内存、磁盘和执行时长。沙盒不是授权系统、数据治理或审计的替代品。

#### 5.4.2 资源与弹性

- **预算与配额：** 按平台、租户、智能体和任务设置 token、工具调用、CPU、内存及外部 API 配额。
- **超时：** 为网络请求、工具执行和整个任务分别设置超时。
- **重试：** 只对具有幂等性且可能恢复的错误重试，并采用退避与抖动。
- **熔断：** 当依赖持续失败时暂时停止调用，防止级联故障。
- **背压与限流：** 当下游容量不足时降低接收或执行速度。
- **安全降级：** 高风险能力不可用时，退回只读、模拟或建议模式。

#### 5.4.3 策略门控

在规划器与执行层之间设置策略门控，可以在行动发生前进行最后的授权和风险检查：

- 根据用户、服务身份和资源属性执行 RBAC 或 ABAC；
- 检查数据地域、用途和保留期限等合规约束；
- 对参数和结果进行密钥、个人信息及敏感数据检测；
- 将网页、文档和工具结果标记为不可信数据，避免其覆盖高优先级指令；
- 对付款、删除、发送消息、公开发布等操作要求更强的确认；
- 记录“谁在何时请求什么、依据什么策略、执行结果如何”。

指令注入防御不能只依赖关键词或恶意模式识别。更可靠的方案是同时使用指令与数据隔离、最小权限、能力限制、参数校验、人工审批和沙盒执行。

### 5.5 度量与演进

评测指标应服务于具体决策。建议按四类组织：

#### 任务质量

- 任务成功率（Task Success Rate）；
- 指令遵循率（Instruction Following Rate）；
- 工具调用正确率或有效率（Tool Use Accuracy/Effectiveness）；
- 事实正确性、完整性及人工验收通过率；
- 回归失败率。

#### 服务质量

- 端到端延迟（End-to-End Latency）；
- 首次 token 延迟（Time to First Token）；
- 首次行动延迟（Time to First Action）；
- 错误率、超时率和恢复成功率；
- 可用性及任务积压。

#### 资源效率

- 单任务平均或分位数 token 消耗；
- 单任务工具调用次数；
- 模型、计算和外部 API 成本；
- 人工介入次数与处理时间。

#### 安全与合规

- 策略拒绝率及误拒绝率；
- 越权调用和敏感数据暴露事件数；
- 高风险操作的审批覆盖率；
- 审计记录完整率和安全事件恢复时间。

指标不能脱离任务难度、用户群体和版本变化孤立比较。任务成功率下降时，应结合失败分类、上下文命中率、工具错误和策略拒绝原因定位问题；成本升高时，也要判断是否换来了更高的质量或更低的人工投入。

运行数据只有在完成脱敏、权限控制和质量筛选后，才适合进入评测集或改进闭环。数据驱动演进不是简单地“收集更多日志”，而是将可靠证据转化为可验证的文档、规则、工具和测试。

## 写在最后

Harness Engineering 不是新的“银弹”，而是一种把智能体问题重新放回软件工程语境中的方法：接受模型具有不确定性，同时用明确的边界、工具、状态、测试和反馈管理这种不确定性。

当智能体承担更多代码生成和任务执行工作时，工程师的核心职责并未消失，而是从直接完成每一步，扩展到设计环境、表达意图、建立约束并验收结果。高质量 Harness 的价值，不是让模型永远不犯错，而是让错误更容易被发现、影响更容易被控制、系统更容易恢复，并让同类问题逐步转化为可复用的工程能力。

这套驾驭系统的目的不是束缚模型，而是在可控边界内更充分地释放模型能力。随着模型和平台不断演进，Harness 的具体形态也会变化，但可靠性、安全性、可追溯性和工程责任不会因此失去价值。
