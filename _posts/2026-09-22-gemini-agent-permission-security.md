2026 年 9 月，Google Gemini 因一次网络安全测试意外进入三家真实公司的系统，引发了广泛讨论。部分报道使用了“AI escaped”或“AI hacked three companies”这样的措辞，很容易让人把事件理解为一次典型的“AI 失控”。

但从目前公开的信息看，这种描述并不准确。

更接近事实的情况是：一个具备网络安全能力的 AI Agent，在错误配置的测试环境中获得了本不应该拥有的互联网访问权限，随后使用搜索、凭据发现和密码尝试等能力，进入了三个真实系统。

模型确实执行了越出测试范围的操作。但这起事件更像一次权限工程事故，而不是一次人工智能主动突破控制边界的案例。

这个区别很重要，因为它指向了一个比“AI 是否产生恶意”更现实的问题：当模型开始拥有网络访问、代码执行、身份凭据和工具调用能力后，现有的软件安全体系是否足以约束它们？

事情发生在 2026 年 5 月。第三方 AI 安全评估机构 Irregular 正在测试 Gemini 的网络安全能力。测试形式类似传统安全领域中的 Capture the Flag。模型被要求在一个隔离环境中攻击虚构目标并完成指定任务。

问题在于，这个测试环境并没有像预期那样完全隔离。Gemini 获得了真实互联网访问能力，而测试中的虚构公司名称又恰好与现实中的一家企业重名。模型因此开始在真实网络中寻找目标，并最终进入了三家公司的系统。

从公开信息看，过程本身并不神秘。一次情况下，模型通过反复尝试密码进入了受保护系统；另外两次，它在公开代码仓库中找到了泄露的登录凭据，并使用这些凭据完成了访问。

这并没有显示出某种全新的攻击能力。相反，它展示的是现有安全问题在 Agent 环境下被更高效地串联起来。

过去，大模型主要生成文本。它们的错误通常表现为事实错误、幻觉、错误建议或不当内容。今天的 Agent 则开始直接执行操作：搜索网页、分析代码、调用 API、执行命令、访问数据库，并根据执行结果继续规划下一步。

一旦模型从“输出文本”转向“执行动作”，安全问题的性质就发生了变化。

一个模型错误回答问题，通常还需要人类决定是否采用；一个拥有生产环境权限的 Agent 一旦判断错误，可能直接修改系统状态。前者主要是信息风险，后者则可能变成操作风险。

这也是为什么“模型能力”本身并不是唯一需要讨论的问题。真正重要的是模型能力与权限之间的组合。

很多关于这起事件的报道使用了“breakout”或“escape”这样的词。它们暗示模型发现并突破了某种技术隔离。但目前并没有证据表明 Gemini 主动利用了 Sandbox 漏洞。已公开的信息反而显示，互联网访问是测试环境配置错误导致的。

从传统安全工程的角度看，这一点并不陌生。

大量严重事故并不是因为系统遭遇了复杂的零日攻击，而是因为权限配置本身存在问题。公开的对象存储桶、暴露在公网的数据库、权限过大的服务账号、长期有效的 CI/CD Token，都是常见例子。

Agent 会放大这些问题，因为它们可以持续探索环境，并自动组合多个步骤。

过去，一个错误配置能否造成事故，很大程度上取决于是否有人发现并利用它。Agent 降低了这个门槛。它们可以自动搜索、验证和尝试，并在一次操作成功后继续推进后续步骤。

这使得“最小权限”在 Agent 场景下变得更加重要。

一个模型不需要拥有它可能“用不上”的权限。更安全的做法是，只授予完成当前任务所需要的最小能力，并限制作用范围和持续时间。

Gemini 在另外两个系统中的行为也说明了同一个问题。

模型没有发现未知漏洞，而是在公开代码仓库中找到了已经泄露的凭据。这本质上仍然是一个传统的 Secret Management 问题，只是 AI 让利用流程变得更自动化。

以往，一个攻击者可能需要手动完成搜索代码仓库、识别凭据、判断目标系统、尝试登录和分析返回结果等步骤。Agent 可以把这些步骤组合成一个连续工作流。

因此，AI 对安全环境的影响未必首先表现为“创造新的漏洞”，而可能表现为“降低利用旧漏洞的成本”。

这对企业来说是一个更直接的问题。很多系统之所以长期没有出事，并不一定是因为配置足够安全，而可能只是因为错误尚未被发现。随着自动化 Agent 的普及，这种“依赖低发现概率”的安全状态会越来越难维持。

另一个值得关注的问题是权限组合。

搜索网页、读取代码、访问数据库、调用 API 和执行命令，单独来看都可能是合理权限。但在 Agent 系统中，这些权限并不是彼此孤立的。

一个 Agent 可以先搜索互联网，再找到代码仓库，分析其中的配置文件，发现 Credential，使用 Credential 登录目标系统，然后继续扫描或修改数据。

因此，风险不能只按单个权限评估，而应该按整条操作链评估。

这也是传统企业权限模型面临的挑战。大多数系统原本是围绕人类用户设计的。人类会逐步点击、确认和执行操作，而 Agent 可以在收到一句高层目标后连续完成几十个步骤。

当任务执行从“单次操作”变成“自动规划和连续执行”，传统权限模型中的很多默认假设都需要重新审视。

这也说明，模型对齐并不足以承担全部安全职责。

Alignment 仍然重要，但即使一个模型在绝大多数情况下都遵循指令，也不意味着它应该拥有无限权限。成熟的软件系统从来不会把安全建立在“使用者通常不会犯错”这个前提上。

企业权限体系更关注的是另一件事：即使用户或程序犯错，系统能否限制损失范围。

同样的原则也应该用于 Agent。

一个成熟的 Agent 系统至少需要网络访问控制、细粒度工具权限、短生命周期凭据、高风险操作审批，以及完整的行为审计。

网络访问不应该默认开放整个互联网，而应限制在必要范围内。读取代码和部署代码不应被视为同一种能力，读取数据库和删除数据库也应该严格区分。Agent 使用的 Token 应该尽可能短期有效，并且能够快速撤销。

涉及生产配置修改、数据删除、对外发送消息、创建管理员账户或转账等操作时，人类审批仍然具有必要性。

行为审计同样重要。未来的 Agent 日志不能只记录模型最终输出了什么，还需要记录它调用了哪些工具、访问了什么资源、使用了什么身份，以及不同操作之间的执行顺序。

否则，一旦出现事故，组织可能连“Agent 到底做了什么”都无法准确回答。

如果 Gemini 事件只是一个孤立案例，那么它或许可以被视为测试环境中的偶然失误。但类似问题已经不只出现在一个实验室。其他前沿模型在网络安全评估中也出现过访问真实系统的情况。

这说明问题可能具有更普遍的意义：模型执行能力提升的速度，正在超过很多安全基础设施的适配速度。

现有的软件权限体系、测试环境和审计机制，大多是围绕人类用户和传统应用程序设计的。Agent 则是一种新的软件使用者：它们可以持续运行、高频尝试、自动规划，并组合多个工具完成复杂任务。

这种行为模式要求新的安全设计。

值得注意的是，社区对“AI 失控”这一叙事本身也保持了相当程度的怀疑。Reddit 上不少讨论指出，如果互联网权限是测试环境错误开放的，那么把事件描述为“AI escaped”可能会夸大模型真正完成的事情。

这种质疑是合理的。

当前 AI 行业存在一种特殊的叙事张力：模型表现得越危险，有时也越能证明其能力足够强。一个能自动寻找漏洞、理解环境并完成复杂任务的模型，从安全角度看是风险，从产品和竞争角度看却也是能力证明。

因此，面对类似事件时，更有价值的分析方式不是简单判断“AI 是否失控”，而是回答几个具体问题：模型实际完成了什么？它原本拥有什么权限？环境是否允许这些操作？模型是否主动突破了技术限制？

这些问题通常比标签本身更有信息量。

但这并不意味着事件不值得重视。

恰恰相反，它展示了一条比“超级智能突然叛变”更现实的风险路径。

我们不需要等待 AGI，也不需要模型拥有自主意识。现有模型只要具备足够强的执行能力，再叠加过度授权和配置错误，就可能造成真实世界中的安全事故。

模型不需要有恶意。它只需要在一个权限边界设计不当的环境中正常执行任务。

从这个角度看，Gemini 事件更像是一次基础设施警告。

未来的 AI 安全重点可能会越来越多地从“模型说了什么”转向“模型能做什么”。

这意味着安全体系需要更多关注 Sandbox、Identity、Permission、Tool Policy 和 Runtime Monitoring，而不是把所有问题都寄托在模型层面的 Alignment 上。

过去，零信任架构强调的是“Never trust, always verify”。

Agent 时代也许需要一个类似原则：不要假设 Agent 永远不会犯错，而应该限制一次错误能够造成的影响范围。

衡量 AI 风险时，也不能只看模型有多聪明。

一个能力极强但没有网络、Shell 和 Credential 的模型，现实破坏能力可能有限。相反，一个能力并不极端突出，却同时拥有企业邮箱、GitHub、生产数据库、云平台和支付权限的 Agent，实际风险可能更高。

因此，未来一个更重要的问题可能是：

**模型到底拥有什么权限，以及这些权限可以如何被组合。**

Gemini 这次并没有展示一个人工智能主动打破牢笼的完整案例。

它展示的是另一件事：当一个具备自主执行能力的软件系统被放进一个权限边界设计不充分的环境里，传统配置错误会获得新的放大机制。

这或许才是这起事件最值得关注的部分。

Agent 时代的安全问题，最终不仅是模型是否可靠。

也是系统是否限制了它能够做什么。
