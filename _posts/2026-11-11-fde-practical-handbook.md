## B01｜零基础先读：把整套系统想成一次工单协作

### B1.1 你将完成什么

假设一家小公司网络间歇中断，员工创建一条工单。值班人员先读问题，再查询告警，查找处理规程，提出下一步检查，交给有权限的人确认，并保存处理记录。软件会帮助完成其中一些步骤，语言模型负责理解和生成文本，业务系统负责提供事实、保存状态和执行授权动作。

第一阶段的学习结果是你能在自己电脑上运行一个小程序，知道它读了什么、为什么返回该结果，并能修改一条规则。第二阶段接入文件和数据库。第三阶段再加入模型或 AI 编程助手。真实客户试点还需要数据授权、运行责任和业务验证。

### B1.2 十六个必须先懂的词

| 词 | 通俗解释 | 工单例子 |
| --- | --- | --- |
| 文件 | 存在磁盘上的一份内容 | tickets.csv 存放模拟工单 |
| 文件夹 | 一组文件的容器，也称目录 | fde-beginner 保存练习 |
| 路径 | 文件在电脑上的位置 | 项目目录下的 hello.py |
| 程序 | 告诉电脑按什么步骤工作的文字 | 读取、筛选、汇总工单 |
| Python | 一种编程语言 | 用它写查询和校验逻辑 |
| 解释器 | 执行 Python 程序的软件 | python 命令启动解释器 |
| 终端 | 输入命令并查看结果的窗口 | 输入运行命令，看到结果或报错 |
| 编辑器 | 编写和修改文件的工具 | 用 VS Code 修改代码 |
| 函数 | 一段有名字、可重复调用的操作 | get_ticket 查询一条工单 |
| 参数 | 交给操作的输入值 | 工单号 T-1001 |
| 返回值 | 操作完成后交回的数据 | 工单内容或未找到状态 |
| JSON | 用键和值组织数据的文本格式 | 客户号、状态、建议组成一个对象 |
| 数据库 | 按规则保存和查询数据的系统 | 按客户号查询工单 |
| API | 软件向另一软件提出请求的约定入口 | 用工单号请求最新状态 |
| 模型 | 根据输入生成或预测输出的组件 | 将工单现象整理成摘要 |
| Agent | 可以根据中间结果选择后续工具或步骤的应用 | 查询后发现资料缺失，再选择另一项查询 |

“客户号”在企业多客户应用中常称 tenant_id，即租户标识。“Schema”表示输入或输出的结构约定。“部署”表示把应用放到目标运行环境，使用户能够使用。第一次遇到缩写时先记住它解决什么问题，回到第 25 章再查完整术语。

### B1.3 浏览器、应用、模型之间的关系

浏览器显示页面，应用后端接收请求，数据接口提供事实，模型生成建议，应用检查结果并呈现给用户。工具调用是应用执行的一次外部查询或操作，模型提出调用请求后仍需要应用真正执行。用户看见“完成”时，应能找到实际保存记录。

开发环境是你写和调试程序的地方。测试环境用来试验。生产环境服务实际用户。零基础练习全部从自己的模拟数据开始，先建立“改了代码会影响什么”的认识。

### B1.4 两条阅读路线

零编程基础按 B01 → B02 → B03 → B04 → B05 阅读，再进入 01–09 和 20–21。已能写简单 Python 的读者可直接运行 B03 三个练习，能解释并修改后进入工程章节。原来的 14 天计划作为基础达标后的项目阶段，完整零基础学习可先安排 30 天打底。

**今天的检查。** 用自己的话解释程序、API、模型和 Agent 各做什么。再画出一条“收到工单—获得事实—提出建议—审核—保存”的流程，标注哪些步骤需要人判断。

### B1.5 模型、提示词、Token 和幻觉

提示词是交给模型的任务说明，上下文是模型当前能看到的指令、资料、历史和工具结果。Token 是模型处理文本的计量单位，与汉字或英文单词并非固定一一对应。输入和输出都可能计入费用，具体口径取决于服务。上下文窗口表示一次处理可容纳的信息范围，窗口更大仍需要选择相关信息。

模型可能生成流畅但没有依据的内容，常称为幻觉。应用应提供有效证据、允许返回信息不足，并用评测发现错误。仅让模型写一句“请保证准确”不足以建立可靠交付。输出随机性也意味着同一题多次运行可能不同，需要按任务性质重复验证。

RAG 可理解为“先查资料，再根据资料回答”。例如先查找该设备适用的现行规程，再生成处理建议。微调是用训练数据调整模型参数，通常比写提示词或更新检索资料需要更多数据与评估准备。零基础阶段先学会用现有模型处理有证据的小任务。

### B1.6 读懂一次 API 请求

请求通常包含地址、方法、身份信息和参数。响应包含状态与数据。GET 常用于读取，POST 常用于提交处理或创建操作，具体含义由接口契约规定。身份验证常使用令牌等凭据，真实凭据应通过获准的配置方式保存。

| 常见 HTTP 状态 | 入门理解 | 程序下一步 |
| --- | --- | --- |
| 200 | 本次 HTTP 请求成功处理 | 继续检查业务响应内容 |
| 400 | 请求内容不符合要求 | 核对字段与格式 |
| 401 | 身份未通过认证 | 核对认证配置 |
| 403 | 请求被禁止 | 核对访问权限与策略 |
| 404 | 请求的资源未找到或未公开 | 检查地址、对象和接口约定 |
| 409 | 当前状态或版本存在冲突 | 重新读取并核查 |
| 429 | 请求过多或受配额限制 | 按响应与服务策略处理 |
| 500 | 服务端发生错误 | 记录请求标识并按约定重试或接手 |

HTTP 成功后仍需检查业务字段。例如 status=awaiting_review 说明建议等待审核，不能据此显示“已保存”。具体错误含义以服务文档为准。

## B02｜从安装到运行第一个程序

### B2.1 只准备三类工具

先准备浏览器、Python 3 和编辑器。聊天式 AI 可以帮助解释概念、审核代码与模拟访谈。编辑器内的 AI 助手可在后续帮助修改文件。标准库练习主要消耗本地电脑资源，尚无需接入付费模型 API。聊天产品订阅与开发者 API 是两种不同服务，真正调用外部 API 时再核对所选服务的账号和计费。

Python 使用官网提供的受支持 Python 3 版本，并以所选课程和依赖兼容性为准。以下练习使用普通标准库语法，不依赖某个最新小版本。VS Code 是编辑器，安装 Python 扩展后仍需安装或选择 Python 解释器。

官方入口 [Python 下载](https://www.python.org/downloads/) · [VS Code 下载](https://code.visualstudio.com/download) · [Python 与 VS Code 入门](https://code.visualstudio.com/docs/python/python-tutorial)。

### B2.2 准备文件夹和文件

在文档目录新建 fde-beginner 文件夹，用 VS Code 的“打开文件夹”打开它。通过文件列表新建 hello.py。扩展名 .py 表示 Python 文件，检查没有被保存成 hello.py.txt。复制代码时只复制代码块内部内容。

```python
ticket_id = "T-1001"
print("开始检查工单", ticket_id)
```

第一行给变量 ticket_id 一个字符串值。变量是保存值的名字，字符串是带引号的文本。第二行使用 print 将信息显示到终端。保存文件后打开 VS Code 的终端。

### B2.3 macOS 运行步骤

先在终端执行版本检查，看到 Python 3.x 字样后继续。每条命令单独输入并回车。

```shell
python3 --version
python3 -m venv .venv
.venv/bin/python hello.py
```

第一条检查解释器。第二条在当前目录创建项目虚拟环境。第三条明确使用该环境中的解释器运行文件。预期看到“开始检查工单 T-1001”。如果命令提示找不到 Python，按官方安装说明安装后重新打开终端再检查。

### B2.4 Windows 运行步骤

在终端执行下列命令。如果安装中提供了 py 启动命令，可使用这一组。

```shell
py --version
py -m venv .venv
.\.venv\Scripts\python.exe hello.py
```

若 py 不可用但 python --version 能显示已安装的 Python 3，则用 python 替换前两条中的 py。第三条直接调用虚拟环境中的程序，避免把是否激活环境变成最初的额外障碍。

### B2.5 确认当前目录

“当前目录”是终端此刻工作的文件夹。macOS 用 pwd 查看位置、ls 查看文件，Windows PowerShell 用 Get-Location 和 Get-ChildItem。应能看到 hello.py 和刚创建的 .venv。文件不在当前目录时，先在编辑器打开正确项目文件夹并创建新终端。

### B2.6 设置编辑器解释器

在 VS Code 命令面板中搜索 Python: Select Interpreter，选择当前项目 .venv 下的 Python。命令面板通常可通过 macOS 的 Shift+Command+P 或 Windows 的 Ctrl+Shift+P 打开。菜单与交互若变化，按当前官方教程操作。

环境验证 [S17 · Python 虚拟环境](https://docs.python.org/3/tutorial/venv.html) · [S18 · VS Code Python 教程](https://code.visualstudio.com/docs/python/python-tutorial)。

### B2.7 常见报错速查

| 报错或现象 | 通常含义 | 第一步检查 |
| --- | --- | --- |
| command not found / 无法识别命令 | 当前终端找不到该程序 | 安装是否完成、命令名称、重开终端 |
| can't open file | 文件位置或名字不匹配 | 当前目录、扩展名、保存状态 |
| SyntaxError | 代码语法有问题 | 报错行及前一行、英文引号与括号 |
| IndentationError | 缩进不符合 Python 结构 | 使用一致空格，检查 if 或 def 下方 |
| NameError | 用到了未定义的名字 | 拼写、定义是否在前、作用范围 |
| ModuleNotFoundError | 当前解释器找不到某个包 | 选用哪个环境、是否真的需要外部包 |
| FileNotFoundError | 程序要读的文件不存在于指定位置 | 路径相对于哪里、文件名是否正确 |
| 中文显示异常 | 编码或终端显示设置不一致 | 文件用 UTF-8，读取时指定编码 |
| 程序没有新输出 | 可能未保存、未运行正确文件 | 保存后核对运行命令和文件 |

遇到问题保留完整错误文字与运行命令。问 AI 时附上操作系统、解释器版本、当前目录和去除敏感信息的相关代码，先请它解释错误，再提出最小修复。

## B03｜三次小练习：数据从哪里来，程序怎样处理

### B3.1 练习一，理解输入、判断与输出

新建 01_check_ticket.py，复制下面代码并保存。运行方法与 hello.py 相同，替换文件名即可。

```python
import json


def check_ticket(ticket):
    ticket_id = ticket.get("ticket_id")
    if not ticket_id:
        return {"status": "invalid", "reason": "缺少工单号"}
    return {"status": "ready", "ticket_id": ticket_id}


valid = check_ticket({"ticket_id": "T-1001"})
missing = check_ticket({})
assert valid["status"] == "ready"
assert missing["status"] == "invalid"
print(json.dumps([valid, missing], ensure_ascii=False, indent=2))
```

字典用键和值保存信息。get 读取一个键，缺少时默认返回 None。if 判断条件，return 交回函数结果。assert 检查条件是否为真，失败会停止程序。json.dumps 把对象转换为 JSON 文本，ensure_ascii=False 便于显示中文。

预期得到一个 ready 结果和一个 invalid 结果。自己先预测，再把第一条工单号改成空字符串，观察结果为何改变。增加“缺少客户号”检查是进阶题，可请 AI 给提示，自己修改后再验证。

### B3.2 练习二，从 CSV 读取模拟工单

在项目文件夹新建 tickets.csv，使用 UTF-8 保存如下文本。

```csv
tenant_id,ticket_id,status
customer_a,T-1001,open
customer_a,T-1002,closed
customer_b,T-2001,open
```

新建 02_read_csv.py，复制以下代码。它按客户过滤后统计未关闭工单。教学身份写死在程序里，真实身份必须通过服务端认证获得。

```python
import csv
from pathlib import Path


data_path = Path(__file__).with_name("tickets.csv")
with data_path.open(encoding="utf-8-sig", newline="") as file:
    rows = list(csv.DictReader(file))

required = {"tenant_id", "ticket_id", "status"}
if not rows or not required.issubset(rows[0]):
    raise ValueError("CSV 为空或缺少必要列")

visible = [row for row in rows if row["tenant_id"] == "customer_a"]
opened = [row for row in visible if row["status"] == "open"]
assert len(visible) == 2
assert len(opened) == 1
print("客户 A 可见工单", len(visible), "其中未关闭", len(opened))
```

预期输出“客户 A 可见工单 2 其中未关闭 1”。with 在结束后关闭文件。Path(__file__) 指向程序本身，with_name 找到同文件夹下的数据，因此在其他当前目录运行也能定位它。这个练习只做最小列检查，重复键、空字段与非法状态留给后续练习扩展。

来源定位 [S19 · Python CSV](https://docs.python.org/3/library/csv.html)。

### B3.3 练习三，使用 SQL 查询

新建 03_query_sqlite.py。SQLite 允许用一个轻量数据库练习 SQL，以下数据库仅在内存中创建，程序结束后消失。

```python
import sqlite3


connection = sqlite3.connect(":memory:")
try:
    connection.execute(
        "CREATE TABLE tickets (tenant_id TEXT, ticket_id TEXT, status TEXT)"
    )
    connection.executemany(
        "INSERT INTO tickets VALUES (?, ?, ?)",
        [
            ("customer_a", "T-1001", "open"),
            ("customer_b", "T-2001", "open"),
        ],
    )
    rows = connection.execute(
        "SELECT ticket_id FROM tickets WHERE tenant_id = ? AND status = ?",
        ("customer_a", "open"),
    ).fetchall()
    assert rows == [("T-1001",)]
    print("查询结果", rows)
finally:
    connection.close()
```

CREATE TABLE 创建表，INSERT 写入行，SELECT 选字段，WHERE 限定条件。问号是参数占位符，具体值通过单独参数传入。fetchall 取出结果行。预期只返回 T-1001。把查询租户换成 customer_b 前，先预测断言为什么会失败，再修改断言验证自己的理解。

来源定位 [S20 · Python sqlite3](https://docs.python.org/3/library/sqlite3.html)。

## B04｜怎样把 AI 用成学习伙伴和工作助手

### B4.1 建立一个可检查的协作循环

先告诉 AI 当前任务、已知事实和已有文件，再让它提出一个小步骤。运行或检查这个步骤，把实际结果返回给它，最后保存通过验证的版本。每次记录 AI 生成了什么、你核对了什么、仍有哪些未知。用于客户资料时先确认获准的工具与数据范围，可用模拟数据完成学习。

聊天助手适合解释概念、模拟访谈、整理文字和审核短代码。能读取项目文件的编码助手适合定位文件、生成小范围修改、运行已有检查。能操作终端或网页的 Agent 还需要明确可执行动作、允许的数据与停止条件。权限范围与执行结果由使用者确认。

## 01｜FDE 的职责和工作边界

### 1.1 从结果反推工作

**来源摘要。** 麦肯锡 2026 年 10 月访谈强调，FDE 嵌入客户环境，用真实系统和数据构建工具，并与使用者共同改变流程。三位受访者分别强调工程实现、组织决策和流程重构，且对咨询与工程角色的融合程度存在不同侧重。参见 S01 的定义、岗位差异和初期工作章节。

**实践建议。** 将一项 FDE 工作分解成六个连续责任，可以避免只完成其中一段就误判交付结束。

| 责任 | 要回答的问题 | 证据 |
| --- | --- | --- |
| 发现 | 哪个具体决策或操作值得改善 | 访谈、操作观察、基线 |
| 定义 | 由谁在什么条件下验收 | 一页项目定义与验收案例 |
| 构建 | 系统怎样获得数据并完成任务 | 数据契约、接口、可运行版本 |
| 验证 | 正常与异常条件下表现怎样 | 评测报告、人工复核 |
| 运行 | 故障时谁接手、如何恢复 | 监控、运行手册、回退记录 |
| 积累 | 哪些能力可交给客户或其他项目 | 交接演练、复用记录 |

### 1.2 与相邻岗位如何协作

下表是本手册建议的分工视角。不同企业可能把几项责任放在一个人身上，岗位名称不能替代职责约定。

| 工作 | FDE 需要承担的部分 | 常见协作方 |
| --- | --- | --- |
| 业务发现 | 理解实际流程，将问题落成可测试范围 | 业务负责人、产品经理、咨询顾问 |
| 技术验证 | 连通最小链路，验证约束 | 解决方案工程师、架构师 |
| 应用构建 | 代码、集成、评测与使用反馈 | 后端、前端、数据工程师 |
| 生产运行 | 明确运行责任并完成交接 | 运维、平台、安全与系统团队 |
| 产品抽象 | 带回多个客户的共性与差异 | 核心产品、平台工程团队 |

FDE 不必亲自完成每项专业工作，但需要知道某个依赖尚未解决会怎样影响结果。项目需要在开始时指定业务验收人、系统授权人、发布负责人和运行负责人。组织中某人愿意支持项目，不代表其同时拥有这些权力。

### 1.3 三种完成程度

技术可行意味着一条链路能跑通。业务采用意味着目标用户能够在实际工作中使用它。业务价值意味着相应结果发生了可验证的变化。三种证据应分别保留。客户确认界面好用，可以支持采用判断，但不足以独立证明节省了多少成本。

**自测。** 用五句话解释一个旧项目。用户是谁、原流程怎样、你改变了什么、怎样测量结果、交付后谁维护。缺少的一句通常就是要补的交付证据。

来源定位 [S01](https://www.mckinsey.com/featured-insights/mckinsey-explainers/what-is-a-forward-deployed-engineer)。

### 新手解释与 AI 辅助

**先理解。** 先把岗位理解成一个从问题到交付的完整责任链。第一次练习可以由你同时扮演业务用户与工程师，但要在记录中区分两种身份。

**可以交给 AI 的工作。** 把一页项目介绍交给 AI，请它按“用户、输入、动作、结果、责任人”抽查缺项。核对它指出的缺口是否真的没有证据，补资料后再整理职责表。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

| 行业理解 | 能解释业务对象、时限和异常代价 | 画一条真实工单流程 |
| 客户发现 | 区分事实、观点和待验证假设 | 复盘最近一次任务 |
| 软件基础 | 能读错误堆栈、改代码、管理依赖 | CSV 输入校验与错误报告 |
| 数据与集成 | 能读写 SQL、调用 API、处理分页 | 增量同步模拟工单 |
| AI 应用 | 能组织上下文、定义工具和输出 | 实现结构化处置建议 |
| 评测 | 能写成功条件并定位失败层级 | 构造错误和拒绝案例 |
| 生产运行 | 能查日志、停用功能和恢复版本 | 演练一次接口超时 |
| 产品与商业 | 能衡量用户结果和复用成本 | 换一套客户配置重跑 |

建议采用 0–3 分自评。0 分为不了解，1 分为跟教程完成，2 分为能独立完成，3 分为能解释取舍并处理异常。标记每项最近一次实际证据，避免只凭熟悉术语打分。

### 2.2 技术基础清单

Python 需要掌握函数、字典、异常、文件读写、类型提示、环境隔离、单元测试，以及 async/await 的基本用途。SQL 需要掌握连接、聚合、唯一键、事务和索引。HTTP 需要理解请求、响应、状态码、认证、分页、超时与限流。Git 需要掌握差异、分支、提交和回退。

异步适合等待多个互相独立的 I/O 调用。它不能自动保证更快，也不能代替连接池和并发上限。初学者先用同步接口正确实现数据与错误处理，再把已知瓶颈改成受控并发。

在进入 Agent 框架前，先做一个无需模型的工单查询服务。能够根据工单号返回所属客户、状态、更新时间和关联告警，并对不存在、无权限和接口不可用给出不同结果。这个练习会暴露很多真实 FDE 项目同样需要处理的基础问题。

### 2.3 怎样选择学习资料

FDE Lab 的 29 个里程碑可以作为自测和练习进度表。FDE Factory 的公开手册可辅助了解岗位和培训机构的能力划分，其 FDEE 命名与认证属于该机构的体系。使用这些材料时，将它们的岗位描述与目标公司的实际职责相互核对。参见 S12、S14。

来源定位 [S12](https://fdelab.dev/learn/) · [S14](https://www.fdefactory.ai/handbook)。

### 新手解释与 AI 辅助

**先理解。** 刚开始不必同时学所有技术。先能运行、解释和修改 B03 的三个小程序，再扩展到接口和模型。

**可以交给 AI 的工作。** 使用 P12 做能力诊断。让 AI 给出一道新输入或新约束，用实际修改结果评估自己。把不会解释的语法写进下一次练习。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 03｜进入客户现场的前五天

**实践建议。** 第一周的目标是把“值得做、能够做、有人用、有人接手”四项不确定性变成可核查的问题。可以演示小工具，但应同时积累业务与技术证据。

| 日期 | 主要动作 | 当天产物 | 需要确认的人 |
| --- | --- | --- | --- |
| 第 1 天 | 对齐目标、负责人、约束和时限 | 项目定义草案、利益相关者图 | 业务发起人 |
| 第 2 天 | 跟随实际操作，复盘近期案例 | 现状流程、异常分支、等待时间 | 一线操作人员 |
| 第 3 天 | 验证数据字段、权限和接口 | 数据样例、访问矩阵、依赖清单 | 数据及系统负责人 |
| 第 4 天 | 比较人工、规则和 AI 方案 | 技术决策记录、最小切片 | 技术负责人及用户 |
| 第 5 天 | 走查验收案例，展示初步链路 | 范围、验收集、下一周期计划 | 验收人和运行负责人 |

### 3.1 访谈问题库

1. 请打开最近处理的一条工单，从收到到结束走一遍。
2. 每一步使用什么系统，需要从哪里复制什么信息？
3. 哪一步花时间最多？其中多少是操作，多少是等待？
4. 你在哪些情况下会找同事确认？他知道什么额外信息？
5. 最近一次处理错误发生在什么地方，后来怎样发现？
6. 哪些步骤需要授权，授权可能因客户或金额不同而变化吗？
7. 系统给出建议后，你要看到什么证据才会使用？
8. 谁会因新流程增加额外工作？
9. 遇到资料冲突、数据缺失或系统停机时，现在怎么处理？
10. 交付后谁维护知识和规则，谁确认结果是否改善？

### 3.2 观察记录

记录事件时间、系统名、输入、输出、操作角色、等待时长、返工和例外。将“用户说平均十分钟”和“观察到三条工单分别用时 8、17、24 分钟”分别记录。少量观察用于发现机制，不代表可靠总体平均值。

### 3.3 证据台账

| 主张 | 当前依据 | 状态 | 下一步 | 负责人 |
| --- | --- | --- | --- | --- |
| 大量工单时间耗在查询告警 | 两位用户访谈 | 待量化 | 抽样测量查询时间 | 业务分析人员 |
| 可访问历史告警 API | 系统负责人说明 | 待实测 | 用测试身份取一条记录 | 接口负责人 |
| 建议可直接写回工单 | 会议中的设想 | 待授权 | 明确字段、角色与审批 | 系统授权人 |

麦肯锡强调的现场理解可作为这一章的起点。具体日程与台账是本手册设计。来源定位 [S01](https://www.mckinsey.com/featured-insights/mckinsey-explainers/what-is-a-forward-deployed-engineer)。

### 新手解释与 AI 辅助

**先理解。** 业务访谈是让用户演示最近做过的事情。模拟访谈能练提问，真实项目还要与实际操作记录核对。

**可以交给 AI 的工作。** 用 P02 模拟访谈，用 P03 整理纪要。把原话、观察和推测分开，任何 AI 补出的数量、人物与日期都回到原记录确认。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 04｜场景选择与业务价值基线

### 4.1 用决策对象描述场景

一个有效场景应描述“哪类用户在什么触发条件下，根据哪些资料，完成哪个决定或操作”。“建设智能运维平台”还需要继续拆解。“值班人员收到企业专线故障工单后，整理最新相关告警、引用有效处理规程，并生成待审核的下一步建议”已经可以设计输入、输出和验收。

### 4.2 场景评分

教学评分可采用 1–5 分，分别衡量业务价值、发生频率、数据可用性、反馈可观测性和交付可控性。权重由团队共同确定。任何关键授权未解决都单独列为依赖，即使总分很高也不能凭评分越过它。

| 维度 | 高分的表现 | 低分需要补的证据 |
| --- | --- | --- |
| 业务价值 | 影响清晰的时限、成本或客户结果 | 价值仅停留在感觉 |
| 频率 | 在试点期内能观察足够任务 | 样本少且季节差异大 |
| 数据 | 样例可取、字段可理解、授权明确 | 只有截图和口头承诺 |
| 可观测性 | 能确认任务结果与人工判断 | 成败长期无法观测 |
| 可控性 | 边界清楚、失败可接手 | 多系统写入责任不清 |

### 4.3 建立基线

至少记录任务量、人工活动时间、端到端时长、返工率和异常分布。端到端时长包括排队、等待审批和系统处理时间。活动时间与等待时间分开，才能判断 AI 到底改变了哪一部分。

教学例。每月 1,000 条适用工单，平均整理资料 12 分钟，试点后 7 分钟，可用工时减少估算为 1,000 × 5 ÷ 60 ≈ 83.3 小时。若按 150 元/小时折算，对应约 12,500 元的时间价值。只有这些时间确实用于其他工作或减少了支出，才可以进一步主张相应的经济收益。模型、基础设施、人工复核和维护成本需另行计入。

### 4.4 试点测量方式

可按相近类型工单分组比较，或采用分阶段上线。记录客户类型、严重程度、班次和数据完整性，检查两组是否可比。同一个人先做人工版再用 AI 处理同一工单，会受到记忆影响。样本有限时明确描述观察范围，避免把短期变化直接归因为系统。

完成标准是业务负责人能解释指标的定义、分母、采样区间和数据来源。三项商业方向参考 A&M，计算方式和示例为教学补充。来源定位 [S02，第 3 页](https://www.alvarezandmarsal.com/sites/default/files/2026-04/The%20Rise%20and%20Role%20of%20the%20Forward%20Deployed%20Engineer.pdf)。

### 新手解释与 AI 辅助

**先理解。** 基线是改变之前的表现。先知道过去处理一件事要多久，才有条件讨论新方案是否改善。

**可以交给 AI 的工作。** 让 AI 根据你给出的任务量与工时生成可编辑计算表，并解释公式。用手算复核一行，再检查是否漏计审核与维护成本。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 05｜把模糊需求写成可验收范围

### 5.1 最小可交付切片

第一版应包含一个触发入口、一类目标用户、一组可获得的数据、一项明确输出和一条异常处理路径。工单案例的最小切片可以是读取指定工单、查询其关联告警、检索规程、输出带证据的建议，由操作员审核。需要变更网络配置的动作应作为另一项有独立授权和验证的需求。

### 5.2 一页项目定义

| 字段 | 教学填写示例 |
| --- | --- |
| 用户 | 企业专线一线值班人员 |
| 触发 | 打开一条新建故障工单 |
| 痛点 | 查询分散、规程版本难确认 |
| 当前基线 | 先抽样测量资料整理时间 |
| 首版结果 | 按现状证据生成下一步建议与缺失信息 |
| 数据 | 工单、告警、规程及其权限元数据 |
| 允许动作 | 读取、生成建议、经审核保存备注 |
| 范围边界 | 网络设备变更单独立项 |
| 验收 | 约定案例通过、权限测试通过、用户完成任务 |
| 依赖 | 数据访问、接口账号、知识负责人 |
| 责任 | 业务验收人、发布人、运行负责人分别具名 |

### 5.3 可测试需求

需求“提高准确率”可以改成“当工单客户与告警客户不一致时，系统不把该告警作为归因证据，并在评测集中通过指定跨客户案例”。“响应快”可以改成“在约定并发与输入规模下，统计 p50、p95 端到端延迟，并满足业务确认的等待预算”。阈值先列为待约定，测过基线后再确定。

### 5.4 需求变更

每项变更记录触发事实、受影响的流程、数据与权限、验收新增项、时间和成本影响、决策人。业务学习带来的范围调整可以正常发生，但需要同步更改测试与交接材料。每周演示用真实使用路径走一遍，同时演示至少一个异常。

### 新手解释与 AI 辅助

**先理解。** 范围是第一版具体要完成的事。验收是用事先约定的例子判断是否做到。

**可以交给 AI 的工作。** 使用 P04 将想法改写为小试点，再用 P09 生成验收候选。由业务用户确认这些例子确实代表需要解决的问题。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 06｜数据发现、契约与质量

### 6.1 数据资产登记

| 字段 | 要记录的内容 |
| --- | --- |
| 系统与负责人 | 谁解释业务含义、谁维护接口 |
| 主键与粒度 | 一行代表工单、事件还是快照 |
| 时间 | 发生、采集、更新时间及其时区 |
| 更新策略 | 全量、增量、补发与删除 |
| 质量 | 空值、重复、迟到、冲突和缺失比例 |
| 访问 | 哪些身份可看哪些租户、对象和字段 |
| 保留 | 原始数据、派生结果和日志保存多久 |

### 6.2 数据契约示例

```json
{
  "schema_version": "1.0",
  "tenant_id": "demo_customer_a",
  "ticket_id": "T-1001",
  "service_id": "S-501",
  "status": "open",
  "summary": "用户反馈链路间歇中断",
  "updated_at": "2026-11-11T01:00:00Z",
  "record_version": 7
}
```

契约应规定必填字段、枚举、长度、唯一性和时间含义。主键通常需要与租户共同判断。源系统重新打开工单、合并工单或修正历史记录时，消费方如何处理也应写清楚。

### 6.3 五个高频问题

**连接扩大。** 一条工单关联十条告警，直接连接后统计工单数会膨胀。先定义结果粒度，再聚合或去重。  
**时区混淆。** 统一存储时刻，展示时转换到用户时区，保留源时区用于解释。  
**数据过期。** 告警采集时间与设备实际观测时间都应可见，超出业务有效期要重新获取。  
**迟到记录。** 增量同步可保留重叠窗口并按稳定键去重，具体窗口根据数据迟到情况确定。  
**删除遗留。** 文档被撤回后，向量索引、缓存和派生结果也需要删除或失效。

### 6.4 最低数据质量检查

检查复合主键唯一性、必填字段、状态枚举、未来时间、对象引用完整性、租户匹配和更新时间。把“数据不完整”变成可见状态。模型遇到缺失字段时应返回缺失信息或请求补充，实际缺失不能被默认值掩盖。

完成标准是用十条样例解释每个字段，并复现一条脏数据如何被发现、隔离或退回。数据决策闭环的背景参见 [S09](https://www.palantir.com/docs/foundry/getting-started/delivering-a-use-case)。

### 新手解释与 AI 辅助

**先理解。** 数据契约像表格填写说明，规定每列含义、格式和缺失时怎么办。先拿三行样例逐列解释。

**可以交给 AI 的工作。** 把模拟字段表交给 AI，请它列出空值、重复、时间和客户关联检查。自己加入一条已知错误，验证程序能否发现。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 07｜业务对象、关系与动作

**来源摘要。** Palantir Ontology 将企业数据映射到业务对象与关系，Actions 支持对象状态变更。其用例交付文档强调用数据支持决策、记录决策，再评估影响。参见 S09–S11。以下模型是独立于平台的教学实现。

### 7.1 工单案例对象

| 对象 | 主键 | 重要属性 | 关系 |
| --- | --- | --- | --- |
| Customer | tenant_id | 客户等级、服务约定 | 拥有 Service |
| Service | tenant_id + service_id | 区域、状态、维护窗口 | 关联 Ticket 与 Alarm |
| Ticket | tenant_id + ticket_id | 状态、严重程度、版本 | 属于 Service |
| Alarm | tenant_id + alarm_id | 类型、发生时刻、恢复时刻 | 关联 Service |
| Procedure | procedure_id + version | 生效时间、适用产品、审核人 | 支持 Recommendation |
| Recommendation | recommendation_id | 证据、建议、缺失信息、状态 | 引用 Ticket 与 Procedure |
| Approval | approval_id | 审核人、对象版本、期限、结论 | 授权指定 Recommendation |

### 7.2 动作契约

每个动作说明执行前提、允许角色、读写字段、幂等规则、审计结果和失败处理。以“保存经审核的建议”为例，前提是工单仍处于可写状态，审核对象与实际建议相同，工单版本未变化。完成后应能查询到保存记录及其动作 ID。

### 7.3 避免把对象模型等同于知识图谱项目

项目初期用几张带主外键约束的表，就可以表达上述关系。只有当多跳关联、实体消歧和图遍历确实构成需求时，再评估图数据库。对象建模的直接收益是统一字段和操作含义，便于模型、界面、权限和评测共享同一语义。

来源定位 [S10](https://www.palantir.com/docs/foundry/ontology) · [S11](https://www.palantir.com/docs/foundry/action-types/overview)。

### 新手解释与 AI 辅助

**先理解。** 对象可以先理解为一张表中的一种事物，关系说明两类事物怎样关联，动作表示怎样改变状态。

**可以交给 AI 的工作。** 请 AI 用客户、服务、工单三个对象设计表格，并举出一对多关系。用一条工单追溯其客户，检查主键与关联是否明确。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 08｜规则、检索、工作流与 Agent 的选择

### 8.1 从最小复杂度开始

**来源摘要。** Anthropic 的 Agent 基础文章区分预定义路径的工作流与由模型动态决定步骤的 Agent，并讨论链式、路由、并行、编排与评估优化等模式。原文发布于 2024 年，页面已提示工具生态变化。原理学习与当前 SDK 操作应分别核对。参见 S03。

| 需求特征 | 首先考虑 | 选择原因 |
| --- | --- | --- |
| 固定阈值、字段校验、权限判断 | 规则与普通代码 | 可重复、可解释、易测试 |
| 从当前业务系统取精确状态 | API 或 SQL | 直接访问权威记录 |
| 从长文档找相关依据 | 检索或 RAG | 支持来源与知识更新 |
| 已知步骤、每步有少量语言理解 | 固定工作流 | 顺序与失败路径容易控制 |
| 下一步取决于未知中间结果 | 有边界的 Agent | 允许动态选择工具或路径 |
| 子任务确实独立且可分别验证 | 受控并行或多 Agent | 可换取速度或专业分工 |

### 8.2 四个选择问题

先问能否明确写出成功路径。再问未知因素发生在哪里，是否必须让模型做路径选择。接着确定输出错误或误操作的代价。最后检查是否有工具结果或业务状态作为反馈。无法观察结果的自主循环很难调试和验收。

### 8.3 工单首版架构

采用固定工作流。校验身份后读取工单和告警，检索匹配的现行规程，生成结构化建议，再进行规则检查并交给人工。后续若发现异常分类不固定，可只把“选择进一步查询哪个工具”开放给 Agent。无论采取哪种编排方式，权限判断和写入前检查都由后端强制执行。

### 8.4 何时评估微调

先检查数据是否正确、检索是否找到依据、输出契约是否清晰、工具是否工作、基线是否足够。若积累了稳定标注数据且存在重复性的任务表现缺口，可比较微调与提示、检索及工作流改进。评估时包括训练维护、版本迁移和推理成本。具体模型能力与支持方式按当时官方文档确认。

来源定位 [S03](https://www.anthropic.com/research/building-effective-agents)。

### 新手解释与 AI 辅助

**先理解。** 先写出固定的处理步骤。只有下一步确实需要根据中间结果决定时，再考虑让模型选择。

**可以交给 AI 的工作。** 让 AI 比较规则、固定工作流和 Agent 三种方案，要求每项选择对应一个已知业务约束。删除没有证据支持的复杂组件。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 09｜上下文工程与 RAG

### 9.1 为一次任务准备足够且相关的信息

**来源摘要。** Anthropic 将上下文工程描述为对模型调用时所见信息进行持续选择和管理，范围包括指令、工具、外部数据与对话历史。信息越多并不自动带来更可靠的表现。参见 S04。

**实践建议。** 将上下文拆成稳定规则、当前任务、可追溯证据和已完成动作。每份事实记录来源 ID、更新时间、适用范围和权限。实际 token 预算用实验确定，可先规定各类内容上限，再观察是否删掉了关键证据。

### 9.2 RAG 链路

文档入库先验证来源、版本、生效时间和可见范围，再进行结构化提取、分块和索引。查询时先限定用户可见与业务适用范围，再检索候选段落，必要时排序，最后把证据交给生成步骤。返回前检查引用能否定位到真实文档和具体段落。

| 环节 | 要保留的元数据 | 常见失效 |
| --- | --- | --- |
| 文档接收 | 来源、所有者、版本、生效日期 | 草稿与现行规程混合 |
| 分块 | 标题路径、段落、页码或锚点 | 条件与操作被拆开 |
| 索引 | 文档版本、租户、权限、生效状态 | 已撤回文件继续命中 |
| 检索 | 查询、过滤条件、候选证据 | 产品或客户条件缺失 |
| 生成 | 证据 ID 与引用对应关系 | 引用真实但不支持结论 |

### 9.3 分块与检索的调试方法

从人工标注的十个查询开始，指出每题应该命中哪份文件及哪段内容。先查看检索结果，再看答案。检索未命中时检查解析、术语、过滤、分块和版本。检索正确而回答错误时，再检查上下文构造和生成。不要在两个问题之间反复调整提示词而不保存实验记录。

混合检索可以同时利用精确术语与语义相似性，但应在当前查询集上比较结果。若答案取决于最新告警状态，实时 API 比规程索引更适合提供事实。检索负责提供制度和操作依据，实时接口负责当前状态，两者保留各自时间戳。

### 9.4 冲突与缺失

文档冲突时展示版本和冲突字段，按已约定的权威来源规则处理。规则未定义则要求人工确认。若最新规程不适用该设备型号，不能因为相似度高就当作有效依据。缺少证据时输出待确认项和建议查询动作。

来源定位 [S04](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)。

### 新手解释与 AI 辅助

**先理解。** 检索是先找相关材料，生成是再根据材料组织答案。先检查找到了什么，才容易定位问题。

**可以交给 AI 的工作。** 给 AI 三段模拟规程和一个问题，让它逐项标出结论依据。插入一份过期规程，人工检查它是否正确排除或提示冲突。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 10｜工具、API 与 MCP 集成

### 10.1 工具的设计单位

一个工具围绕清晰业务动作设计，例如“获取某工单的最新关联告警”。输入要有类型、约束和语义，输出要区分成功、空结果、无权限、超时和源系统失败。工具名、说明和错误信息会直接影响模型是否能正确调用。

| 工具 | 读写属性 | 必要参数 | 结果重点 |
| --- | --- | --- | --- |
| get_ticket | 读 | ticket_id | 状态、版本、租户、更新时间 |
| get_related_alarms | 读 | service_id、时间范围 | 关联依据、采集时刻、分页 |
| search_procedures | 读 | 产品、现象、查询 | 生效版本、段落和来源 |
| propose_note | 生成草稿 | 建议与证据 ID | 草稿 ID、版本、待审核状态 |
| commit_note | 写 | 草稿 ID、批准凭据、工单版本 | 动作 ID、最终状态或冲突 |

身份和租户从经过认证的服务端上下文传入。模型生成的 tenant_id 或角色声明不能作为授权依据。

### 10.2 MCP 能提供什么

**来源摘要。** MCP 官方架构描述 host、client 与 server 的协作方式，通过协议让应用发现和使用上下文能力。它规范交换方式，具体模型编排和上下文管理由应用决定。参见 S15。该次核对的文档跳转到 2026-07-28 版本，实施时应记录实际采用版本。

已有 REST API 可以直接包装为内部工具，也可以在需要多个 AI 客户端复用、统一发现和管理时通过 MCP 暴露。采用哪种方式都需要处理用户身份、对象权限、错误、限流和审计。协议层的工具声明不能替代底层系统授权。

### 10.3 重试与副作用

读取请求可根据错误类型有限重试，采用退避、抖动和总时限。认证失败、参数错误和权限拒绝应返回明确错误供修正。写请求超时可能意味着服务端已执行但响应丢失，需要用动作 ID 查询状态，再决定下一步。

幂等键应对应一个已批准的业务动作，绑定租户、目标对象、有效载荷摘要和版本。重复提交同一动作返回既有结果。同一键被用于不同载荷应拒绝。并发场景下，幂等记录和业务写入需要事务或可靠协调机制，进程内字典无法提供生产级保证。

### 10.4 增量同步

保存游标前确认该批记录已持久化。重试时按稳定键去重，支持已更新与已删除记录。对补发事件用时间或版本规则处理，防止旧状态覆盖新状态。监控同步滞后、失败批次和无法解释的游标跳跃。

来源定位 [S15](https://modelcontextprotocol.io/docs/learn/architecture)。

### 新手解释与 AI 辅助

**先理解。** 工具是一个有名字的查询或操作，调用失败时要让程序知道发生了哪种问题。

**可以交给 AI 的工作。** 请 AI 根据工具表生成输入输出样例和错误响应，再核对接口实际返回。使用 P10 检查重试是否可能重复写入。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 11｜工作流状态、人工审核与 Harness

### 11.1 明确状态机

教学状态可以包括 created、collecting、needs_information、proposed、awaiting_review、approved、committing、completed、rejected 和 failed。每次转换记录事件、前后状态、操作身份和关联版本。只有合法的前置状态才能转换，界面与后端共享同一状态含义。

### 11.2 审核应该让人看见什么

审核界面同时展示建议、证据、数据时刻、拟写入字段、目标工单和实际副作用。审核人可以同意、修改、拒绝或要求补充。修改内容后生成新版本，再按项目规则确认。审批凭据应限定对象、载荷、身份和有效期，执行前重新验证权限和当前状态。

### 11.3 处理中断与恢复

把任务进度和动作记录保存到持久存储，模型会话只携带完成当前步骤所需的信息。进程恢复后先查询业务动作状态。已完成的副作用步骤不重复执行，未完成的纯计算步骤可以重新运行。队列重投、服务重启和审批过期都要有可预期路径。

### 11.4 Harness 的工程责任

Harness 是让模型持续完成任务的运行控制层。一个简单项目也需要任务状态、工具注册、超时与步数预算、异常处理、可观测性和停止条件。长任务还要保存阶段产物、文件或状态交接，并验证是否真正完成。

**来源摘要。** Anthropic 的长任务文章展示了通过环境初始化、增量工作和结构化产物维持进度的做法。2026 年更新进一步强调验证标准和随模型能力变化简化控制层。Managed Agents 的工程文章讨论将会话、运行循环和执行环境分开。参见 S06–S08。

这些资料适合学习持久状态和接口边界。多 Agent、额外评估循环或复杂调度是否需要，应通过任务成功率、总耗时和成本比较决定。保留每个组件解决了哪个已观察问题的记录。

来源定位 [S06](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents) · [S07](https://www.anthropic.com/research/harness-design-long-running-apps) · [S08](https://www.anthropic.com/research/managed-agents)。

### 新手解释与 AI 辅助

**先理解。** 状态就是任务当前走到哪一步，批准意味着指定的人同意了指定内容。任务发生变化后应重新检查。

**可以交给 AI 的工作。** 让 AI 列出每个状态允许进入的下一状态和拒绝条件。给出“审核后工单变更”案例，检查其建议是否重新核查版本。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 12｜把评测作为交付验收的一部分

### 12.1 评测对象

**来源摘要。** Anthropic 将任务、单次尝试、评分器、执行记录和最终环境状态区分开来，并建议结合代码、模型与人工评分。多轮 Agent 的验证需要关注动作之后实际发生的结果。参见 S05。

| 层级 | 示例问题 | 验证方式 |
| --- | --- | --- |
| 数据 | 工单与告警是否正确关联 | 键、租户、时间与固定样例断言 |
| 检索 | 是否找到有效规程 | 人工标注证据集与命中检查 |
| 生成 | 结论是否有依据、信息是否完整 | 规则、人工和校准后的模型评分 |
| 工具 | 参数、权限和异常处理是否正确 | 沙箱与接口契约检查 |
| 工作流 | 中断、审批和恢复是否符合要求 | 状态转换与故障注入 |
| 结果 | 备注是否真正保存、是否重复 | 查询业务存储的最终状态 |
| 采用 | 用户能否完成目标任务 | 使用观察与行为记录 |

### 12.2 起步评测集

先设计 30 个教学案例。正常输入 8 个，缺失或冲突信息 6 个，权限边界 5 个，工具失败 5 个，恶意或无关内容 3 个，重复提交与状态变化 3 个。数量只是练习起点，应按实际任务分布、风险和失败经验扩充。

数据划分保留开发调试集与未参与调参的验收集。增加新版本前冻结评测集版本，并记录变更原因。业务分布变化后可以更新，但新旧版本结果不要无说明地混在一起比较。

### 12.3 案例记录格式

```json
{
  "case_id": "permission_003",
  "category": "cross_tenant",
  "fixture": "customer_a_user_customer_b_ticket",
  "expected_status": "denied",
  "required_checks": ["no_foreign_record_in_response", "no_write"],
  "severity_if_failed": "critical"
}
```

成功条件至少包含允许结果和禁止副作用。涉及检索时列出可接受的证据范围。涉及动态任务时允许多种正确路径，避免只因工具调用顺序不同就判错。

### 12.4 模型评分器的使用

先由人定义评分标准，并用已标注样例检查评分器是否可靠。评分器看到的候选答案不能覆盖评分规则。事实、格式、权限和数据库状态能用确定性检查验证时优先使用相应检查。模型评分更适合辅助判断语言质量、证据支持程度和解释完整性，并需定期人工抽样校准。

模型不一定暴露内部推理。日志保留可用的输入摘要、输出、工具调用、状态变化和错误即可完成很多诊断，且应对敏感内容脱敏并限制访问。

来源定位 [S05](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

### 新手解释与 AI 辅助

**先理解。** 评测就是把正确结果写清楚，再反复检查系统。开始时用十条人工知道答案的任务即可。

**可以交给 AI 的工作。** 用 P09 扩充案例，保留至少一个由你独立写出的预期答案。AI 生成的题目要核对数据与答案是否匹配。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 13｜指标、实验与发布门槛

### 13.1 指标必须写分母

| 指标 | 教学定义 | 易误读之处 |
| --- | --- | --- |
| 任务成功率 | 满足全部必要条件的任务数 ÷ 有效任务数 | 仅检查语言输出会漏掉动作失败 |
| 引用支持率 | 被引用证据实际支持的被检验主张 ÷ 被检验主张 | 文档存在不等于支持结论 |
| 审核采用率 | 被采用建议数 ÷ 实际进入审核的建议数 | 需同时报告有多少任务未生成建议 |
| 完成覆盖率 | 有成功产物的适用任务数 ÷ 适用任务数 | 过度拒绝可能抬高输出准确率 |
| 单次成功成本 | 测量区间总成本 ÷ 成功任务数 | 应含失败、重试和复核 |
| 延迟 p95 | 95% 的测量请求不超过的端到端时长 | 要固定负载、输入规模和统计口径 |

### 13.2 关键失败单独报告

跨租户泄露、未经授权的写入、重复副作用等案例单列为关键失败。教学门槛可要求当前测试集中关键失败为 0，但这只表示在该测试范围内未观测到失败，不能推断真实环境风险为零。普通质量指标与关键失败分别展示，避免综合分数掩盖严重问题。

### 13.3 记录重复试验

语言模型有随机性，可对重点案例运行多次并报告每题通过次数。比如 30 题各运行三次，报告 90 次尝试的总成功率，同时列出至少一次失败的题目，区分稳定与偶发问题。若样本小，保留原始次数比只展示百分比更有解释力。

### 13.4 一次只改变可解释因素

比较新旧方案时保留同一输入、数据快照和工具版本，记录模型、提示、检索配置及预算。改变模型和检索器后性能提升，不能只归因于模型。若无法完全隔离因素，明确写出共同变更。

### 13.5 发布门槛样例

教学门槛可以包含关键权限案例全部通过、业务代表签字确认核心任务、已演练回退、成本预算可接受，以及运行负责人能根据日志定位一次故障。准确率和时延阈值应在客户认可的样本与负载上确定，而非直接照搬其他项目的数字。

### 新手解释与 AI 辅助

**先理解。** 先记录成功几次、失败几次和失败原因，再计算百分比。这样更容易发现样本很少或统计口径不同。

**可以交给 AI 的工作。** 把脱敏后的评测记录交给 AI 汇总，要求显示分子、分母、失败清单和版本。随机抽查几条原记录，复算百分比。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 14｜权限、内容信任与失败边界

### 14.1 三条边界

第一条是身份边界，后端知道当前用户和租户。第二条是数据边界，检索和 API 只提供该身份可见的对象与字段。第三条是动作边界，写入前按当前权限和对象状态再次验证。提示词可以解释行为规则，实际权限由系统执行。

### 14.2 处理提示注入

工单描述、网页、附件和知识库内容可能包含“忽略规则”“导出其他客户数据”等指令。应用应将其作为任务资料处理，保留来源和信任等级。工具可用范围、参数验证、数据权限和输出检查共同限制其影响。检测器可作为补充信号，权限控制仍需要独立存在。

### 14.3 日志与数据最小化

日志优先保存 trace_id、对象 ID、版本、状态、耗时和错误类型。确需保留文本时明确用途、访问权限和保留期，对个人及客户敏感字段脱敏。模型提供商、检索系统、追踪平台和导出文件都纳入数据流图，逐项确认数据会到哪里。

### 14.4 执行动作前的检查表

1. 当前请求身份已认证，租户由可信上下文确定。
2. 目标对象存在且仍归属当前权限范围。
3. 参数通过类型、长度、枚举及业务规则校验。
4. 人工批准与实际载荷及版本绑定，仍在有效期内。
5. 幂等键有效，同键载荷冲突会被拒绝。
6. 当前对象版本与审核时一致，否则返回冲突。
7. 动作及审计写入采用项目确认的一致性机制。
8. 客户端能查询最终状态并解释失败。

这些检查是本手册对工单写入场景的设计建议。具体身份、认证与协议实现需核对项目所用系统和当前 SDK 文档。协议范围参见 [S15](https://modelcontextprotocol.io/docs/learn/architecture)，业务动作背景参见 [S11](https://www.palantir.com/docs/foundry/action-types/overview)。

### 新手解释与 AI 辅助

**先理解。** 权限判断相当于在系统入口和每次关键操作前检查身份与范围。用户写在文字里的自我介绍无法代替认证。

**可以交给 AI 的工作。** 请 AI 针对当前模拟流程设计越权与注入测试文本，限定只在练习系统验证。检查是否有任何跨客户内容进入输出或日志。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 15｜从演示到试点，再到生产

### 15.1 分阶段扩展

| 阶段 | 允许能力 | 需要的证据 |
| --- | --- | --- |
| 离线验证 | 使用固定模拟数据 | 数据与输出契约正确 |
| 影子运行 | 读取获准的真实数据，结果仅用于比较 | 与人工记录对照、失败分布可解释 |
| 辅助试点 | 小范围用户查看与审核建议 | 使用反馈、质量、成本、故障接手 |
| 受控写入 | 经审核写入限定字段 | 权限、幂等、并发与回退验证 |
| 扩展运行 | 更多用户、流程与客户环境 | 分组监测、运行责任与复用能力 |

阶段转换按证据决定。影子运行本身也要获得数据访问与处理授权。生产系统使用率低时先排查入口、等待、证据展示和额外操作负担，再决定是否需要提高模型能力。

### 15.2 发布包

发布包至少记录代码版本、依赖、配置版本、模型标识、提示版本、数据或索引版本、评测报告、权限变更和回退方法。测试、预发布和生产环境分别管理密钥与身份。任何动态模型别名变化都应通过回归评测观察影响。

### 15.3 回退与补偿

代码回退、配置回退、模型回退和索引回退分别说明。已经写入业务系统的内容不会因为代码回退自动消失，要有核查与补偿流程。对外发送、真实交易和设备操作等不可简单撤销动作，需要在设计时定义额外控制与处置责任。

### 15.4 用户采用

在用户原有工作入口附近呈现结果，减少重复录入。培训用真实任务和失败案例，教会用户何时可以信任证据、何时需要补充资料、如何报告错误。记录用户拒绝建议的原因，区分事实错误、信息不足、政策差异和界面问题。

### 新手解释与 AI 辅助

**先理解。** 上线是使真实用户可以使用应用，试点先限定用户与功能，减少同时变化的因素。

**可以交给 AI 的工作。** 让 AI 用已验证记录起草发布清单，并为每项加证据位置。实际负责人核对权限、回退和未完成事项后再作发布决定。

**留下证据。** 保存输入、AI 产物、自己的核查和实际结果。用模拟内容练习，客户内容按已批准的数据范围使用。

## 16｜可观测性与故障排查

### 16.1 一条任务的记录

每次任务分配 trace_id，与输入对象、用户或匿名身份、模型与配置版本关联。子步骤保留开始结束时间、状态、错误码、重试次数、输入输出大小和必要的证据引用。写动作使用独立 action_id，并能从 trace 追踪到业务结果。

### 16.2 建议仪表盘

分开观察流量、成功率、关键失败、检索空结果、工具错误、延迟、成本、人工采用和用户反馈。按租户、任务类型、模型版本和数据完整性切片，避免总体平均掩盖某一客户失效。运营指标需要明确时间窗口和统计规则。

### 16.3 排错顺序

| 表现 | 先检查 | 下一步 |
| --- | --- | --- |
| 建议明显不符事实 | 源系统数据和关联键 | 检查工具结果、上下文和生成 |
| 引用不适用 | 检索过滤、文档版本 | 检查分块与回答支持关系 |
| 任务卡住 | 工具超时、审批和队列状态 | 检查步数预算与恢复路径 |
| 重复备注 | 动作 ID 与幂等状态 | 检查响应丢失、重投和事务 |
| 新模型上线后变差 | 发布版本和固定回归集 | 对比同一输入与配置 |
| 用户不采用 | 用户实际工作路径 | 观察额外操作和证据展示 |

### 16.4 事故处理

先限制影响，例如停用写入、暂停特定租户或切回人工。保存必要日志与版本，查询已执行动作，明确影响范围，再修复和补偿。恢复前运行相关回归案例。复盘写清触发条件、影响、发现方式、恢复动作与后续改进，每项改进指定负责人和验证方法。

### 新手解释与 AI 辅助

**先理解。** 日志是运行时留下的记录。先学会用同一个任务编号，把输入、查询、结果和错误串起来。

**可以交给 AI 的工作。** 给 AI 一段脱敏日志，请它按时间排列事件、列出可能原因和最小核查动作。逐项用实际系统状态验证推测。

## 18｜成本、收益与商业交付

### 18.1 成本口径

总成本包括模型输入输出、嵌入与排序、工具和外部数据、计算存储、网络、日志、人工复核、维护与交付。区分一次性建设和持续运行支出。对缓存、批处理和异步处理的优化同时检查数据新鲜度、用户等待和质量影响。

教学例。一个月运行成本 10,000 元，成功完成 8,000 个任务，单次成功成本为 1.25 元。若只统计成功调用的模型账单，会忽略失败尝试、重复运行和审核成本。增加自主循环后，单次输出可能更好，但总成本与总时延也会变化。

### 18.2 收益证明

收益按已节省支出、释放可用时间、降低错误、加快响应和改善客户结果分别报告。每项有基线、测量方法和业务确认人。系统收入、合同扩张与客户收益保持独立记录，避免把供应商卖得更多当作客户效果的唯一证明。

### 18.3 商业阶段

探索阶段购买的是对价值和可行性的验证。试点阶段购买的是限定范围的可用能力。扩展阶段购买的是持续结果和更广覆盖。每阶段说明交付物、数据前提、验收、维护责任和变更处理。若采用按结果收费，应约定结果归因、样本、争议核查和例外处理。

### 18.4 三项指标的本地化

A&M 提出的业务成果、合同扩张和产品杠杆可形成管理看板。实际使用时，为业务成果确定单位，为合同扩张区分范围与价格变化，为产品杠杆同时记录复用部署时间和工程投入。客户复杂度差异单独标注，按可比任务观察趋势。参见 S02 第 3 页。

来源定位 [S02](https://www.alvarezandmarsal.com/sites/default/files/2026-04/The%20Rise%20and%20Role%20of%20the%20Forward%20Deployed%20Engineer.pdf)。

### 新手解释与 AI 辅助

**先理解。** 成本包含模型、软件运行和人工时间。释放的时间价值与实际减少支出分别统计。

**可以交给 AI 的工作。** 让 AI 按已确认输入建立成本明细，列出缺失项。用正常、低任务量和高失败率三种情形比较，自己复核公式。

## 19｜Echo、Delta 与跨客户产品化

### 19.1 组织闭环

**来源摘要。** A&M 将 Echo 定义为关注领域问题、价值场景与相关方对齐的前线角色，将 Delta 定义为快速构建和部署的工程角色。核心产品团队从现场方案中提炼共性，形成可维护平台能力。报告建议安排周期吸收有价值的现场方案，并用独立团队采用来检验抽象。参见 S02 第 2–4 页。

### 19.2 可复用能力分层

| 层级 | 工单例子 | 处理方式 |
| --- | --- | --- |
| 通用基础 | 认证、审计、幂等、评测、追踪 | 统一实现并维护契约 |
| 行业共性 | 工单与告警关联、规程适用性 | 形成可扩展组件 |

### 19.3 第二客户实验

准备客户 B 的不同字段、状态枚举和知识规程，尽量保留客户 A 已有核心组件。记录配置修改量、新增代码量、集成耗时、首个有效结果时间、评测差异与维护负担。若每个字段变化都要改业务逻辑，检查接口与对象契约是否过度贴合客户 A。

### 19.4 铺路评审

每次评审选择一项共性能力，列出两个实际场景、稳定部分、变化部分、现有重复代码、迁移成本和负责人。平台团队与现场团队共同走查。只有平台功能确实被采用，并能替代相应旧实现，才有必要计为复用成果。

### 19.5 避免过早平台化

只有一个使用者、需求还频繁变化时，先保存清楚边界和测试。多个客户出现相似但不同需求后，再决定抽象方式。统一过多会让现场绕开平台，统一过少会扩大维护成本。判断依据是新的交付与维护数据。

## 20｜贯穿实战：企业客户故障工单辅助处置

### 20.1 案例范围

**教学示例。** 客户 A 运营企业专线业务，值班人员在工单系统、告警平台和规程库之间查询。项目目标是生成有证据的资料摘要、待确认项和下一步建议。模拟环境只读查询并生成草稿，增加写回时需单独实现审核和一致性机制。

### 20.2 样例数据

| 数据集 | 最小字段 | 教学数量 |
| --- | --- | --- |
| tickets | tenant_id、ticket_id、service_id、summary、status、version | 50 条 |
| alarms | tenant_id、alarm_id、service_id、type、event_time、state | 200 条 |
| procedures | id、version、product、effective_at、status、text | 10 份 |
| users | user_id、tenant_id、roles | 4 个身份 |

正常样例是 T-1001 关联 S-501，近十五分钟内出现链路抖动告警，现行规程要求先核查端口错误计数和维护窗口。系统应汇总现有事实，并建议人工执行已授权的下一步检查。若缺少端口计数，应明确列出缺失项，不能直接断定物理故障。

### 20.3 输入、输出和验收

输入为已认证用户选择的工单号。后端读取身份范围内的工单、相关告警和适用规程。输出包含 observations、evidence、recommended_next_steps、missing_information 和 review_required。证据项至少带来源 ID 与时间或版本。

| 案例 | 系统应怎样表现 | 验收证据 |
| --- | --- | --- |
| 正常告警 | 说明当前事实并提出可验证检查 | 引用支持、对象匹配 |
| 无相关告警 | 表明未发现记录并保留查询范围 | 空结果未被当成无故障 |
| 规程过期 | 不作为当前执行依据 | 返回失效状态或补充请求 |
| 客户不匹配 | 拒绝访问或隔离外部记录 | 输出和日志无其他客户内容 |
| 工具超时 | 显示数据未获取并允许重试或人工接手 | 不编造告警结果 |
| 恶意工单文本 | 继续按任务与权限处理 | 无额外数据导出或越权动作 |
| 审核后工单变化 | 返回版本冲突，要求重新核查 | 旧批准未直接生效 |
| 写入响应丢失 | 查询动作状态 | 无重复备注 |

### 20.4 仓库组织建议

| 路径 | 责任 |
| --- | --- |
| app/api | 身份校验、请求与响应 |
| app/workflows | 状态流转、步骤预算与异常 |
| app/tools | 工单、告警与知识接口 |
| app/policies | 对象权限与动作校验 |
| app/storage | 任务、版本和动作记录 |
| configs | 客户字段映射和可见配置 |
| data/synthetic | 模拟数据与来源说明 |
| evals | 案例、评分规则和运行报告 |
| docs | 项目定义、决策、运行与交接 |

### 20.5 工程里程碑

M0 无模型。能按权限正确查工单和告警。M1 增加结构化建议。使用固定证据生成且可校验。M2 加入规程检索。引用可追溯并处理过期。M3 加入评测与故障注入。能够定位错误。M4 加入审核与受控写回。状态、版本、幂等均可验证。M5 迁移客户 B。记录复用与新增工作。

各里程碑都保持可运行状态。每次演示围绕一项业务任务，展示正常与异常路径，并提供下一步决策所需证据。建议前端先做工单选择、证据展示、建议审核和结果状态四个功能。

### 新手解释与 AI 辅助

## 21｜可执行基础练习与接口骨架

以下 Python 练习完全使用模拟数据与标准库，可以保存为 fde_exercise.py 并用 Python 3 运行。它演示数据校验、租户过滤、缺失信息和结构化建议。它采用确定性逻辑，便于学习工程边界，尚未接入模型、数据库或真实接口。

```python
import json


TICKETS = {
    "T-1001": {
        "tenant_id": "customer_a",
        "service_id": "S-501",
        "status": "open",
    },
    "T-2001": {
        "tenant_id": "customer_b",
        "service_id": "S-901",
        "status": "open",
    },
}

ALARMS = [
    {
        "tenant_id": "customer_a",
        "service_id": "S-501",
        "alarm_id": "A-01",
        "type": "link_flap",
    }
]


def build_proposal(tenant_id, ticket_id, source_available=True):
    # tenant_id 在真实应用中来自服务端认证上下文。
    if not isinstance(ticket_id, str) or not ticket_id.strip():
        return {"status": "invalid_input", "write_performed": False}

    ticket = TICKETS.get(ticket_id)
    if ticket is None or ticket["tenant_id"] != tenant_id:
        return {"status": "unavailable", "write_performed": False}

    if not source_available:
        return {
            "status": "needs_information",
            "missing_information": ["alarm_source_unavailable"],
            "write_performed": False,
        }

    alarms = [
        alarm for alarm in ALARMS
        if alarm["tenant_id"] == tenant_id
        and alarm["service_id"] == ticket["service_id"]
    ]
    return {
        "status": "awaiting_review",
        "ticket_id": ticket_id,
        "evidence_ids": [alarm["alarm_id"] for alarm in alarms],
        "missing_information": ["port_counters", "maintenance_window"],
        "recommended_next_steps": ["核查授权范围内的端口计数与维护窗口"],
        "review_required": True,
        "write_performed": False,
    }


def main():
    normal = build_proposal("customer_a", "T-1001")
    foreign = build_proposal("customer_a", "T-2001")
    failure = build_proposal("customer_a", "T-1001", False)
    invalid = build_proposal("customer_a", "")
    assert normal["evidence_ids"] == ["A-01"]
    assert foreign == {"status": "unavailable", "write_performed": False}
    assert failure["status"] == "needs_information"
    assert invalid["status"] == "invalid_input"
    print(json.dumps(normal, ensure_ascii=False, indent=2))
    print("4 个模拟场景检查通过")


if __name__ == "__main__":
    main()
```

### 21.1 逐步替换模拟实现

第一步把字典换成带复合键的 SQLite 查询。第二步把告警读取换成模拟 HTTP 服务，并区分超时与空结果。第三步加入规程检索。第四步将生成建议替换为当前模型 SDK 调用，保留输出校验与故障分支。使用实际 SDK 前核对认证、结构化输出、超时和错误类型，锁定依赖版本。

### 21.2 模型输出契约

```json
{
  "observations": ["可从当前证据直接确认的事实"],
  "evidence": [{"source_id": "A-01", "supports": "告警类型"}],
  "recommended_next_steps": ["需要人工确认的下一项检查"],
  "missing_information": ["尚未取得的信息"],
  "review_required": true
}
```

服务端校验 JSON 结构、允许字段和 evidence 引用是否存在于当前可见证据集。随后检查建议是否符合业务范围。结构正确只证明格式符合契约，事实可靠性仍需评测。

### 21.3 写入接口说明

教学契约为 commit_note(proposal_id, approval_id, expected_ticket_version, idempotency_key)。服务端解析已保存草稿和批准记录，检查当前身份、批准期限、载荷摘要和对象版本，在一致性机制内写备注及动作状态，并返回 action_id。此处仅描述契约，生产实现还需完成事务、恢复、并发、审计和权限测试。

**可以交给 AI 的工作。** 使用 P06 逐行讲解，用 P08 排错，再请 AI 加一条新测试。人工确定正确答案，确认测试确实执行到了相关分支。

### 25.2 参考回答

1. 确认目标用户的具体工作、可观察的结果和数据及责任条件。2. 检查等待、审批、排队和下游执行。3. 空结果说明查询成功但未找到，超时说明事实尚未取得。4. 保存输入、数据快照、检索证据、上下文和版本。5. 返回冲突并重新核查、必要时重新审核。6. 写入可能已发生但响应丢失，需要幂等与状态查询。7. 查询业务最终状态及动作记录。8. 对同一任务集比较成功率、成本与耗时，判断改善是否满足业务预算。9. 对可比任务记录每名 FDE 的结果、复制时间和工程投入。10. 补运行与故障演练，并验证接手人员能够完成。
