743 个 Hacker News 点赞、310 条评论。DeepSeek Harness 引发关注，表面上是在讨论一个开源 Agent 工具，背后争夺的却是 AI 产业下一层更重要的控制权：

**当模型可以随时替换，谁来控制上下文、工具、权限与执行循环？**

过去两年，行业竞争的焦点集中在参数规模、推理能力、基准成绩和 API 价格。如今开发者逐渐发现，模型只是 Agent 系统的一部分。

如果把模型比作发动机，那么 Harness 才是整辆车：它决定信息如何进入模型，模型能调用哪些工具，可以修改什么文件，失败后是否重试，以及一个任务究竟怎样从“生成答案”变成“完成工作”。

真正锁住用户的，可能从来不是模型权重，而是发动机周围那套越来越复杂的驾驶系统。

## Harness 究竟是什么？

“Harness”原意是马具或安全束带。在 Agent 语境里，它指的是把模型约束、组织并连接到真实工作环境的系统层。

一个成熟的 Agent Harness，至少包含：

- 上下文收集与压缩；
- 提示词和系统指令管理；
- 文件、终端、浏览器等工具接口；
- 权限申请与安全沙箱；
- 任务规划和执行循环；
- 错误恢复与结果验证；
- 会话状态和长期记忆；
- 模型路由、成本与延迟控制。

用户看到的可能只是一个对话框，背后发生的却是一套持续循环：

    理解任务 → 收集上下文 → 选择工具 → 执行动作
        ↑                              ↓
    验证结果 ← 修正计划 ← 处理错误 ← 读取反馈

模型负责在循环中进行判断，Harness 则决定这个循环是否可靠。

这也是为什么同一个模型接入不同编码工具，体验可能截然不同。差异未必来自智力，而可能来自搜索策略、上下文组织、补丁机制、权限设计和测试反馈。

**模型决定 Agent 能想到什么，Harness 决定它能做成什么。**

## 开源模型之后，轮到开源工作流

DeepSeek 所代表的第一轮冲击，是用开放权重和低成本推理降低模型门槛。开发者可以私有部署、微调模型，或者在不同供应商之间切换。

但这并没有自动带来自由。

当用户把代码仓库索引、项目规则、工具配置、历史会话和权限策略全部交给某个闭源编码助手后，即使底层模型能够更换，工作流也未必能够迁移。

新的锁定不再表现为“你只能调用我的模型”，而是：

- 你的项目上下文储存在我的格式里；
- 你的工具只能通过我的接口调用；
- 你的权限规则依赖我的产品；
- 你的执行记录无法完整导出；
- 你的团队流程围绕我的 Agent 建立。

这是一种比 API 锁定更深的行为锁定。

更换模型可能只需要改一行配置；更换 Harness，却可能意味着重新配置整个开发环境，重新建立安全边界，并让团队重新学习如何与 Agent 协作。

因此，DeepSeek Harness 真正值得关注的地方，不只是它能否驱动某个模型，而是它是否试图把 Agent 的“身体”也变成开放基础设施。

## 它能削弱 Claude Code 和 Codex 的护城河吗？

答案是：**可以削弱，但短期内很难抹平。**

闭源编码助手的护城河并不只是模型能力。它们的优势往往来自大量不显眼但决定体验的工程细节：

- 如何选择需要读取的文件；
- 如何避免上下文被无关代码淹没；
- 如何生成可安全应用的修改；
- 如何判断命令是否具有破坏性；
- 如何处理长任务中的中断和恢复；
- 如何验证修改确实解决了问题；
- 如何在人类介入和自主执行之间切换。

这些能力很难通过展示几个成功案例来证明。Agent 最大的挑战并不是偶尔做对一次，而是在数百次工具调用中持续不犯致命错误。

开源 Harness 的优势则在另一边。

用户可以检查它发送了什么上下文，修改执行策略，替换模型，自行增加工具，并把系统部署在受控环境中。对于金融、政府、工业研发和大型企业，这种可审计性可能比默认体验更重要。

两种路线由此形成不同的竞争结构：

| 维度 | 闭源编码助手 | 开源 Harness |
|---|---|---|
| 初始体验 | 通常更完整 | 依赖配置和集成 |
| 模型选择 | 受平台策略约束 | 可以灵活替换 |
| 执行策略 | 由厂商优化 | 用户可以修改 |
| 数据控制 | 依赖服务条款 | 可本地化部署 |
| 安全责任 | 厂商承担一部分 | 更多转移给部署者 |
| 迁移成本 | 使用越深越高 | 理论较低，实际取决于标准化 |

开放可以拆掉黑箱，但不会自动带来可靠性。闭源可以提供更好的默认设置，却可能让用户失去对关键工作流的控制。

所以竞争不会简单变成“开源打败闭源”，而更可能变成：

**闭源产品出售完成度，开源 Harness 出售控制权。**

## 模型可替换，不代表系统真正可移植

“支持多个模型”很容易成为开源 Agent 的宣传卖点，但模型可替换只是最低层的兼容。

不同模型的工具调用能力、上下文长度、提示敏感性、推理速度和错误模式并不相同。为一种模型设计的执行循环，换上另一种模型后可能立即失效。

例如，有的模型善于先规划再执行；有的模型在获得即时工具反馈时表现更好；有的模型能够稳定生成结构化调用；有的模型则需要额外的解析与纠错。一个 Harness 如果只是把模型名称做成配置项，却没有处理这些行为差异，所谓“可替换”就只是接口层兼容。

真正的可移植性至少需要三层解耦：

1. **模型层解耦**：统一消息、工具调用和响应格式；
2. **工作流解耦**：允许针对不同模型配置执行策略；
3. **状态层解耦**：上下文、权限、记录和项目规则可以导出迁移。

缺少第三层，用户仍然会被锁定，只是从模型厂商转移到了 Harness 平台。

这提醒我们：开源不是锁定的反义词，**可迁移才是。**

## 权限系统可能成为下一代围墙

Agent 与普通聊天机器人最大的不同，是它能够行动。

它可以读取代码、执行命令、安装依赖、访问网络、修改配置，甚至接触部署环境和企业数据。能力越强，权限设计就越重要。

一个 Agent 是否可靠，不只看它能完成多少任务，还要看它在出错时最多能破坏什么。

因此，未来 Harness 的核心竞争力很可能不再是“接入了多少工具”，而是能否回答以下问题：

- Agent 为什么需要这项权限？
- 权限是单次、限时还是永久授予？
- 能否限制到特定文件、域名或命令？
- 高风险操作是否必须由用户确认？
- 执行记录能否完整审计？
- 工具返回的内容是否可能诱导 Agent 越权？
- 多个 Agent 之间如何隔离身份与凭据？

这看起来是安全问题，实际上也是产品锁定问题。

一旦团队围绕某个平台建立了细粒度权限、审批流程、凭据管理和审计规则，迁移成本会非常高。届时，即使所有模型都已商品化，权限系统仍可能构成新的封闭生态。

换句话说，模型时代的锁定发生在 API，Agent 时代的锁定可能发生在身份与权限层。

## 开放 Harness 也会放大安全责任

开源让代码可检查，却不能保证部署安全。

相反，它可能让使用者第一次直接面对闭源产品替他们处理的问题：命令注入、提示注入、凭据泄露、依赖投毒、路径越界以及高风险操作失控。

尤其是在 Agent 能够浏览网页、读取邮件或调用外部服务时，工具返回的任何文本都可能成为攻击入口。恶意网页不需要攻破传统软件，只要诱导模型把页面中的指令当成任务的一部分，就可能影响后续执行。

开源 Harness 如果把“完全自主”作为主要卖点，却没有默认最小权限、危险操作确认、环境隔离和审计能力，就可能把自由误解成了无防护。

评价一个 Agent Harness，不能只看演示中它完成了多少任务，还要看三个失败边界：

- 它不知道时会做什么；
- 它被诱导时能做什么；
- 它做错后能否恢复。

真正成熟的 Harness，不是让 Agent 无条件获得更多权力，而是让每一次权力扩张都可见、可撤销、可追踪。

## 中国 AI 生态正在选择第二条出海路线

中国模型参与全球竞争，第一条路线已经相当清晰：通过更低的推理成本、开放权重和快速迭代，成为全球开发者的模型供应商。

但低价 API 的问题是，利润有限，替代性也很强。今天开发者因为价格选择某个模型，明天就可能因为另一家更便宜而离开。

Harness 提供了第二条路线：不只出售推理能力，而是进入开发者完成任务的全过程。

这条路线的价值更大，也更困难。全球开发者对基础工具链的要求不只是便宜，还包括：

- 文档和社区是否成熟；
- 能否兼容主流模型与工具协议；
- 安全机制是否可信；
- 项目治理是否稳定；
- 企业是否敢于长期依赖；
- 贡献者能否真正参与决策。

如果一个所谓开放 Harness 只对自家模型优化，其他模型体验明显较差，那么它本质上仍是模型分发渠道。只有当开发者能够公平地替换模型、修改策略、导出状态并控制权限时，它才可能成为真正的公共基础设施。

因此，DeepSeek Harness 面临的最大考验不是下载量，而是它愿意开放到什么程度：

**是用开源工具链扩大自家模型份额，还是允许工具链最终超越模型品牌本身？**

## 下一场标准战争已经开始

一旦 Harness 成为 Agent 生态的关键层，行业就会争夺新的事实标准：

- 工具如何描述能力；
- 模型如何请求调用工具；
- Agent 如何声明所需权限；
- 上下文如何在不同产品间迁移；
- 执行轨迹如何记录和验证；
- 项目规则如何跨 Agent 复用；
- 多个 Agent 如何交接任务。

谁控制这些标准，谁就可能掌握 Agent 生态的入口。

开放协议能够降低迁移成本，但厂商也有动力增加专有功能：更强的记忆、更丰富的工具、更精细的企业权限。用户获得短期便利的同时，会逐渐依赖无法迁移的状态。

这与早期云计算极其相似。虚拟机看似可以移动，真正让企业难以迁移的却是数据库、身份系统、监控、队列和部署流程。Agent 时代也可能重复这一过程：

模型是最显眼的部分，却未必是最难搬走的部分。

## 判断 Harness 价值，应看四种成本

未来衡量一个 Agent 平台，不能只比较模型排行榜，而应比较四种更实际的成本：

**第一，切换成本。**  
替换模型、工具或平台时，需要重建多少配置与上下文？

**第二，监督成本。**  
用户需要投入多少注意力，才能确认 Agent 没有偏离任务？

**第三，失败成本。**  
一次错误最多会损坏哪些文件、系统或数据？

**第四，验证成本。**  
用户如何知道任务是真的完成，而不是 Agent 自信地宣布完成？

低价模型可以降低每百万 Token 的费用，却未必能降低这四种成本。一个调用价格更高、但能减少返工和事故的系统，整体上可能更便宜。

这意味着 Agent 竞争最终会从“单位推理价格”，转向“单位可靠任务成本”。

## 结语：模型会商品化，工作流不会自动开放

DeepSeek Harness 的意义，不在于它是否立即取代 Claude Code 或 Codex，而在于它把一个长期被产品界面遮住的问题摆到了台前：

**Agent 的核心资产究竟是模型，还是围绕模型形成的执行系统？**

随着模型能力逐渐接近、价格不断下降，单纯依靠模型差异建立护城河会越来越困难。真正决定用户去留的，将是上下文能否积累、工具能否协同、权限能否控制、任务能否可靠完成，以及这些资产能否自由迁移。

开源模型解决了“谁拥有大脑”的问题，开源 Harness 开始追问“谁控制手脚”。

但最终的开放不能止于代码仓库。它还必须包括可替换的模型、可迁移的状态、可审计的权限和可验证的执行记录。否则，用户只是从一个黑箱搬进另一个黑箱。

模型是发动机，Harness 是整辆车。

而真正值得争夺的，是开发者有没有权决定这辆车装什么发动机、驶向哪里，以及在必要时能否把自己的行李完整带走。
