## 04. RAG 检索增强生成

*Retrieval-Augmented Generation*

> 类比：像「开卷考试」，不让模型凭记忆硬答，先翻到正确答案那一页（真实文档）基于资料作答，从而降低仅依赖参数记忆带来的风险。

### 专业定义

RAG 是一种将「外部知识检索」与「生成式模型」结合的架构，在生成前先从知识库召回相关片段，拼入上下文，使模型基于可验证资料作答，而非仅凭参数记忆。

### 核心机制（四步）

文档切段 → Embedding → 存入向量数据库；

用户问题转 Embedding；

向量库检索语义最相近片段（Top-K）；

拼入 Prompt 交由模型生成。

### 产品启示

RAG 的效果上限往往首先受检索与资料质量约束，而不只取决于生成模型。切分策略、Embedding 选型、Reranking 精排（见 [31](#concept-31)/[08](#concept-08)/[32](#concept-32)）往往比调模型更关键。检索召回错误会显著增加答非所问或错误引用的风险。Agentic RAG 正在被用于需要多轮检索、查询改写和证据校验的复杂任务：由 Agent 自主决定多轮检索、交叉验证与知识重构，而非单次静态召回（见 [68](#concept-68)）。

RAG 是「开卷考试」，通常不修改模型参数，而是在推理时注入检索资料；它仍可能误解、忽略或错误引用证据（区别于微调，见 [05](/ai-product-100-concepts/model-selection/#concept-05)）。

## 08. Embedding 向量嵌入

*Vector Embedding*

> 类比：像把每句话「压成一组气味坐标」，意思相近的句子坐标离得近，意思不同的离得远；搜「燕麦奶拿铁」能命中有「燕麦冰拿铁」的菜单，因为气味相近。

### 专业定义

Embedding 是将离散文本映射为稠密高维（如 1536 维）浮点向量的过程，使语义相近的文本在向量空间中距离更近，从而支持语义级相似度检索。

### 核心机制

Embedding 模型在大规模语料上预训练，将语义相近文本映射到相邻位置。相似度通常用余弦相似度衡量。注意，同一词在不同语境下向量不同，「苹果手机」与「iPhone 性能」距离近，「苹果手机」与「吃苹果」距离远。

### 产品启示（RAG 三关注点）

中文支持度（部分模型英文强中文弱）；

向量维度（越高越准，存储/检索成本也越高）；

向量库选型（速度/规模/运维差异大，见 [30](#concept-30)）。

Embedding 是 RAG 的基础设施，选错后面全是坑。

<a id="concept-29"></a>

## 29. Context Window 上下文窗口

*Context Window*

> 类比：像「一页写不下的便签」，窗口越大听着越能装，但系统提示、工具定义、历史对话都要占位置，真留给业务的没多少，且太长重点会被淹没。

### 专业定义

上下文窗口是模型单次请求可处理的最大 token 总量（含 System Prompt、工具定义、历史、输出预留）。

### 产品启示

标称 128K ≠ 可用 128K。需减去 System Prompt（~3K）、工具定义（~2K+）、历史（动态）、输出预留（~4K），业务文档空间远小于标称。

### 反直觉事实

窗口越大≠效果越好。超长上下文会加剧「中间迷失」，关键证据被无关内容淹没。正确做法分块 → 检索召回最相关片段 → 精排后将最关键内容置于首尾。窗口能力是上限，上下文工程水平才是下限。

<a id="concept-30"></a>

## 30. Vector Database 向量数据库

*Vector DB*

> 类比：像「按气味摆货的仓库」，百万种商品按语义坐标存放，问「不太甜的拿铁」能在毫秒级找到最相近的几款，传统数据库按名字找反而慢。

### 专业定义

向量数据库是专为高维向量最近邻检索（ANN）设计的数据库，支持百万至亿级向量毫秒级相似度搜索。

### 核心机制

文档经 Embedding 入库；查询转向量后在库内做最近邻搜索返回 Top-K。传统关系库做相似度搜索需数十秒，不可用。

### 选型四指标

检索速度（百万级毫秒级）、召回率（相关文档找回比例）、支持规模、运维成本。

### 主流

Pinecone（全托管贵）、Milvus（开源大规模）、Weaviate（混合搜索）、Chroma（轻量快速）。小规模验证用 Chroma，生产看 Milvus/Pinecone。

<a id="concept-31"></a>

## 31. Chunking 文档分块

*Chunking*

> 类比：像「切香肠不能切断馅」，按语义完整切，检索才准；一刀切在句子中间，模型拿到半句话当然答非所问。

### 专业定义

Chunking 是将长文档切分为语义相对完整、适合检索与生成的片段的策略，是 RAG 检索质量的关键前置环节。

### 核心矛盾

块太大→语义杂、相似度被稀释；块太小→语义残、模型拿残缺信息。无万能参数，需按文档结构与场景调。

### 三种策略

固定大小每 500 字+重叠。简单但易切断语义；

按结构按标题/段落/章节。保逻辑但依赖格式；

语义分块可在相邻内容语义变化处切分，可能改善语义完整性，但实现和计算成本更高，效果需要实测。

### 产品启示

先按结构切，无结构处用固定+重叠兜底；块大小应结合文档结构、检索模型和业务查询集测试；切分后按风险和文档类型抽样检查，防止语义被切断。

<a id="concept-32"></a>

## 32. Reranking 重排序

*Reranker*

> 类比：像「初筛后再请专家精读」，向量检索是粗排快但糙，Reranking 把候选逐词细比，把真正对的顶到前面。

### 专业定义

Reranking 是在向量粗排（Top-20/50）基础上，用交叉编码器（cross-encoder）对候选逐对精细打分重排，取 Top-3/5 给模型生成，以提升精度。

### 核心机制

Embedding 将整段压成单向量，必丢细节；Reranker 同时看问题与文档每个词，信息量大、判断更准。

### 产品启示

Reranking 可能改善排序质量，同时增加模型调用和延迟；提升幅度及用户是否可感知均取决于候选集、重排模型和端到端链路。选型时应同时测 NDCG、Recall@K、端到端延迟与成本。

<a id="concept-33"></a>

## 33. Hybrid Search 混合搜索

*Hybrid Search*

> 类比：像「关键词找编号 + 语义找意思，两路合并」，订单号、型号这类精确匹配靠关键词，自然语言描述靠语义，两条都走才不漏。

### 专业定义

Hybrid Search 并行执行向量检索（语义）与关键词检索（BM25/倒排），再融合结果，兼顾语义理解与精确匹配。

### 核心机制

同一查询跑两路，分别返回结果，经 RRF 或加权融合成统一排序。订单号、产品型号、人名等精确匹配场景，关键词检索天然优于向量。

### 产品启示

对包含编号、专名和精确条件的查询，混合搜索通常比单一语义检索更稳健，但提升幅度需在业务查询集上验证。自然语言描述可优先验证向量检索；编号或精确条件查询可加入关键词检索。是否默认采用混合搜索，应由业务查询集评测决定。

<a id="concept-34"></a>

## 34. Knowledge Graph 知识图谱

*Knowledge Graph / GraphRAG*

> 类比：像「一张关系网而非一堆便签」，存的是「A 是 B 的竞品、B 的优势是便宜」这种关系，能多跳推理，而不只是孤立文档。

### 专业定义

知识图谱以「实体—关系—实体」三元组结构化存储知识，支持多跳推理；GraphRAG 将其与向量检索结合，复杂关系查询走图谱路径。

### 核心机制

向量库存孤立文档段，不理解实体关系；图谱存关系，可从 A 跳到 B 再跳到影响，实现多跳推理。

### 产品启示

构建维护成本高（NER + 关系抽取 + 人工校准）。建议，实体关系固定明确的领域（医疗/法律/金融）再上；变化快或关系不清的，先把向量 RAG 做好。

## 35. 知识库建设

*Knowledge Base Construction*

> 类比：像「喂模型的食材得新鲜」，文档乱、旧、重复，RAG 再强也救不回；知识库的天花板就是 RAG 的天花板。

### 专业定义

知识库建设是将业务文档治理、结构化、持续维护为可供 RAG 检索的高质量语料资产的过程，是 RAG 效果的天花板（非模型能力）。

### 核心机制

RAG 上限 = 知识库质量。文档格式混乱、内容重复、过期，RAG 必崩。且知识库非「建好即完」，需持续与业务系统（如 ERP）同步，断更一周效果即崩。

### 三环节

数据治理去重去噪、更新过期、统一格式（最耗时最没技术含量，但跳过全白做）；

结构化处理打标签、加元数据、按主题分类；

质量评估建评测集定期测覆盖率与准确率。

写作方式须为 RAG 优化，每段尽量自包含，不依赖上下文。知识库建设往往是 RAG 项目的主要投入之一；若缺少解析、去重、权限、更新和质量检查，生成模型再强也难以弥补。

## 36. 文档解析

*Document Parsing / OCR-friendly Parsing*

> 类比：像「做饭前先洗切配」，PDF 里表格乱、页眉混进正文，第一步没做好，后面切分、检索、生成全在垃圾上做无用功。

### 专业定义

文档解析是将 PDF/Word/扫描件等源文档转为结构化文本与表格的过程，是 RAG 流水线起点，质量差则后续全在垃圾数据上做功。

### 核心挑战

表格识别PDF 表格常由独立文本框拼成，普通工具乱序输出；

多栏排版左右栏内容易混；

图文混排图内关键信息需 OCR 提取。

### 选型

文本类用 Unstructured / LlamaIndex 解析器；复杂 PDF/扫描件用专门文档智能模型。解析后必须抽样人工检查，若关键字段或结构解析错误超过业务容忍线，应更换解析策略或增加人工校验；容忍线需按错误代价设定。

## 37. Grounding 接地

*Grounding / Attribution*

> 类比：像「说话要有出处」，回答须基于可查的数据源并标注来源，用户能追溯验证；没接地的报价是模型自己编，出事全是产品的锅。

### 专业定义

Grounding 要求模型回答基于可验证数据源并在输出中标注来源，使内容可追溯、可核查，是产品信任的基础设施。

### 核心机制

RAG 即一种 Grounding 手段；更广涵盖实时搜索、数据库查询、API 调用获取实时数据。先检索真实信息再生成，并引用来源。

### 产品启示（信任度设计）

对研究、医疗、法律、金融和企业知识问答等高风险事实任务，应提供来源、引用与时间信息；无法 Grounding 时应明确提示未经验证。对创意生成和一般闲聊，可依据错误代价采用更轻量的披露方式。

<a id="concept-68"></a>

## 68. 自主式 RAG

*Agentic RAG / Self-RAG*

> 类比：像「会自己多翻几页再答题的学生」，不只查一次，而是先改写问题、多跳检索、自评分，确认够准才作答，幻觉再降、准确率再升。

### 专业定义

Agentic RAG 把 RAG 从「一次性检索」升级为「由 Agent 驱动的多步检索—自省—再检索」架构，Agent 规划查询、评估召回质量、必要时改写查询或启用图谱/多跳检索，直至置信度达标。

### 核心机制

区别于静态 RAG（见 [04](#concept-04)）的「问→检索→答」单链，引入查询重写（query rewriting）、假设文档嵌入（HyDE）、自评分（self-grade）、GraphRAG 多跳（见 [34](#concept-34)）。这些方法可能改善复杂企业问答的召回与忠实度，但提升幅度高度依赖数据集、基线和评测方法，应以本业务回归集验证。

### 产品启示

高价值知识问答/复杂推理场景，优先「分层 RAG」，常见问题轻量向量检索，复杂/多跳问题启用 Agentic RAG + 图谱。成本与延迟高于静态 RAG，须按问题难度路由（见 [63](/ai-product-100-concepts/model-selection/#concept-63)）。仍须配合 Grounding（见 [37](#concept-37)）与 Bad Case（见 [53](/ai-product-100-concepts/evaluation-governance/#concept-53)）治理。

## 94. 长上下文策略

*Long-Context Strategy*

> 类比：像「给员工一本逐渐变厚的项目手册」——手册越全，他越不需要反复问你，但你也得防他读到一半走神。

### 专业定义

长上下文策略指在产品层面规划「哪些信息该常驻上下文、何时压缩、何时外置到记忆/检索」，以平衡成本与连贯。

### 核心机制

在产品层规划「哪些信息常驻上下文、何时压缩、何时外置到记忆 / 检索」；长窗口能减少 RAG 依赖，但抬高成本并带来注意力稀释，需在「全量 / 摘要 / 外挂检索」之间权衡。

### 产品启示

不是窗口越大越好。按任务分层（系统提示 / 用户上下文 / 工作记忆 / 外部检索），监控有效上下文利用率与成本，设置自动压缩与淘汰策略，避免为用不上的历史买单。
