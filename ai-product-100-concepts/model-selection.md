## 01. LLM 大语言模型

*Large Language Model*

> 类比：像一台「文字接龙机」，给它一段上下文，它按照解码策略逐步生成后续 token；它的基础训练目标并不是像人一样理解世界，而是学习上下文中的统计规律；这些规律可以产生一定的语义理解与推理表现，但能力并不稳定。

### 专业定义

以大语言模型为代表的自回归生成式模型，本质是基于海量语料训练出的概率语言模型，通过对上下文的条件概率建模，逐个预测序列中下一个 token，从而完成文本生成。

### 核心机制

给定一段文本，模型输出「下一个 token 的条件概率分布」，再依据贪心、采样或其他解码策略选择候选，再将其拼回上下文继续预测，循环至生成终止符或达到长度上限。这是一种「逐 token 自回归生成」机制；模型可在生成过程中表现出推理能力，也可结合搜索、代码与其他工具完成任务，但其内部机制不同于显式的符号程序。

不过，2026 年的主流模型早已不止「文字接龙」。推理模型（Reasoning Models）通常会投入额外的隐藏推理计算，并引入 Test-time Compute（推理时计算扩展）——在回答阶段额外投入算力做多步推导与自检，使严密逻辑推理、数学与代码类任务的可靠性大幅跃升。PM 须知：这显著增强了模型在部分任务上的推理表现，但代价是更高延迟与成本，需在关键链路按需启用（见 [62](#concept-62) 推理模型、13 Temperature）。

### 产品启示（三个硬约束）

- 边界一，能表现出推理能力，但不等于结果可靠。

在严密逻辑、精确计算和强约束求解场景中，模型可能出错；应结合代码执行、规则校验、外部工具或人工复核，而不能把语言流畅度等同于结论正确。

- 约束二，知识有截止日期（knowledge cutoff）。

模型对训练数据截止时间后的事件缺乏可靠、系统的知识，可能从上下文推断出部分信息，也可能生成未经验证的内容。实时事实应通过搜索、数据库或 API 获取，并保留来源与时间信息。

约束三，输出具有随机性。

不同产品和 API 可能采用贪心、temperature、top-p 或其他解码策略；启用采样时，相同输入可能得到不同输出。需要更稳定时可降低随机性参数，并配合结构化输出与校验（见 [13](/ai-product-100-concepts/prompt-generation/#concept-13)/[66](/ai-product-100-concepts/prompt-generation/#concept-66)）。

做 AI 产品的第一步不是想「AI 能干什么」，而是想明白「AI 干不了什么」，把干不了的部分用规则、人工、兜底策略补上。如果忽略能力边界，项目风险会显著上升。

## 03. Token 文本处理单元

*Token*

> 类比：像打印店「按字收费」，许多模型服务会分别统计输入、输出、缓存和推理 token；token 越多，通常意味着更高成本，但具体计费方式以供应商为准。

### 专业定义

Token 是模型处理文本的基本离散单元，由 tokenizer 将输入转换为 token 序列。商业 API 通常区分输入、输出、缓存以及部分模型的推理 token；计费方式会变化，应以供应商当前文档为准。[^4]

### 核心机制

token 数取决于分词器、文本类型与语种，中文在不同模型间差异尤其明显。结论，不要假设「一个汉字 = 1.5 token」普适，应以目标模型的 tokenizer 实测为准。

### 产品启示（两个决策点）

成本

System Prompt 每次调用都重发。较长的 System Prompt 会在大量调用中持续累积成本；中文字符与 token 之间不存在通用固定换算率，应使用目标模型的 tokenizer 和最新价格表实测。

上下文窗口

模型可处理 token 总量有上限，扣掉 System Prompt、工具定义、历史对话后，留给业务内容的空间远小于标称窗口。

需求评审必填公式，单次 token 消耗 × 日均调用量 × 单价 = 月成本。这笔账应与质量、延迟和业务价值一起进入需求评审。

<a id="concept-05"></a>

## 05. Fine-tuning 微调

*Full-parameter Fine-tuning*

> 类比：像让通才「转岗培训」，不是重读大学（重训模型），而是针对你们公司的说话方式和规矩短期特训，把它变成「自己人」。

### 专业定义

微调是在预训练基座模型基础上，用特定任务数据继续训练、更新模型参数，使模型习得目标风格、格式或分类体系的能力。

### 核心机制（与 RAG 的分界）

补知识 → 用 RAG

（模型不知道的事实，检索注入即可）；

- 调风格/语气/专属格式 → 用微调

（Prompt 管不住、RAG 也无用）。

### 何时上微调（三类）

特定输出风格/语气，Prompt 无法稳定约束；

自定义分类体系，标准与通用不一致；

Prompt Engineering 已到天花板，加示例仍无效。

### 产品启示

微调需要准备、质检和维护训练数据，并承担训练与回归评测成本；实际投入取决于模型、方法和任务。可先建立基础模型与 Prompt 基线：事实时效或私有知识问题优先评估 RAG，稳定行为、风格或任务适配问题再评估微调，两者也可以组合使用。

<a id="concept-18"></a>

## 18. Pre-training 预训练

*Pre-training*

> 类比：像进行大规模通识训练：模型从海量文本、代码等数据中学习统计规律，形成随后可继续适配的基座。

### 专业定义

预训练是以海量无标注语料训练随机初始化 Transformer、使其习得语言统计规律与通用知识的阶段，是整个模型链条中最烧钱的一步，产出「基座模型」。

### 核心机制

将互联网文本/书籍/代码/论文喂入模型，反复做「预测下一个 token」，预测错则调整参数，经数万亿次更新后习得语言规律。前沿模型预训练通常需要大规模算力、数据和工程投入；由于模型规模、硬件利用率和披露口径不同，不宜用单一成本数字概括。

### 产品启示

知识截止日期训练数据只到某时点，之后事实模型不知 → 决定是否需要 RAG；

训练偏差英文语料远多于中文 → 选模型看中文评测分而非总分；

自建不现实绝大多数公司只能用现成基座做产品。

基座模型「什么都会一点但不会好好说话」，需 SFT + RLHF 才成助手。

<a id="concept-19"></a>

## 19. SFT 监督微调

*Supervised Fine-Tuning*

> 类比：像「岗前话术训练」，用几千条标准问答教基座模型「该怎么回答」，把它从「续写机器」调成「问答助手」。

### 专业定义

SFT 是用人工标注的「问题—标准答案」数据对，训练基座模型习得期望的回答格式、风格与逻辑，使其从「续写机器」变为「问答助手」。

### 核心机制

数据质量、覆盖范围与任务难度共同决定 SFT 效果；所需样本量应通过学习曲线和独立评测集判断。

### 产品启示

- 数据质量决定一切；

- SFT 教会「怎么答」，但教不会「什么算好答」（价值观/安全需 RLHF）；

评估供应商时问

SFT 数据来源？量级？，可快速判断其垂直领域效果。

## 20. RLHF 人类反馈强化学习

*Reinforcement Learning from Human Feedback*

> 类比：像「用顾客评分倒逼服务态度」，收集「哪种回答更让人舒服」的偏好，反过来训练模型先共情再解决，而非冷冰冰回「已退款」。

### 专业定义

RLHF 是用人类偏好数据训练奖励模型，再以强化学习（如 PPO）优化大模型，使其生成更符合人类偏好的回答，决定模型的「性格」与安全性边界。

### 核心机制（三步）

收集偏好数据（同一问题多回答排序）；

训练奖励模型（RM）学人类偏好标准；

PPO 强化学习用 RM 打分优化大模型。

### 产品启示

RLHF 决定模型是过度拒答还是该拒不拒、啰嗦还是简练、讨好还是坚持原则。用开源模型自建时，偏好标准与拒答边界需产品经理参与定义。DPO 在经典形式下不显式训练奖励模型，也不执行在线强化学习；它通常更简洁，但效果仍取决于偏好数据、基座模型和训练设置。

<a id="concept-21"></a>

## 21. LoRA 低秩适应

*Low-Rank Adaptation*

> 类比：像「给原模型贴一层可撕的补丁」，不动原始大模型，只训练极小增量，风格/口吻一贴就变，换场景撕下补丁换一张，省钱九成。

### 专业定义

LoRA 是参数高效微调（PEFT）方法：冻结基座参数，只训练注入的低秩矩阵。原始论文在 GPT-3 175B 实验设置中报告，可训练参数相对全量微调最多减少约 10,000 倍、GPU 显存需求约降至三分之一；这不是所有模型和任务的统一收益。[^2]

### 核心机制

训练结果形如「补丁」，可动态挂载到基座。多场景各训一个几 MB 的 LoRA，调用时按意图加载，一个基座当多个用。

### 产品启示

- 擅长风格/格式/口吻调整；

- 需灌全新知识领域则效果有限（用 RAG）；

- 数据需求低（数百至数千条），训练从数天压缩至数小时。

调风格用 LoRA，补知识用 RAG，搞混即花冤枉钱。

## 22. Distillation 知识蒸馏

*Knowledge Distillation*

> 类比：像「名师带徒弟」，用大模型产出的高质量答案去训小模型，小徒弟学得神似，单次成本却从几分钱降到几厘。

### 专业定义

知识蒸馏是用强教师模型（如 GPT-4）生成的软标签（含概率分布）训练小模型，使其以远低于教师的计算成本逼近教师能力。

### 核心机制

小模型不仅学「答案」，还学教师对每个 token 的置信分布（软标签信息量远大于硬标签），故蒸馏小模型远优于同数据从头训练。

### 产品启示（降本标准打法）

研发阶段用闭源强模型验证可行性，效果确认后蒸馏到开源小模型部署，单次成本从「分」降「厘」，降一个数量级。法律风险部分闭源模型条款禁止用其输出训练竞品，蒸馏前须确认许可。

## 23. Quantization 量化

*Quantization*

> 类比：像「把高清图压成缩略图」，精度降一点，体积和显存大减，原本塞不进的模型能跑在便宜的卡上，端侧也能用。

### 专业定义

量化是将模型参数精度由高位（FP32/FP16）降至低位（INT8/INT4）的压缩技术，以可控精度损失换取显存与算力的大幅下降。

### 核心机制

仅计算权重时，7B 参数模型使用 FP32、INT8、INT4 分别约需 28GB、7GB、3.5GB；实际部署还要计入 KV cache、激活、运行时与并行开销。精度影响依模型、量化方法和任务而异，应以目标评测集验证。

### 产品启示

- 直接决定私有化部署硬件成本（A100 80GB vs 消费级 4090 24GB，差一个量级）；

- 端侧/离线场景几乎必选（手机芯片显存有限）；

选型看两指标

困惑度损失越小越好、推理提速倍数越大越好。

## 24. Inference 推理

*Inference*

> 类比：像「每次打电话都计费」，训练是一次性买断，推理是天天用天天烧；上线后，推理通常成为持续发生的主要成本之一。

### 专业定义

推理是模型训练完成后，对每次请求执行前向计算产出结果的过程。训练是一次性投入，推理是持续性支出，生产期成本往往由推理、工具调用、存储、网络与运维共同构成，比例需按业务负载核算。

### 核心机制

单次成本 = 输入 token × 输入单价 + 输出 token × 输出单价。日调用量级放大后，成本差异直接决定商业模型是否成立。

### 产品启示（三指标写进 PRD）

延迟 Latency影响体验；

吞吐量 Throughput影响可服务用户规模；

单次成本 Cost per Query影响商业模型。

优化手段，量化、蒸馏、Prompt 精简、缓存高频问答、批量推理。成本约束须在需求阶段写入，别等账单。

## 25. Transformer 架构

*Transformer*

> 类比：像「全班同时读同一篇文章」，不像旧模型轮流读（串行），它让每个词同时看全篇，所以能并行、能抓远距离关联，但文本越长计算越贵。

### 专业定义

Transformer 由 Vaswani 等人在 2017 年提出，以注意力机制取代传统循环结构，后来成为大语言模型最重要的基础架构之一。[^1]

### 两大产品相关特性

并行计算训练和提示词预填充阶段可以并行处理多个 token；自回归生成阶段仍需逐 token 解码，使千亿参数训练可行；

长距离依赖任意两 token 可直接建立关联，理解长文本前后文。

### 核心代价

标准全注意力的计算和显存开销会随序列长度快速增长，注意力计算复杂度通常为平方级；现代系统可用稀疏注意力、滑动窗口、缓存等方法改变实际成本曲线。长文档场景优先 RAG 检索筛选，而非整篇塞入窗口。

<a id="concept-26"></a>

## 26. Attention 注意力机制

*Self-Attention*

> 类比：像「读句子时自动圈重点」，生成每个词时给相关词更高权重，开头和结尾最易被记住，夹在中间的易被忽略（中间迷失）。

### 专业定义

Self-Attention 是模型生成每个 token 时，计算其与允许访问的位置之间的相关度；自回归解码器通常通过因果掩码只关注当前位置及之前的 token并加权聚合的机制，使模型自动聚焦关键信号。

### 产品含义（Lost in the Middle）

模型处理长文本非平均关注，部分模型和任务会出现“中间信息利用率较低”的现象，但位置效应并非固定规律，应使用目标模型和业务样本验证。Few-shot 示例与关键约束的排列顺序直接影响输出质量。

### Multi-Head Attention

多组注意力并行，各组关注不同维度（语义/语法/位置），多视角联合提升理解全面性。

<a id="concept-27"></a>

## 27. 开源模型 vs 闭源模型

*Open vs Closed Source*

> 类比：像「自家厨房 vs 外卖」，闭源是点外卖，好吃省事但数据出域、长期贵、随时可能涨价；开源是自家厨房，数据不出门、可定制，但要自己买锅请厨师。

### 专业定义

闭源模型（GPT-4/Claude/Gemini）由厂商托管、按量付费；开源模型（Llama/Qwen/DeepSeek）权重开放，可私有部署与微调。

### 权衡

闭源

效果上限高、即开即用、持续升级；但数据出域、长期成本高、供应商锁定。

开源

数据不出域、可深度定制、长期成本可控；但需自建 GPU 集群与运维、效果可能稍弱、需自跟进升级。

### 产品启示（四问选型）

合规是否禁数据外传？→ 必选开源私有部署；

是否需最前沿推理？→ 先闭源；

日均调用量多大？→ 高频开源更省；

时间压力？→ 两周上线用闭源 API，半年规划走开源。

成熟做法，混合架构，高敏业务开源本地、通用复杂任务闭源 API，按任务路由。

<a id="concept-56"></a>

## 56. API 接口

*Application Programming Interface*

> 类比：像「两个系统之间的插座」，你发请求（模型名+消息+参数），它回结果（文本+token 用量），看懂 JSON 字段才能和开发一起拍板。

### 专业定义

API 是产品后端与模型服务间的通信接口，通过 HTTP 请求传入模型名/消息/参数，返回生成文本与 token 用量。

### 产品启示（PM 需懂四件事）

入参出参格式直接定功能边界（如是否支持图片输入决定能否做多模态）；

计费方式按 token 还是按次、输入输出是否分开、能否批量降本；

限制RPM/TPM、单次最大 token、并发；

错误码429 限流、504 超时、503 不可用，产品层如何兜底须事先定义。

不必会写代码，但要能读 API 文档并与开发讨论参数选择，这是 AI PM 与传统 PM 的关键区别之一。

<a id="concept-61"></a>

## 61. MoE 混合专家模型

*Mixture of Experts*

> 类比：像「医院分诊台」，不是每次都请全院专家，而是按问题路由到对应科室（专家），大部分 token 只激活少数「专家」，省算力又保效果。

### 专业定义

MoE 是一种模型架构，将前馈网络替换为多个「专家」子网络，每个 token 仅由门控网络（router）动态激活其中少数几个专家，从而在总参数量巨大的同时保持单次推理的计算量可控。

### 核心机制

与稠密模型不同，MoE 用 router 对每个 token 激活部分专家。它可以在控制单次计算量的同时扩大总参数规模，但会增加通信、路由均衡、显存管理和服务部署复杂度；质量收益需要在目标任务上验证。

### 产品启示

不能仅凭总参数量判断 MoE 的质量或成本。选型时应比较目标任务质量、端到端延迟、吞吐、部署显存和服务价格，并关注路由均衡与通信开销。是否与模型路由组合使用，应由请求分布和压测结果决定（见 [63](#concept-63)）。


---

<a id="concept-62"></a>

## 62. 推理模型 / 推理时扩展

*Reasoning Model / Test-time Compute*

> 类比：像为难题分配更多计算预算：模型可以多做搜索、采样或内部推演，但更多计算不保证答案一定更正确。

### 专业定义

推理模型通常指针对复杂推理任务优化、能够在回答阶段使用额外计算预算的模型；推理时扩展（test-time compute）指在推理阶段增加采样、搜索、验证或隐藏推理计算，以尝试提高任务成功率。具体实现和命名因供应商而异。

### 核心机制

模型可能在输出答案前使用额外的隐藏推理计算、搜索或采样；这些内部过程不应直接视为可验证的推理证据。增加推理预算有时能改善复杂任务表现，但存在收益递减，延迟与成本通常也会上升。

### 产品启示

按任务价值密度选型，高价值低频深度分析用推理模型；高频低复杂日常任务用标准模型控成本（见 [63](#concept-63) 路由、24 推理成本）。PRD 须明确「是否开推理、思考预算上限、超时降级」，并给用户可见的「分析中」进度（见 [11](/ai-product-100-concepts/prompt-generation/#concept-11) 流式、57 延迟）。注意推理模型也会错，仍需 RAG 接地与校验（见 [09](/ai-product-100-concepts/evaluation-governance/#concept-09)/[37](/ai-product-100-concepts/rag-knowledge/#concept-37)）。

<a id="concept-72"></a>

## 72. 端侧 / 小语言模型

*Small Language Model / On-device*

> 类比：像把部分助手能力放到本地设备：可以离线运行并减少数据出域，但仍有本地计算延迟、能耗、包体和设备兼容成本。

### 专业定义

SLM 与端侧推理指在手机、PC 或边缘设备上运行相对较小或经过压缩的模型。它可以支持离线能力并减少部分数据出域，但隐私仍取决于日志、同步、更新和工具调用链路。

### 核心机制

量化、蒸馏和专用加速器可以降低端侧推理资源需求。端云协同可按能力、隐私、网络、能耗和延迟在本地与云端之间路由，但可行性取决于目标设备和模型。

### 产品启示

隐私敏感、离线或网络不稳定场景可以优先评估端侧小模型；同时比较能力、能耗、设备覆盖率、更新机制和云端成本。PM 应定义端云路由条件（见 [63](#concept-63)）、本地缓存与失败降级策略。


---

<a id="concept-75"></a>

## 75. 推理引擎 / 模型服务

*Inference Engine / Model Serving*

> 类比：像餐厅的「后厨流水线」，同样的菜（模型），配不同的灶台和动线（vLLM / TensorRT-LLM / SGLang），出餐速度和翻台率天差地别。

### 专业定义

推理引擎是承载大模型在线服务的系统软件，负责连续批处理（continuous batching）、KV Cache 管理与分页注意力（PagedAttention）、调度与显存复用，直接决定吞吐、延迟与单位推理成本（见 [24](#concept-24)）。

### 核心机制

推理引擎可通过动态批处理、KV Cache 管理、并行和调度策略提升硬件利用率。实际吞吐与延迟受模型、硬件、上下文长度、输出长度和并发分布影响，需要在目标负载下压测。

### 产品启示

架构评审要把「推理引擎选型」写进决策，推理引擎可能通过连续批处理、KV cache 管理和并行策略显著改善吞吐与单位成本；具体收益应在相同硬件、模型与负载下压测；它直接决定 57 延迟与 24 推理账单。是否支持 76 推测解码、77 MLA、65 提示缓存也应列入约束。


---

<a id="concept-76"></a>

## 76. 推测解码

*Speculative Decoding*

> 类比：像「实习生先起草、主厨只批改」，小模型飞快写出一整段草稿，大模型只做「对/错」验收，省掉逐字慢推。

### 专业定义

推测解码用一个小草稿模型（draft）一次预测多个 token，再由目标大模型并行验证，被接受的片段直接输出，从而在不改变输出分布的前提下大幅提速。

### 核心机制

草稿模型先生成候选，目标模型并行验证，并通过修正后的采样规则保持目标分布。原始研究在特定 T5-XXL 实验设置中报告约 2–3 倍加速；实际收益取决于草稿命中率、硬件和服务实现。[^3]

### 产品启示

推测解码适合评估在延迟敏感、目标分布不能改变的场景中使用；前提是推理引擎（见 [75](#concept-75)）支持，并且草稿模型具有足够高的接受率。是否优于量化、批处理或换用小模型，需要通过端到端压测判断。


---

<a id="concept-77"></a>

## 77. 多头潜在注意力 MLA

*Multi-head Latent Attention*

> 类比：像压缩每个 token 需要保存的 Key/Value 表示，主要减少 KV Cache 的显存和带宽压力。

### 专业定义

MLA 是一种注意力变体，通过低秩潜在表示压缩需要缓存的 Key/Value 信息，从而降低长上下文推理中的 KV Cache 显存与带宽开销。

### 核心机制

传统 MHA 为每个 token 存完整 Key/Value，KV Cache 显存随上下文长度线性增长（常数较大）；MLA 用低秩投影把每 token 的 KV 压成极小的潜在表示，使长上下文显存大幅降低、仍保持线性增长。注意：随长度平方增长的是注意力计算算力（见 [24](#concept-24)），不是显存——MLA 主要省的是显存与带宽，而非把平方变成线性。

### 产品启示

长文档、长对话和多轮 Agent 场景应比较模型在目标上下文长度下的质量、首 token 延迟、生成速度、显存与价格。MLA 可以是架构信息之一，但不应替代端到端评测（见 [06](/ai-product-100-concepts/agents/#concept-06)/[40](/ai-product-100-concepts/agents/#concept-40)）。


---

<a id="concept-78"></a>

## 78. DPO 直接偏好优化

*Direct Preference Optimization*

> 类比：像「不用请打分员，直接拿两个回答让你挑喜欢的」，省掉奖励模型这层中介，对齐更快更稳。

### 专业定义

DPO 是一种直接使用偏好对（chosen / rejected）优化策略模型的方法。在经典形式下，它不需要显式训练奖励模型，也不执行 PPO 式在线强化学习（见 [20](#concept-20)）。

### 核心机制

DPO 根据策略模型相对参考模型对 chosen 与 rejected 回答的偏好差异构造目标。流程通常比经典 RLHF 更简单，但仍受数据偏差、超参数和参考模型选择影响。

### 产品启示

需要自有偏好适配时，可把 DPO 与 SFT、奖励模型方案或其他偏好优化方法放在同一评测集上比较。产品侧应定义偏好数据、拒答边界和验收指标，而不是预先指定唯一训练算法（见 [55](/ai-product-100-concepts/evaluation-governance/#concept-55)）。


---

<a id="concept-79"></a>

## 79. 训练后量化 PTQ

*GPTQ / AWQ*

> 类比：像「成品出厂前的瘦身包装」，模型已经练好，不用重训，直接把权重精度压下来就能发货上线，省掉从头再练的代价（区别于 23 量化，PTQ 特指训练完成后的这一步压缩）。

### 专业定义

PTQ（Post-Training Quantization）在模型训练完成后直接把权重从 FP16 压到 INT4/INT3，无需重训；GPTQ、AWQ 是当前主流权重量化算法，是 23 量化的工程实现。

### 核心机制

分析权重重要度，对敏感权重保留更高精度、冗余权重压更低比特（AWQ 的「激活感知」保护重要通道），目标是在显著降低权重显存的同时控制任务质量损失；实际结果依模型、校准数据和量化配置而异。

### 产品启示

私有化 / 端侧（见 [72](#concept-72)）部署标配，同模型 INT4 显存仅 FP16 的 1/4，单卡跑更大模型；选型把「是否支持 AWQ/GPTQ」列为部署约束，并与 75 推理引擎兼容性核对。

<a id="concept-96"></a>

## 96. 世界模型

*World Model*

> 类比：像「老司机脑子里的路况预判」——不必真撞一次，也能想象下一步会发生什么。

### 专业定义

世界模型是系统对环境状态与因果的动态内部表征，能基于当前状态推演未来，支撑规划与具身决策。

### 核心机制

系统对环境状态与因果的动态内部表征，能基于当前状态推演未来与反事实后果；在 LLM 语境下表现为对物理与社会常识的隐式建模，支撑规划与具身决策。

### 产品启示

适用于仿真、预测与规划类场景（游戏、机器人、供应链）。但 LLM 的世界模型是统计近似而非真实物理，关键决策要可验证、可干预，不能盲信其推演结果。

<a id="concept-99"></a>

## 99. 模型供给与 MaaS

*Model Supply & MaaS*

> 类比：像「用水不必自建水厂」——按用量从模型云平台接水，高峰多接、淡季少接，省下自建大模型的重资产。

### 专业定义

模型供给与 MaaS（Model as a Service）指通过 API/平台按需获取模型能力，产品侧不再自建全栈训练。

### 核心机制

通过 API 或平台按需获取模型能力（闭源、开源托管或自部署），产品侧不再全栈自训；供给层决定可用性、价格、合规与版本节奏，模型可热替换。

### 产品启示

把「模型选择」做成可配置（按任务路由不同模型）；关注供应商锁定、SLA、数据出域与版本漂移；预留多供应商与自托管兜底，避免单点依赖。

<a id="concept-63"></a>

## 63. 模型路由

*Model Routing*

> 类比：像「按难易派单」，简单意图走便宜小模型，复杂推理走强模型，运行时动态选择模型，有机会在质量约束下优化整体成本与延迟。

### 专业定义

模型路由是按请求的任务类型、敏感度、用户层级、语言、预期输出结构等特征，在运行时自动将请求导向不同等级/供应商模型的架构机制，是一种常见的成本与质量治理手段。

### 核心机制

典型路由器 = 分类器 + 策略表 + 校验器 + 兜底。先分类请求，再选满足延迟/成本约束的主模型，经轻量校验（schema/策略/事实性）后，失败则升级到更强模型或转人工。

### 产品启示

把「选模型」从一次性架构决策变为运行时决策，有机会在满足质量底线的前提下降低整体成本，但收益取决于任务分布、模型价差与路由准确率（见 [24](#concept-24)/[58](/ai-product-100-concepts/evaluation-governance/#concept-58)）。PM 须定义路由规则与分层 SLA，低敏摘要→自托管小模型；中敏客服→中层 API；高敏法务→前沿模型+人工复核。路由是「模型网关」，务必配套可观测与回滚（见 [69](/ai-product-100-concepts/evaluation-governance/#concept-69)/[59](/ai-product-100-concepts/evaluation-governance/#concept-59)）。
