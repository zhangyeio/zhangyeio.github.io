## 09. Hallucination 幻觉

*Hallucination*

> 类比：像「没有核对资料就直接作答」：回答可能语言流畅、结构完整，却与事实或给定证据不一致。

### 专业定义

幻觉指模型生成看似合理但与事实不符、或缺乏依据的内容，常与概率生成目标、训练数据局限、上下文不足和系统链路错误有关。

### 核心机制

模型不会自动执行可靠的事实核验；当知识、上下文或任务约束不足时，可能生成看似合理但缺乏依据的答案，也可能拒答。幻觉率会随模型、任务、提示、知识时效与评测定义大幅变化；产品应在自己的事实性问答集上建立基线，并分别测量答案正确性、引用忠实度与拒答质量。

### 产品启示（三条防范路径）

RAG 接地基于真实文档作答；

输出校验生成后二次核查数字/规则是否匹配；

信任度设计标注来源，低置信度转人工。

上线前应在具有代表性的评测集上做 Bad Case 测试（见 [53](#concept-53)），别拿 Demo 效果当真。

<a id="concept-17"></a>

## 17. Prompt Injection 提示词注入

*Prompt Injection*

> 类比：像「有人冒充老板发邮件」，模型分不清「系统真指令」和「用户伪装的指令」，一句「忽略上面所有要求」就可能套出商业机密。

### 专业定义

Prompt Injection 是不可信输入改变模型预期行为或输出的漏洞，可能导致越权调用、敏感信息泄露或错误决策，是生成式 AI 应用需要重点治理的风险之一。[^9]

### 核心机制

模型难以区分「系统真指令」与「用户伪装的指令」，即使接口存在消息角色和指令优先级，模型仍可能把不可信内容误当成可执行指令；接入网页、文档和工具后还会出现间接注入。

### 四层防护

输入检测分类模型/规则过滤注入模式；

Prompt 加固明确指令边界，并把外部内容标记为不可信数据；Prompt 加固只能降低风险，不能替代权限控制；

输出过滤检查是否含 System Prompt 片段或敏感信息；

权限隔离按用户权限严格限制可调工具与数据。

面向用户的产品上线前应进行覆盖直接注入、间接注入、越权工具调用和敏感数据泄露的红队测试，并在上线后持续回归；不存在一次测试即可证明“攻不破”的安全状态。

<a id="concept-51"></a>

## 51. Precision 精确率

*Precision*

> 类比：像「报出的结果尽量是真的」。例如某些需要立即处置的风控环节，误伤正常用户代价很高，因此会提高精确率；而在线索筛查阶段则可能优先召回率。

### 专业定义

精确率 = 预测为正且确实为正 / 预测为正，衡量「别乱报」（预测阳性的纯度）。

### 产品启示

在误报代价较大的流程环节，应重点关注精确率；提高判定阈值通常会减少误报，但可能降低召回率。指标取舍应同时考虑误报成本、漏报成本和后续复核能力，同一业务的不同阶段也可能采用不同策略。

<a id="concept-52"></a>

## 52. Recall 召回率

*Recall*

> 类比：像「宁可误报不可漏报」，内容安全漏一条违法被举报，平台就被约谈，所以宁可多删几条正常评论也不能漏真违规。

### 专业定义

召回率 = 预测为正且确实为正 / 实际为正，衡量「别漏掉」（真实阳性的覆盖率）。

### 产品启示

在内容安全筛查、疾病初筛等漏报代价较大的环节，通常更重视召回率，再通过二级模型或人工复核控制误报。Precision 与 Recall 往往随阈值变化而此消彼长；F1 是二者的调和平均，但不包含具体业务成本，设计时仍应先确定主指标，并为次指标设置底线。

<a id="concept-53"></a>

## 53. Bad Case 分析

*Error Analysis*

> 类比：像「每周复盘错题本」，别凭感觉改 Prompt，把踩坑、退单、投诉拉出来分类归因，哪类问题对应哪类修法，一周修一点稳定上升。

### 专业定义

Bad Case 分析是基于线上真实失败样本，分类归因并针对性优化的方法论，是 AI 产品迭代的核心闭环。

### 五步法

收集按周期采样日志 + 负反馈标记，按业务量和风险分层抽样，并保证覆盖高频、长尾和高风险样本；

分类幻觉/拒答/格式错/逻辑错/检索失败，统计占比；

归因根因（Prompt/知识库/检索/模型能力）；

修复对症优化；

验证同集验证防改 A 坏 B。

### 产品启示

固定节奏复盘 Bad Case，通常比仅凭主观感受调整 Prompt 更可验证。Bad Case 告诉你问题在哪，不用猜。

<a id="concept-54"></a>

## 54. 数据标注

*Data Annotation*

> 类比：像「给 AI 出标准答案的阅卷」，标注指南不写细，两个人标出相反结果，数据一致性差，训出来的模型就废。

### 专业定义

数据标注是为训练/评测生产高质量标注样本的过程，标注质量即模型质量上限。

### 三环节卡死

标注指南边界 Case 必有明确标准，不能靠标注员自解；

试标校准先进行小批量多人试标，选用适合任务的 Kappa、Krippendorff's alpha 或一致率；阈值应结合任务风险和行业要求设定；

质检机制持续抽检，准确率低于阈值者重训。

### 成本参考

标注单价、所需训练样本和评测集规模受任务复杂度、领域资质、质量目标和模型能力影响，应先试标并根据学习曲线估算。标注周期与成本最易被低估。

<a id="concept-55"></a>

## 55. Human Evaluation 人工评测

*Human Evaluation*

> 类比：像「请人尝菜而非只看热量表」，BLEU/ROUGE 只比文本相似度，判不出「答得对但像机器人说话」；语气合不合适只有人评得出。

### 专业定义

人工评测由人按多维度（准确性/相关性/流畅度/安全性/有用性）对模型输出打分，弥补自动指标（BLEU/ROUGE）只能测文本相似度、测不了「好不好用/安不安全/语气合不合适」的缺陷。

### 标准流程

定义维度与评分量表 → 准备覆盖主场景、长尾和高风险样本的评测集 → 采用盲评并检查评审一致性 → 对低一致性维度重新校准标准 → 汇总定位短板。样本规模和一致性阈值应由任务风险、差异大小与统计把握度决定。

### 产品启示

每次模型更新或 Prompt 大改后跑一轮，评测集规模应由场景数量、风险和长尾分布决定；先用覆盖主流程的小型集合建立基线，再持续纳入线上 Bad Case。人评是自动指标的「护城河补充」，非替代关系。

<a id="concept-57"></a>

## 57. Latency 延迟

*End-to-end Latency*

> 类比：像「排队等咖啡」，AI 产品端到端可能等几秒到十几秒，用户耐心比传统 App 少得多；流式输出就是把「等出杯」变成「边做边递」。

### 专业定义

端到端延迟是用户发请求到收到完整回答的总耗时。生成式 AI 的端到端延迟通常显著高于传统确定性接口，并随模型、输出长度、工具调用和负载变化。

### 延迟构成

端到端延迟可拆为网络传输、排队、首 token 生成、逐 token 输出、工具调用与结果返回；各项应通过链路追踪实测。高峰期排队可能成瓶颈。

### 产品启示（优化）

流式输出（降感知延迟）、Prompt 精简（收益依模型和服务负载实测）、选更快模型（小模型优于大模型）、预加载（预判意图提前发）、体验设计（loading/分步/先摘要后展开）。

<a id="concept-58"></a>

## 58. Rate Limiting 限流

*Rate Limiting*

> 类比：像「商场限流闸机」，不是为难顾客，是高峰怕挤爆；供应商层、系统层、用户层三层限流，保住核心体验不崩。

### 专业定义

限流是通过配额约束保护系统不被流量峰值击穿的机制，非「限制用户」，而是「保护体验」。

### 三层规划

供应商层API Key 的 RPM/TPM 上限，超即 429；

系统层自有后端对用户请求限流，防击穿供应商；

用户层每用户日调用配额，VIP/免费不同。

### 产品启示

PRD 须定义，正常/峰值负载、限流时的用户提示（禁空白报错）、是否排队、降级策略（临时切更便宜更快模型）、突增自动扩容规则。不提前设计，首次流量高峰即事故。

<a id="concept-59"></a>

## 59. 灰度发布

*Canary / Staged Rollout*

> 类比：像「先小范围试吃再全城铺开」，改个 Prompt 直接全量，长尾场景客诉可能飙升；5%→10%→30%…逐步放量，不行就回滚。

### 专业定义

灰度发布是将变更先对小比例流量生效、对比核心指标、逐步放量的发布策略，是应对 AI 系统「概率性」风险的必备手段。

### 标准流程

先向小比例、低风险流量开放，对质量、满意度、延迟、成本和安全指标观察足够周期，再逐步扩大；任一步触发预设退化阈值即暂停或回滚。具体比例与观察周期应按流量、风险和统计把握度确定。

### 产品启示

影响模型行为的变更应根据风险采用灰度、影子流量、离线回放或受控试验等发布策略。小规模案例变好不代表线上总体效果改善，因此需要预设回滚条件并监测分群结果。

<a id="concept-60"></a>

## 60. 数据飞轮

*Data Flywheel*

> 类比：像「越用越聪明的雪球」，每次交互产生的点踩/复购都是反馈，回流优化模型，体验变好吸引更多用户，更多数据让雪球越滚越快，后来者追不上。

### 专业定义

数据飞轮是通过持续收集用户反馈与行为数据、反哺优化模型、从而提升体验吸引更多用户、产生更多数据的自我增强闭环，是 AI 产品的终极壁垒。

### 四阶段闭环

产品上线 → 收集数据 → 优化模型 → 体验提升 → 吸引更多用户 → 更多数据（越转越快）。

### 产品启示（须主动设计）

定义收集哪些数据，

隐式反馈用户点「重新生成」= 对上次不满；

显式反馈点赞/点踩/评分；

行为数据是否复制使用、是否手动修改；

转化数据AI 推荐是否被点击购买。

飞轮不是自然形成，是被设计出来的。先跑起来的产品护城河越来越深，别人可追技术，追不上已积累的真实业务数据。越早做越好，因数据积累有时间价值。

<a id="concept-69"></a>

## 69. 大模型可观测性

*LLM Observability / LLMOps*

> 类比：像「给 AI 装行车记录仪」，每次调用链、延迟、成本、幻觉全留痕，出问题能定位哪一步；部分高风险或受监管场景还需要满足相应的日志、监控和文档义务。

### 专业定义

LLM 可观测性是端到端追踪 AI 系统每次推理/Agent 执行的全链路（输入、检索、工具调用、输出、延迟、成本、质量），并配套评测门禁与回放调试的工程实践，是生产级 AI 系统的重要基础能力。

### 核心机制

通过 Langfuse / Arize Phoenix / Braintrust / LangSmith 等采集 trace、span、eval；将评测作为 CI 门禁（变更须过场景测试才放行）。它也可为法规合规和风险管理提供证据。EU AI Act 的具体义务取决于系统角色与风险分类；NIST AI RMF 是自愿性框架。[^7][^8]

### 产品启示

上线前应建立与风险等级匹配的可观测能力。PM 可要求，全链路追踪、幻觉/毒性/延迟看板、模型版本血缘、每日自动评测、人工反馈回流（见 [53](#concept-53)/[55](#concept-55)/[60](#concept-60)）、合规审计日志。缺少可观测能力时，应限制放量并保留回滚路径（见 [59](#concept-59) 灰度）。

<a id="concept-74"></a>

## 74. 安全护栏

*Guardrails*

> 类比：像「产品里的减速带和护栏」，在 Prompt、工具、输出各层设规则，越界就拦；OpenAI Agents SDK 已内置，是 to C 产品的必备件。

### 专业定义

Guardrails 是部署在模型输入/输出边界的产品层安全策略与校验机制，对越权、违规、敏感、格式、事实性等风险做强制拦截或降级，是「安全左移」到产品层的体现（OpenAI Agents SDK 等已内置）。

### 核心机制

请求进模型前做输入护栏（敏感词/注入检测，见 [17](#concept-17)），输出出模型后做输出护栏（schema 校验、PII 脱敏、事实性核查、拒答规则）。可与可观测（见 [69](#concept-69)）联动形成审计闭环。

### 产品启示

任何 to C / 企业级 AI 都须把护栏作为一等公民写进 PRD，定义拦截策略、降级路径（转人工/标准话术）、审计日志与红队持续测试（见 [17](#concept-17)/[53](#concept-53)/[59](#concept-59)）。护栏不是模型的事，是产品的责任边界。

<a id="concept-81"></a>

## 81. LLM-as-Judge / Agent 评测

*LLM-as-Judge*

> 类比：像「让一位资深同事当评委」，用强模型按评分表给另一模型的输出打分，规模化替代部分 55 人工评测。

### 专业定义

LLM-as-Judge 用大模型替代或辅助人类，对生成内容按预设维度（准确性、有用性、安全）自动评分，是 55 人工评测的工程化扩展，也用于 Agent 任务成败判定。

### 核心机制

给定 rubric 与待评样本，裁判模型输出结构化评分 + 理由；常与人工抽检交叉验证，用裁判间一致性筛选「难样本」回流标注。

### 产品启示

上线前用 LLM-as-Judge 跑大批量回归（每改一次 Prompt 见 [02](/ai-product-100-concepts/prompt-generation/#concept-02)/[64](/ai-product-100-concepts/prompt-generation/#concept-64) 都测一遍），成本远低于全量人评；但须防「裁判自己也幻觉」，关键决策保留人评兜底，把裁判分当趋势信号而非终审。

<a id="concept-82"></a>

## 82. 红队测试

*Red Teaming*

> 类比：像「请白帽黑客来搞破坏」，正式上线前，专找人用各种歪招攻击你的 Prompt、工具、护栏，看能不能攻破。

### 专业定义

红队是以对抗视角系统性尝试突破 AI 系统安全边界的测试活动，覆盖提示注入（见 [17](#concept-17)）、越权调用、敏感泄露、越狱（jailbreak）等，是安全左移的验证环节。

### 核心机制

红队成员构造对抗样本与攻击链，对 17 注入、74 护栏、56 API 边界逐一施压，记录突破点与影响面，输出修复清单并复测。

### 产品启示

面向用户或高风险业务应在上线前开展与威胁模型匹配的对抗测试，并在模型、Prompt、工具或权限变化后回归。红队测试与 Bad Case 分析互补：前者主动寻找可利用路径，后者分析自然发生的失败（见 [53](#concept-53)）。

<a id="concept-84"></a>

## 84. AI 合规框架

*EU AI Act / NIST AI RMF*

> 类比：像「产品的交规和年检」，不同风险等级适用不同强制要求，违规不是道歉能解决的。

### 专业定义

EU AI Act 是具有法律约束力的欧盟法规，规定禁止性做法、高风险系统义务、特定透明度要求以及通用目的 AI 模型规则；其条款分阶段适用。NIST AI RMF 则是自愿、非行业特定的风险管理框架，核心功能包括 Govern、Map、Measure、Manage。[^7][^8]

### 核心机制

先确定组织在具体场景中的角色、系统风险分类和适用日期，再识别相应的数据治理、技术文档、日志、透明度与人工监督义务。不同主体和系统类别的要求并不相同。

### 产品启示

面向受监管市场或高风险用途时，应尽早让法务、合规、安全和产品共同确认适用范围、证据留存与人工监督要求。产品文章只能提供风险识别框架，不能替代针对具体业务的法律意见（见 [69](#concept-69)/[83](/ai-product-100-concepts/agents/#concept-83)）。

<a id="concept-85"></a>

## 85. AI 成本工程 FinOps

*AI FinOps*

> 类比：像「给 AI 算明细账的财务」，不只看总账单，而是按模型、按功能、按用户拆出每笔钱花在哪、值不值。

### 专业定义

FinOps for AI 是把模型成本透明化、按业务维度分摊与优化的工程实践，计量每次调用的模型、Token、工具次数，定位高成本低价值环节。

### 核心机制

埋点采集每次推理的 model × tokens × tool_calls × 延迟，聚合到「功能 / 用户 / 会话」维度，结合 65 提示缓存命中率、63 模型路由命中率找优化点。

### 产品启示

把「单功能月成本」写进 PRD 验收（呼应 03/24）；用 63 路由 + 65 缓存 + 小模型（见 [72](/ai-product-100-concepts/model-selection/#concept-72)）+ 批处理把成本压到可接受线，再谈商业化。成本不透明，会使商业模型缺乏可靠依据。

<a id="concept-86"></a>

## 86. AI 定价与价值定价

*Pricing / Value-based Pricing*

> 类比：像「把成本变成用户愿意付的价格」，一杯奶茶成本几块，卖你 30，是因为「送到手」的便利值这个价。

### 专业定义

AI 定价是依据成本结构（见 [03](/ai-product-100-concepts/model-selection/#concept-03)/[24](/ai-product-100-concepts/model-selection/#concept-24)/[85](#concept-85)）与用户感知价值，设计订阅、按量、按结果或混合计费模式，让产品形成商业闭环。

### 核心机制

核算「每服务一次的真实成本」（推理 + 工具 + 缓存命中），对照用户愿为「省下的时间 / 办成的事」付多少，定档位与上限；高价功能配 83 人工兜底控风险。

### 产品启示

PM 要算「毛利 = 客单价 − 单次成本 × 频次」，用 58 限流 + 分层配额（免费 / VIP）保护利润；定价本身也是「护栏」，防被刷爆（见 [58](#concept-58)/[74](#concept-74)）。成本工程（85）与定价（86）合起来，才叫商业闭环。

<a id="concept-88"></a>

## 88. Synthetic Data 合成数据

*Synthetic Data*

> 类比：像「请资深员工照着真实工单，批量编造一批脱敏演练单」——既保住了业务分布，又不会泄露客户隐私。

### 专业定义

合成数据是用模型或规则生成、人工生成、模型生成或仿真得到的样本；它可以降低直接使用真实数据的需求，但不能自动等同于匿名化，常用于训练、微调、评测与隐私合规场景。

### 核心机制

用更强的生成模型、仿真器或规则产生近似真实分布的样本，再经过滤、去重、质量评分与隐私脱敏（如差分隐私、合成—真实混合）评估可用性、偏差、记忆泄漏和隐私风险；常用于冷启动、长尾覆盖与评测集构造。

### 产品启示

它解决「真实数据不够或不能碰」的困境，但有两个陷阱：一是模型塌陷（用合成数据反复训练自身会丢失多样性），二是分布偏移（合成分布 ≠ 线上分布）。落地要把「合成占比 + 真实数据校验」写进数据管线，并保留可审计的来源。

<a id="concept-89"></a>

## 89. Personalization 个性化体验

*Personalization*

> 类比：像「同一个 App，对老用户和新游客长成了两张脸」——不是换皮，是它真的记得你是谁、要什么。

### 专业定义

个性化是基于用户历史、身份与上下文，动态调整内容、语气与功能的体验策略；在 AI 产品里，它由用户画像与记忆机制共同驱动。

### 核心机制

基于用户画像、历史行为与当前上下文，在推理时注入个性化信号（长期记忆、偏好、角色设定），动态调节输出的语气、内容与功能；可离线预计算画像，也可在线实时拼接进提示。

### 产品启示

个性化是高留存杠杆，但带来可解释与隐私风险。建议做分层（全局默认 / 群体 / 个人），提供「为什么给我这个」的可解释说明与一键关闭开关，并把同意与数据最小化作为默认。

<a id="concept-90"></a>

## 90. AI Search 答案引擎

*Answer Engine*

> 类比：像「不给你一堆蓝色链接，而是直接端上一盘已经拌好的菜」——你问完，答案和出处一起上桌。

### 专业定义

答案引擎以「生成式检索」替代传统罗列：先理解意图、检索并阅读多源资料，再综合成带引用的直接答案，而非十条链接。

### 核心机制

以「生成式检索」替代链接罗列：意图理解 → 多源检索 → 阅读与去重 → 带引用的综合回答；答案上限取决于检索召回率、来源可信度排序与引用忠实度（不编造出处）。

### 产品启示

价值在于「直接给结论 + 可溯源」，而非十条蓝链接。要公开来源、支持追问与多源对比，并重点监控幻觉引用（编造或错位的出处）；商业模式也从广告转向订阅或按次计费。

<a id="concept-91"></a>

## 91. AI 原生应用

*AI-Native App*

> 类比：像「为电设计的电器，而不是给马车装发动机」——从根上就以对话、生成、推理为主交互，而非在传统界面上贴一层智能。

### 专业定义

AI 原生应用指架构与交互围绕模型能力重做的产品：核心流程由生成/推理驱动，传统 CRUD 退为底层支撑。

### 核心机制

架构围绕模型能力重做——核心流程由生成、推理与工具调用驱动，传统数据库与 CRUD 退为被调用的底层能力；天然支持自然语言入口、非结构化处理与自适应流程。

### 产品启示

不要只在旧产品上「加一个 AI 按钮」。应重新设计信息架构与交互（流式输出、可中断、可溯源），并把模型的不确定性显式纳入 UX，而不是假装每次都确定。

<a id="concept-93"></a>

## 93. Agent UX 智能体交互设计

*Agent UX*

> 类比：像「给实习生派活」——你不能只给结果页，得让他边想边汇报、可随时打断、可撤回重来。

### 专业定义

Agent UX 是面向「会自主行动的系统」的交互范式：强调过程可见、可干预、可回滚，而非传统「请求—响应」黑箱。

### 核心机制

面向会自主行动的系统：强调过程可见（展示计划与步骤）、可干预（中途改指令或暂停）、可回滚（撤销已执行动作）；信任来自「可控」而非「全自动」。

### 产品启示

把黑箱式的「请求—响应」改成白盒协作：提供计划预览、分步确认（高危操作必确认）、运行日志与一键中止；高风险动作默认设置人在回路；低风险、可撤销动作可在明确授权和完整日志的前提下提高自动化程度。

<a id="concept-95"></a>

## 95. 评测驱动开发

*Eval-Driven Dev*

> 类比：像「先写验收标准再写代码」——不是上线后看客诉，而是用一套考题在每次改动后给模型打分。

### 专业定义

评测驱动开发把「评测集+指标」作为 AI 功能的一等公民：改动前后跑同一套题，用分数变化判断是否退步。

### 核心机制

把「评测集 + 指标」作为功能的一等公民：改动前后跑同一套题，用分数（准确率、忠实度、偏好、成本）变化判断是否退步；结合自动评测与人工抽检形成基线。

### 产品启示

没有评测就没有迭代基线。建立「黄金集 + 回归集」，每次发布前必跑；指标要与业务目标对齐（如满意度、转化率），警惕「指标涨了、体验却降了」的错位。

<a id="concept-100"></a>

## 100. AI 产品增长与留存

*AI Growth & Retention*

> 类比：像「健身房续费」——首月新鲜感拉新，真正留人的是「它让我变强了」的持续价值。

### 专业定义

AI 产品增长与留存关注「首用惊艳→习惯养成→价值证明」的链路，用个性化与记忆把一次性尝鲜变成长期依赖。

### 核心机制

增长靠「啊哈时刻」的触达与复访钩子，留存靠把 AI 能力嵌进高频刚需场景并持续兑现价值；在用户授权、反馈质量和数据治理成立时，个性化与反馈闭环可能提升长期价值；网络效应和数据飞轮并不会自动形成。

### 产品启示

增长不等于堆功能。用 Aha-moment（首次感知价值）、留存曲线与价值时刻衡量；把 AI 能力放进用户每天本就要做的事里，而非做成孤立的玩具，留存才有支点。
