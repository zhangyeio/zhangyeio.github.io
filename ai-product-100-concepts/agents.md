## 06. Agent 智能体

*Autonomous Agent*

> 类比：像「会自己动手的助理」，不止动嘴给建议，而是自己拆任务、调工具、看结果、再决定下一步，直到把事办成。

### 专业定义

Agent 是以目标为导向、具备「规划—工具调用—观察反馈」闭环能力的系统，能自主拆解复杂任务并调用外部工具执行，而非仅生成文本。

### 核心机制（三件套）

规划（Planning）将目标拆为可执行步骤；

工具调用（Tool Use）通过 API 执行每步操作；

观察调整（Observation）依据执行结果决定继续或换路。

### 产品启示

设计范式从「对话流」变为「任务流」。对话流有标准答案，任务流没有，每次执行路径可能不同。当前最大问题是可靠性多步串联错误累积。带过的 Agent 项目里，兜底策略设计时间占比常高于主流程（约 3:7）。Agent 失败用户可接受，失败还不告知用户则不可接受。

## 07. Function Calling 函数调用

*Tool/Function Calling*

> 类比：像「助理口述、秘书动手」，模型只负责说「去调下单接口，门店=瑞幸、商品=燕麦拿铁」，真正执行的是你后端代码。

### 专业定义

Function Calling 是模型以结构化方式（通常为 JSON）输出「应调用哪个函数及参数」的能力；真正执行操作的是后端代码，模型只负责「决策与产出调用请求」。

### 核心机制

预先向模型声明可用工具及参数 Schema；用户自然语言请求后，模型从工具列表选最匹配者，输出结构化调用请求；后端执行并将结果回传模型，模型再生成最终回复。

### PM 四项定义职责

工具集Agent 可用哪些工具，功能描述需写到模型可理解；

使用条件何时调何工具，边界清晰；

优先级多工具可用时如何排序：建议按「成本→能力→用户意图」定优先级，并用兜底链路（fallback）保证关键路径不中断；

错误处理超时、空结果、格式异常的兜底：须定义重试次数与退避策略、参数合法性校验（Schema 校验，拒绝非法入参）、以及最终失败时的降级话术，避免把未处理的内部异常直接暴露给用户；

工具描述质量直接决定选对率，把工具描述当 API 文档写（名称/功能/参数/返回值/场景）。

💡 产品启示

Function Calling 把「模型决策」与「代码执行」彻底解耦：模型只产出调用请求，真正干活的是你的后端。PM 的核心风险不在模型多聪明，而在工具定义是否清晰、失败处理是否兜底——把每个接口当产品契约来设计（名称/功能/参数/返回值/场景），比换更贵的模型更能决定体验上限。

## 12. MCP 模型上下文协议

*Model Context Protocol*

> 类比：像「AI 世界的 USB 接口」，不管插鼠标还是 U 盘，协议统一；工具按 MCP 封装，换模型、换应用都能直接插上用。

### 专业定义

MCP 是连接 AI 应用与外部资源、工具和提示模板的开放协议，采用 Host—Client—Server 架构，并通过能力协商明确双方支持的功能。[^5]

### 核心机制（三角色）

MCP Host

模型所在应用；

MCP Client

协议通信中间层；

MCP Server

具体工具的服务端封装。

工具封装为 MCP Server 后，任何支持 MCP 的模型/应用均可直接调用，无需单独写对接代码；换底层模型时工具层不动。

### 产品启示

重点关注工具注册与权限管理，产品能连哪些工具、用户是否有权调用、失败如何兜底。这些直接影响体验与安全性，需要产品、研发与安全团队共同定义。（与 A2A 配合见 [67](#concept-67)）

## 38. Workflow 工作流

*Workflow Orchestration*

> 类比：像「固定 SOP 而非自由发挥」，步骤、工具、格式全预定义，稳定可控；商业场景错一步代价大，比让 Agent 自由规划靠谱。

### 专业定义

Workflow 是将复杂任务拆为固定步骤序列、每步输入输出与逻辑预定义的确定式执行框架，区别于 Agent 的自由规划。

### 产品启示（选择标准）

- 步骤固定、规则明确、错一步代价大 → 用 Workflow（稳定可控）；

- 步骤不可预测、需动态决策、探索性强 → 用 Agent。

绝大部分企业落地场景适合 Workflow，因稳定可控比灵活重要。成熟产品多为混合，主流程 Workflow 保可控，个别灵活节点嵌 Agent。Dify/LangFlow/Coze 支持可视化编排。

## 39. Multi-Agent 多智能体

*Multi-Agent System*

> 类比：像「一个团队各管一摊」，一个 Agent 干所有事容易样样稀松，拆成点单 Agent、查询 Agent、路由 Agent，按角色分工有时更易控制，但也会增加协调、延迟和成本。

### 专业定义

Multi-Agent 是将任务按垂直领域分解给多个专职 Agent，通过协调/通信机制协同工作的架构，用于任务确实可以分解、并行或相互校验的场景；它并不天然优于单智能体。

### 两种主流架构

Orchestrator 模式协调者 Agent 理解需求、拆分、分发、汇总（任务分界明确场景）；

讨论模式多 Agent 各抒己见互评综合（需多角度分析场景）。

### 产品启示（四定义）

各 Agent 职责边界、通信协议、任务路由规则、冲突解决机制（矛盾结果如何处理须事先定义）。推荐三层，Router Agent（意图识别分发）+ N 个垂直 Agent + 共享工具池。

## 40. Planning 规划能力

*Planning*

> 类比：像「先列待办再动手」，好 Agent 会先拆步骤、排依赖、失败了换路；没规划的 Agent 上来就干，做到一半发现缺前提只能重来。

### 专业定义

Planning 是 Agent 将复杂目标拆为可执行子任务、确定依赖与顺序、并在执行中动态调整的能力，是当前大模型最薄弱的环节之一。

### 三层能力

任务分解拆为可执行子任务；

依赖排序确定先后与并行/串行；

动态调整某步失败则重规划而非崩溃。

### 产品启示

复杂多步任务的成功率高度依赖模型、工具、任务长度与评测口径，不能用单一比例概括。常见提升方法包括预定义计划模板、限制可选动作、分步校验、失败重试与必要的人工确认。

## 41. Memory 记忆机制

*Memory*

> 类比：像「助理的笔记本」，工作记忆管当前会话，短期记忆存近期摘要，长期记忆记你的过敏和偏好；关掉页面再打开，它还记得你乳糖不耐受。

### 专业定义

Memory 是跨会话长期存储与调用用户信息的机制，区别于仅管当前对话的上下文管理。

### 三层架构

工作记忆当前对话上下文，关会话即清；

短期记忆可保存近期会话摘要，保留期限应由任务价值、用户预期和隐私政策确定；

长期记忆用户固定属性/偏好（过敏、习惯），永久存。

### 产品启示

须定义「什么值得记、存多久、冲突怎么办」（用户改口偏好记哪个？需更新规则）。应依据适用的隐私法规、产品承诺和数据类型，提供相应的访问、更正、删除或撤回机制。

<a id="concept-42"></a>

## 42. ReAct 推理与行动

*Reasoning + Acting*

> 类比：像「边想边干、干完再看」，先想「我得先知道用户在哪」，再定位，再看结果，再想下一步，每步都基于真实信息而非凭空编。

### 专业定义

ReAct 是让 Agent 在「思考（Thought）—行动（Action）—观察（Observation）」间循环交替的框架，使每步基于真实外部信息而非凭空生成。

### 核心机制

传统一步到位易编造；ReAct 多步循环，每步推理链路可追溯，出错可定位是「想歪」还是「工具调错」。

### 产品启示（延迟代价）

每次循环含一次推理+一次工具调用，复杂任务可能经历多轮推理与工具调用，端到端延迟会随步骤数快速累积。须设计「进度反馈」与「分步展示」。

<a id="concept-43"></a>

## 43. Tool Use 工具使用

*Tool Use*

> 类比：像「扬长避短」，模型擅长理解和说，不擅长算数和查实时数据，就给它配计算器、搜索引擎、代码执行器，让它当「指挥官」而非「操作员」。

### 专业定义

Tool Use 是为模型配外部工具（计算器/搜索/代码执行/API），弥补模型不擅长精确计算、实时数据、确定操作的短板。

### 产品启示（四维设计）

工具粒度一事一工具，避免瑞士军刀式（粒度越细选择越准）；

错误处理超时/空结果/格式异常；

权限控制用户可用哪些、工具可访哪些数据；

成本控制限制单次对话工具调用次数。

黄金法则，模型擅长的（理解/生成）让模型做，不擅长的（计算/查询/操作）让工具做。

<a id="concept-44"></a>

## 44. Orchestrator 编排器

*Orchestrator*

> 类比：像「项目总调度」，一句话同时触发点单+查快递，它负责拆意图、分任务、排顺序、合结果，没它多 Agent 就是一团散沙。

### 专业定义

Orchestrator 是 AI 系统的总调度，负责意图理解、Agent/Workflow 选择、多组件调用顺序协调与结果融合。

### 三层逻辑

意图路由请求属哪个场景、交哪个 Agent；

执行编排多 Agent 协作的先后与数据传递；

结果融合多输出合并为一条回复。

### 产品启示

Orchestrator 自身常是 LLM 驱动模块，其 Prompt 定义了所有 Agent 能力描述与路由规则，是整个系统最关键的 Prompt。其设计通常需要独立评测，不能被简化为单个 Agent 的 Prompt 优化。

## 67. 智能体间协议 A2A

*Agent-to-Agent Protocol*

> 类比：像「不同公司前台之间的转接规范」，MCP 是 Agent 连工具（垂直），A2A 是 Agent 连 Agent（水平），靠 Agent Card 互相认识、交办任务。

### 专业定义

A2A 是面向智能体互操作的开放协议，使用 Agent Card 描述能力，并定义任务委派、状态更新和产物交换等机制。协议归属与版本可能演进，实施时应核对官方规范。[^6]

### 核心机制

每个 Agent 发布一张 Agent Card（名片），声明能力、输入/输出格式；其他 Agent 读卡决定委派。截至 2026 年 7 月，A2A 已获得多家技术与企业软件厂商支持；组织数量和兼容程度仍在变化，引用时应核对协议官网的最新名单。它与 MCP 的定位总体互补，但实际集成仍需验证版本与实现差异。

### 产品启示

设计跨团队/跨厂商的多 Agent 协作（见 [39](#concept-39)）时，优先采用 A2A + MCP 标准，避免为每个对接写胶水代码。PM 须关注 Agent Card 的能力声明粒度、委派权限边界与审计（见 [74](/ai-product-100-concepts/evaluation-governance/#concept-74) 护栏、17 注入）。

<a id="concept-70"></a>

## 70. 电脑操作智能体

*Computer Use / GUI Agent*

> 类比：像「雇了个会操作电脑的新人」，不给你开 API 也能点按钮、填表单、翻网页，像人一样用软件，补齐没接口的旧系统。

### 专业定义

Computer Use 指 Agent 直接操作图形界面（点击、输入、滚动、截图理解）完成任务的新型能力，无需为每个应用写 API 对接，把「数字员工」从「调接口」扩到「用软件」。

### 核心机制

模型接收屏幕截图→理解当前界面→输出操作动作（坐标/按键）→执行→再截图观察，循环至目标达成（类 ReAct，见 [42](#concept-42)）。Claude Computer Use、OpenAI Operator 为代表。

### 产品启示

适合「无 API 的老系统/长尾 SaaS」自动化，但风险高于 Function Calling（见 [07](#concept-07)），误操作代价大、可审计性差。PM 须设计「沙箱+确认+回滚+操作白名单+录像审计」，高敏操作须人工确认（见 [74](/ai-product-100-concepts/evaluation-governance/#concept-74) 护栏、17 注入）。UI 变动可能导致流程失效，需持续监控。

## 80. Agent 框架

*LangGraph / CrewAI*

> 类比：像「给 Agent 装交通信号灯和轨道」，自由发挥的 Agent 容易乱窜，框架用状态机 / 图把步骤钉死、可控可回放。

### 专业定义

Agent 框架是封装规划、工具调用、记忆、状态流转与人工协作的软件开发库，让多步 Agent 从「手写 prompt 循环」升级为「可编排、可调试的工程系统」。

### 核心机制

以图（LangGraph）或角色组（CrewAI）描述流程，节点 = 一步动作，边 = 转移条件，checkpoint = 状态持久化，使 40 规划、42 ReAct、41 记忆可工程化落地。

### 产品启示

生产级 Agent 别用裸循环，框架提供的断点续跑、状态回溯、人工介入节点（见 [83](#concept-83)）正是企业落地要的「可控性」；技术评审要问「用哪个框架、状态怎么存、失败怎么回滚」。

## 83. 人在回路 Human-in-the-loop

*HITL*

> 类比：像「关键路口设人工闸口」，Agent 能跑就让它跑，到了高风险一步先让人点个头再放行。

### 专业定义

HITL 是在自动化流程的关键决策点插入人工确认、修正或接管的设计模式，平衡自动化的效率与高风险错误的代价，是 74 护栏的「终极兜底」。

### 核心机制

在 Agent 工作流（见 [38](#concept-38)/[80](#concept-80)）中标注「需人工」节点（退款、外发消息、调用付费工具），流程在此挂起等待人工 action，结果回写记忆（见 [41](#concept-41)）与 60 数据飞轮。

### 产品启示

资金、对外承诺和不可逆操作等高风险动作，原则上应设置人工确认或等效的强校验机制；它既是护栏兜底，也是数据飞轮的高质量标注来源（人工修正即反馈）。设计时要明确「哪些节点必须人确认、超时怎么办」。

<a id="concept-87"></a>

## 87. Deep Research 深度研究智能体

*Deep Research Agent*

> 类比：像「带研究助理的写稿记者」，你给个题目，它自己查资料、交叉验证、边写边改，最后交一份带出处的新稿，而不是只扔一句答案。

### 专业定义

Deep Research 是一类以「多轮检索—阅读—综合」为主循环的智能体：给定开放性问题，它自主拆分子问题、调用搜索/数据库、阅读并提炼证据，最终产出带引用的结构化报告。

### 核心机制

以「规划—检索—阅读—综合」为主循环：把开放问题拆成子问题，并行或串行调用搜索、数据库、代码等工具，对检索到的证据做交叉验证与冲突消解，再用引用回溯拼成结构化报告。瓶颈通常不在模型，而在工具调用次数、上下文压缩质量与中途纠偏能力。

### 产品启示

交付物不是一句答案，而是一份带出处的调研过程；要把检索轨迹可视化、支持中途改方向，并对不确定结论显式标注置信度。成本通常受轮数、工具调用和 token 共同影响，应设置预算、超时与步数上限，否则容易出现调用轮数和成本失控。

<a id="concept-97"></a>

## 97. 具身智能

*Embodied AI*

> 类比：像「终于长出手和脚的大脑」——不再只在屏幕里聊天，而是能感知真实环境、动手完成物理任务。

### 专业定义

具身智能指将模型能力落到物理载体（机器人、车辆、设备），通过感知—决策—执行闭环与真实世界交互。

### 核心机制

将模型能力落到物理载体（机器人、车辆、设备），通过「感知—决策—执行」闭环与真实世界交互，并从反馈中持续学习；强调实时性、安全与鲁棒。

### 产品启示

落地于制造、物流、服务机器人等场景；难点在长尾环境与故障安全。产品设计要把「人类接管、急停、可解释」作为一等需求，而非事后补丁。

## 98. 多智能体协作拓扑

*Multi-Agent Topology*

> 类比：像「一个项目组，有人写、有人审、有人查资料」——不是一个人硬扛，而是按角色分工流转。

### 专业定义

多智能体协作拓扑描述多个智能体如何分工、通信与汇总：串行、并行、评议、层级等结构决定整体效果与成本。

### 核心机制

多个智能体分工、通信与汇总：串行（流水线）、并行（分治）、评议（多生成 + 裁决）、层级（管理者 / 工人）；拓扑结构决定效果、成本与延迟，需防范群体漂移与无限循环。

### 产品启示

用拓扑换取质量或并行度，但要监控 token 总消耗与一致性；关键任务加「裁判 / 汇总」角色与明确终止条件。不是智能体越多越好——先测单机基线再扩展。
